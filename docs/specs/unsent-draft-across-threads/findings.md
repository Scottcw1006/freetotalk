# bug 單：輸入框裡沒送出的字，切換對話之後還留著

**這個目錄沒有版號目錄＝還沒被拿起來。** 拿起來時走 spec-flow 路線 B；階段 0 的產出就是這一份。

記錄日期：2026-09-18。記錄時的程式碼：`main`，commit `07aa0a8`。

# 現象

來源：QA 在 `docs/specs/message-store-normalization/v1/test-report.md` 第 116 行的旁記：「輸入框裡沒送出的字在切換對話後仍留著。是不是問題由呼叫者判斷。」

RD 在模擬器（AVD Pixel_9，`main` 的建置）上重現到的：在人格「朋友」的對話裡輸入 `unsent zqdraft`、不送出 → 按「換人」選「老師」→ 畫面換成老師的新對話（開場白是「來，今天想弄懂什麼？慢慢說沒關係。」），**輸入框裡仍是 `unsent zqdraft`**，送出鈕可按。這時按送出，那句話會送進老師那一段，而不是原本打字時的那一段。

# 重現步驟

1. 打開 App，在聊天畫面的輸入框打幾個字，不要送出。
2. 做任何一種會換掉開著那一段的動作：「換人」選另一個人格、抽屜裡換模型、「開始新的對話」、從歷史清單打開另一段、從搜尋結果打開另一段。（RD 實際做的是第一種；其餘四種是依下面的診斷推的，沒有逐一做。）
3. 看輸入框：打的字還在。

每次都重現，不需要等、不挑模型。

# 診斷

`ui/ChatScreen.kt:748` —— `InputBar` 裡的草稿是 `var draft by remember { mutableStateOf("") }`。

- 它**沒有綁開著的是哪一段對話**：`remember` 沒有 key，`InputBar` 也沒有被包在以對話 id 為 key 的區塊裡（`ChatScreen.kt:550` 呼叫時只傳了 `enabled`、`isReplying` 與兩個 callback）。切換對話只換掉 `state.conversation`，`InputBar` 留在原位不重組，草稿自然留著。
- 草稿只活在畫面這一層，`ChatViewModel` 與 `ChatUiState` 都不知道有它，所以沒有任何一條切換的路有機會處理它。

**同一個根源帶出的相鄰行為**（觀察，不是這張單要修的範圍，但決定「什麼算對」時要一起看）：

- 它是 `remember` 不是 `rememberSaveable`，而 `InputBar` 離開畫面就會被丟掉：進搜尋或比較畫面再回來、旋轉螢幕、行程被系統回收，草稿都會**消失**。也就是說現在的行為是「換對話時留著、換畫面時不見」，兩邊方向相反。（依程式碼推的，沒有在裝置上逐一確認。）
- 送出時 `submit()` 先清空草稿再呼叫 `onSend`（`ChatScreen.kt:750-755`）；`ChatViewModel.send` 在 `canSend` 為否時直接 return（`ChatViewModel.kt` 的 `send`），那種情況下字會被清掉卻沒送出。`submit()` 自己先擋了 `enabled`，所以目前走不到，但兩邊各擋一次。

# 要不要 PM

**要。** 「什麼算對」不是自明的，而且沒有任何一份規格在管輸入框：`docs/product/features.md` 的聊天-01（輸入框）、聊天-02（空的時候送出鈕按不下去）都是「尚無 spec」。至少有三種說得通的答案：

1. **切換對話就清空。** 最單純；代價是打到一半不小心切走，字就沒了。
2. **每一段對話各自記得自己的草稿。** 切回去時字還在；草稿要不要撐過關掉 App 是連帶的問題（要的話就是一樣新的要存的東西，會碰到 `conversation-store-db` 與 `message-store-normalization` 的儲存規則）。
3. **維持現狀：草稿跟著輸入框走，不跟著對話走。** 有人會把它當成功能（先打字、再決定要問誰）；那就要把它寫進功能清單，並處理「換畫面時卻會不見」那個不一致。

選哪一個都會連帶決定：換畫面（搜尋、比較）與旋轉螢幕時草稿留不留。

**不得被修過頭的相鄰行為**：

- 送出之後輸入框清空、空的時候送出鈕按不下去（聊天-02）照舊。
- 回覆生成中仍然可以在輸入框打字（現在可以；送出鈕那時是停止鈕）。
- 切換對話的其他行為（被切走的那一段當下存檔、生成中切換會先停止）不因此改變 —— 那些分別由 `stop-generation`、`conversation-store-db` 在守。
- 搜尋畫面自己的輸入框（離開搜尋會清掉，搜尋-18）是另一個欄位，不在範圍內。

**重現案例要怎麼變成測試**：草稿現在只存在 Compose 的畫面狀態裡，JVM 測試碰不到。若裁決的做法把草稿搬進 `ChatUiState`／`ChatViewModel`，切換時草稿該變成什麼就能用 JVM 測試守；若留在畫面層，就只能是一條裝置上的驗收。這一點請 PM 在寫驗收時處理。
