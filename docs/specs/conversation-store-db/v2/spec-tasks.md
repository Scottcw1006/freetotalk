# 任務與驗收標準

## 先看這裡

**（v2）沒有任何條文在等決定。** D1–D4 已於 2026-09-17 拍板，每一條怎麼落到下面的任務，列在 slug 根目錄的 `changes-v2.md`。

**標準測試指令**：`./gradlew testDebugUnitTest`。**本輪所有新的自動化測試都只用現有的 JUnit、不碰資料庫**（D1）。

## 測資與讀取的約定（v2，依 D2 裁決）

**造測資分兩條路：**

1. **App 自己做得出來的資料，一律用 App 的正常操作建立**（送出訊息、切換、刪除…）。**每一個測試開一段新的對話**，那一條判讀完之後，**從 App 裡把那段刪掉**。
   - **清理排在判讀之後**：凡是要比「操作前後儲存裡的對話數或內容」的條文（任務 7 驗收 3、4、9 等），清理不得落在基準與判讀之間。
   - **開著的那段刪不掉**（刪除鈕只在抽屜清單上）：要清理時先開一段新的對話，再從抽屜刪。
   - **可以直接清空 App 資料的時候**（使用者已同意，模型檔保留），清空也算清理。
2. **App 做不出來的資料，才直接改資料庫檔**：只含助理訊息的對話、讀不起來的一段、整份壞掉的儲存。另外兩件同一性質的前置也走這一條：把**舊格式的對話檔**放進舊位置（新建置做不出它們）、把「上次停在哪」的偏好寫成一個指定值（任務 4 驗收 2）。
   - **一律在 App 停止時改、改完再冷啟動**：Room 看不到 App 以外的修改（`spec.md`「這次會踩到的既有事實」第 13 條）。
   - 位置與結構照任務 6 的交付物（`plan/architecture.html` 儲存那一節）。

**產品程式碼不加任何測試專用的匯入、匯出或造資料入口**（D2 的 (b) 不採用）。

**讀出「儲存的內容」**（任務 5、6、7 裡比對操作前後的條文）：**App 停止時，唯讀地直接讀資料庫檔**。比的是**內容**（每一段對話的每一個欄位、每一則訊息），不是檔案位元組 —— App 把同一段內容重寫一次不算改動。
- **這一點是 PM 的判斷，不是裁決的原文**：裁決講的是「怎麼造資料」，沒有直接講「怎麼讀」。「唯讀地讀資料庫檔」不寫入任何東西、不需要產品程式碼，屬於裁決第二條路的延伸；**而且只有它看得到儲存裡精確的最後更新時間**（畫面上只顯示到分）。理由記在 `spec-decisions.md`「本輪我自己做的判斷」。

## 任務 1：對話儲存換成資料庫

- **說明**：把對話的儲存從舊位置的 JSON 檔換成資料庫，提供 `spec.md` §1 的全部性質，並讓儲存能通知「有變動」（§2 要用）。**用哪個程式庫、結構長什麼樣、怎麼切類別，由 RD 決定。** 存檔的**時機與次數**本輪不要求改動；若判斷非改不可，**先寫進本 slug 的 `pm-inbox.md`**（那兩件事受另兩份規格保護，改了會變成跨輪待決事項）。
- **對應功能模組**：對話儲存。
- **資料庫程式庫**：Room（使用者指定，`spec-architecture.md` §I）。
- **測試（v2，依 D1 改寫）**：**資料庫層不寫自動化測試**（使用者開的例外，見「明確不做」）。從資料庫層拆出來的規則 —— 讀回不加工（§1.1）、空白對話的處置（§1.2）、一筆解不開只丟那一筆與兩條讀取路徑同一個答案（§1.5）—— **照常用 JUnit 測，而且測試不得碰資料庫**。
  - **可驗證性要求**：上面那幾條規則必須放在一個**不依賴 Android、不依賴資料庫**、能被測試直接驅動的地方。怎麼切由 RD 決定；RD 回報的做法（Room 只交出每一列的原始字串，解析與容錯在純邏輯裡做，`spec-architecture.md` §B.1、§C.1）滿足這一點。
- **驗收標準**：
  1. **讀回來的就是存進去的（§1.1，不碰資料庫）**。一支在標準測試指令下執行、不碰資料庫的測試：一段對話含 `spec.md` §1.1 第一條可判定列出的每一種文字，轉成**存進資料庫的形式**、再經由**「依 id 取」與「取全部」共用的讀取規則**轉回來，每一個欄位、每一則訊息都與原本的**完全相等**（不是「不為空」、不是 `contains`）。同一支測試另轉一則被標成「生成中」的訊息 → 轉回來不是生成中。
     - *獨自抓得到什麼*：讀取時對文字再加工（現行的讀取修復會把兩個字元的 `\n` 變成換行、去掉前後空白）；任一欄位漏轉或轉錯（例如模型、建立時間、訊息順序）。
     - **這一條管不到的**：資料庫那一端有沒有把字串原樣存好、原樣交回。那一半由裝置上的任務 7 驗收 8（冷啟動後內容都在）承接，並列在「明確不做」的 D1 例外裡。
  2. **（v2 依 D1 移除，編號保留不遞補。不要再驗它。）** 原本要求：並發存同一段對話時讀取不會讀不到它的資料庫層測試（§1.4，H2），並由 QA 以突變模式連跑 5 次。
     - **§1.4 的規則本身保留。** 現在的守衛是裝置上的任務 2 驗收 3（每輪都跑），以及 RD 的單一指令存檔（`spec-architecture.md` §B.1）。已知缺口與觸發條件在「明確不做」的 D1 例外那一條。
  3. **一段解不開不連累其他段，兩條讀取路徑同一個答案（§1.5，H3；不碰資料庫）**。一支不碰資料庫的測試，給讀取規則一組「從資料庫取出的原始列」：其中一列是解不開的 X（例如某則訊息的作者是不存在的值、或那一列的訊息內容根本不是合法格式），其餘是正常的 E、F。斷言：
     - 「取全部」的結果**恰為 E、F**，而且在測試時限內結束；
     - 「依 id 取」對 X → 找不到；對 E → 取得 E 且內容相等；對一個從來不存在的 id → 找不到；
     - **對上面每一個 id，「依 id 取」與「取全部再挑出同一個 id」的答案相同。**
     - *獨自抓得到什麼*：一列壞資料讓整份讀取失敗（使用者看到整份歷史不見）；「依 id 取」走了另一套解析而繞過容錯（兩條路答案不同）；把「解不開」當成「稍後再試」而卡住。
     - **這一條管不到的**：「依 id 取」在資料庫那一端查的是不是同一列。由裝置上的任務 7 驗收 6 承接一部分。
  4. **空白對話的處置（§1.2；不碰資料庫）**。一支不碰資料庫的測試，驅動「存一段對話時該寫入還是刪除」的那個判斷：只有開場白的對話 → 判成**刪除那個 id**（不寫入）；只含助理訊息、id 為 X 的對話 → 判成刪除 X；訊息清單為空的對話 → 判成刪除。**正向對照**：有使用者訊息的對話 → 判成寫入。
     - *獨自抓得到什麼*：空白對話被寫進儲存（歷史長出空殼）；「外面來的只含助理訊息的那段」打開再離開後沒有被清掉（`conversation-search` 決策 J 的行為被默默改掉）。**這一條同時是 `docs/specs/conversation-search/spec-tasks.md`／「明確不做」裡「任務 16 的行為不要求自動化測試」那條觸發條件所要求的存取層那一半。**
     - **這一條管不到的**：「判成刪除」之後資料庫真的刪了。由裝置上的任務 7 驗收 4、5 承接。
  5. **（v2 依 D1 移除，編號保留不遞補。）** 原本要求：刪除只刪那一段、同一段存兩次仍是一段的資料庫層測試（§1.3、§1.6）。現在由裝置上的任務 7 驗收 7（刪除）、任務 2 驗收 3（恰好一列）與任務 7 驗收 4、9（對話數不變）承接。
  6. **（v2 依 D1 移除，編號保留不遞補。）** 原本要求：訂閱儲存變動的資料庫層測試。現在由裝置上的任務 2 驗收 3、4 承接（每一種會改變儲存的動作之後，清單都立刻跟著變）。
  7. **除本輪新增之外，專案既有的測試全部通過**（標準測試指令；一支都不得變紅、停用或刪除）。

## 任務 2：歷史清單跟著儲存走

- **說明**：讓抽屜上的歷史清單＝儲存裡的所有對話 − 開著的那段，並隨兩者任一變動更新（`spec.md` §2）。現行「存完之後讀一次全部」的做法要不要留，由 RD 決定，只要 §2 成立。
- **對應功能模組**：歷史清單的組合、聊天狀態。
- **驗收標準**：
  1. **組合本身可被直接驅動（可驗證性要求；不碰資料庫）**。一支不依賴 Android、在標準測試指令下執行的測試，給這個組合一個可控的「儲存裡的全部對話」來源與一個可控的「開著的 id」，斷言：
     - (i) 每一份輸出都等於**最新**的來源扣掉**最新**開著的那段；
     - (ii) 來源變動（新增、改內容、刪除）與開著的 id 變動，**各自**都會讓輸出更新；
     - (iii) **重現這個 bug 的順序**：開著 A（來源裡沒有 A）→ 開著的換成 N → 之後來源才出現 A → 最新輸出含 A、不含 N。
     - **鑑別力**：把組合改成「只在開著的 id 變動時重算、來源變動不重算」，(ii) 與 (iii) 必須變紅；把「扣掉開著的那段」拿掉，(i) 必須變紅。
     - *獨自抓得到什麼*：清單在某一刻讀一次就存起來（晚於那一刻的存檔永遠不會出現）；忘了扣掉開著的那段（`conversation-search` §5.2 的「歷史列表不含目前開著的那段」會被打破）。
  2. **（v2 依 D1 移除，編號保留不遞補。）** 原本要求：把組合接到真的儲存的自動化測試。「組合接錯來源（例如接成一次性讀取）」現在由裝置上的驗收 3、4 承接 —— 接錯時，切換或刪除之後清單不會跟著變。
  3. **在裝置上：串流中切換，被切走的那段立刻在清單上（§2.2，H1）。這一條每一輪都要跑**，不論那一輪有沒有動到儲存 —— 它是「重現案例進測試套件」那條規則的**替代守衛**（使用者開的例外，見「明確不做」的 D1 例外）。照 `spec.md` §2.2 的前置與預期：
     - 四個入口（切換人格、切換模型、開始新的對話、開啟另一段對話）**各做一次**，每一次預期 1–5 全部成立；
     - 零文字變體用「切換人格」做一次，預期 1–3 成立；
     - **這一次算不算數**：切換之後打開 A，那則回覆結尾是中斷標記才算「切換時還在生成」；結尾是完整回覆或其他收束標記 → 那一次不算，重做。零文字變體則看那則空回覆沒有留下、使用者那句還在。
     - 模型與提示由驗的人選（`spec.md` §2.2 給的提示加上 Gemma3 1B 是一組起點，不是要求）；報告寫明用了什麼、每次切換時回覆大約出現幾個字。**攔不到「還在生成」時**記「本環境無法觀察」，並寫明試過的模型、提示與串流大約持續多久 —— 不得只寫這幾個字。
     - **次數的理由**：這個 bug 在新做法下不再是競態，而是「每個入口有沒有接上」—— 每個入口一次就照得出來。**「並發不會讓讀取漏掉」這一條證明不了**；v2 起它沒有自動化測試，靠單一指令存檔從結構上排除，是使用者知情接受的缺口（「明確不做」的 D1 例外）。
  4. **在裝置上：其他會改變儲存的動作，清單也立刻跟著變（§2.3）**。同一次執行裡依序：不在生成時從抽屜開另一段 → 打開抽屜，剛才那段在；刪掉清單上的一段 → 那一列立刻消失，不必關再開；送出一則訊息、等回覆結束、切走 → 打開抽屜，那段在，預覽是完整回覆的開頭。
     - *獨自抓得到什麼*：只有串流中那條路接上了、一般的切換或刪除仍靠舊的重讀（或根本沒更新）。驗收 3 只走串流中那條。

## 任務 3：還沒存下的東西仍然搜得到

- **說明**：`spec.md` §3。本輪改了清單的來源，搜尋不得跟著變成只看儲存。
- **對應功能模組**：聊天狀態、搜尋（不改搜尋本身）。
- **驗收標準**：
  1. **在裝置上：從未存下的新對話搜得到**。在一段有內容的對話裡切換人格，產生只有開場白的新對話 N → 從抽屜進入搜尋，查 N 開場白裡的一個詞 → N 的分組出現，而且排在最前。
     - *獨自抓得到什麼*：搜尋改成讀儲存（N 永遠不會被存下，所以永遠搜不到）。
  2. **在裝置上（盡力）：已送出、還沒收尾的那句搜得到**。在一段新開的對話送出一句含有獨特詞（例如 `harborlight`）的訊息，**回覆還在生成時**進入搜尋、查那個詞 → 那段的分組出現。之後回到聊天，確認那則回覆結尾是中斷標記（進入搜尋不會停止生成時，改以「進入搜尋當下回覆還在增加」的截圖為證）。
     - 攔不到「還在生成」時記「本環境無法觀察」，寫明試過的模型、提示、串流持續多久。**不判 fail**：驗收 1 已經判得出「搜尋改讀儲存」這一型。
     - *獨自抓得到什麼*：搜尋來源是「儲存 ＋ 開著的那段在儲存裡的版本」而不是記憶體裡的即時版本 —— 驗收 1 的 N 整段不在儲存，照不出這一型。

## 任務 4：舊資料：不搬遷、刪掉舊位置

- **說明**：`spec.md` §4。
- **對應功能模組**：舊資料清理、聊天狀態（啟動）。
- **驗收標準**：
  1. **清理的範圍（不經過裝置、不碰資料庫）**。一支不依賴 Android、在標準測試指令下執行的測試，在暫存目錄裡模擬 App 的檔案目錄：舊位置底下有三個 `.json`；舊位置旁邊有一個名稱以 `.task` 結尾的檔、一個以 `.task.part` 結尾的檔、一個名為 `profileInstalled` 的檔、另一個含檔案的子目錄。對它執行清理 → 舊位置不存在；**旁邊每一個檔的位元組都與清理前相同**，子目錄與其中的檔仍在。另外三個案例：舊位置本來就不存在 → 不出錯、旁邊的東西不變；舊位置裡有一個刪不掉的檔（把舊位置設成不可寫）→ **清理不丟出錯誤**、旁邊的東西不變；舊位置恢復可寫之後再清理一次 → 舊位置不存在。
     - **可驗證性要求**：清理必須能對任意一個目錄執行，才寫得出這支測試。
     - *獨自抓得到什麼*：刪錯一層（模型檔被刪，使用者要重新等 GB 級的解壓；偏好被刪，忘記上次停在哪）；刪不掉時讓啟動失敗。
  2. **在裝置上：升級情境（§4.1、§4.2）**。新建置已安裝、至少一個模型已經解壓過。**這一條的前置走「測資與讀取的約定」的第二條路**（新建置做不出舊格式的檔，也做不出指向舊對話的偏好）。結束 App 的行程，把三個**舊格式**的對話檔放進舊位置（格式照舊版程式：commit `a4c7b20` 的 `app/src/main/java/com/example/demo/data/ConversationStore.kt`，可用 `git show a4c7b20:<路徑>` 查），其中一個的 id 寫進「上次停在哪」的偏好，人格與模型也寫進偏好（各選一個非預設值）。冷啟動：
     - (i) 抽屜顯示「還沒有其他對話。」；搜尋那三段裡的詞都找不到；
     - (ii) 聊天畫面是一段只有開場白的新對話，頂端的人格與模型是寫進偏好的那一組；
     - (iii) 舊位置不存在；
     - (iv) 沒有出現「正在把 AI 模型解壓到裝置上」的橫幅，App 檔案目錄裡原有的模型檔仍在（以檔案清單與大小判定）；
     - (v) 送出一則訊息、等回覆結束，再冷啟動一次 → 續接到那段、內容都在、舊位置仍不存在。
     - **做不到「把檔放進舊位置」時**：記「本環境無法觀察」並寫明原因；(iii) 與 (iv) 的範圍由驗收 1 承接，(i)(ii) 仍可用「清空資料後第一次啟動」的畫面判一半，報告要明講只判了一半。
     - *獨自抓得到什麼*：新建置把舊檔讀進來（搬遷或顯示了）、升級後因為「上次停在哪」指到不存在的對話而卡住或閃退、清理在真的裝置目錄上刪錯東西。

## 任務 5：儲存壞掉或寫不進去

- **說明**：`spec.md` §5。§5.1 依 D3 選 (b) 寫定：告知一次、丟掉壞的那份、重新開始。**Room 的預設行為只做到一半**（`spec-architecture.md` §G）。
- **對應功能模組**：儲存故障的呈現、對話儲存、聊天狀態。
- **驗收標準**：
  1. **在裝置上：整份讀不起來（§5.1）**。先用正常操作存好一段對話 P。結束 App 的行程，照「測資與讀取的約定」第二條路把資料庫檔整份覆寫成無法讀取的內容（例如亂碼），冷啟動：
     - 不閃退；聊天畫面出現；沒有出現解壓橫幅；可以送出訊息、收到回覆、按停止；
     - 畫面上出現**一次**「之前的對話紀錄讀不出來，已經清空，從這裡重新開始。」，至少停留 3 秒或直到關掉它；
     - 抽屜是「還沒有其他對話。」、搜尋 P 裡的詞找不到（壞掉的那份不保留）；
     - 「上次停在哪」的偏好內容與冷啟動前相同；
     - 在一段新對話送出訊息、等回覆結束、再冷啟動 → 那段在，**而且提示不再出現**。
     - *獨自抓得到什麼*：只靠 Room 預設的刪檔、沒有提示（使用者看到抽屜突然空掉）；每次啟動都跳提示（沒有真的重新開始）；之後的對話存不下來。
     - **使用途中才發現損毀的那一種**在裝置上造不出可靠的時機，**本條不驗**；規則仍在 `spec.md` §5.1，建議在 `spec-architecture.md` §G.1。
  2. **在裝置上（盡力）：寫不進去（§5.2）**。先存好一段對話 P。用任何能讓儲存寫入失敗的方式（例如把儲存設成唯讀）→ 在另一段對話送出訊息、等回覆結束 → 不閃退；出現「有一段對話沒能存下來。」且至少停留 3 秒；那段內容仍在畫面上、可以再送出；P 仍在抽屜上、內容不變。恢復可寫之後再送出一則並等回覆結束 → 冷啟動後那段在。
     - **P 用正常操作建立**；讓儲存寫不進去的那一步（例如改檔案權限）屬於「測資與讀取的約定」第二條路，在 App 停止時做。
     - **環境做不出「寫入失敗」時**：記「本環境無法觀察」並寫明試過的方式與結果。**這時本條在這一輪完全沒有判到**（v2 起沒有資料庫層的自動化測試承接），報告要明講，不得寫成 pass。
     - *獨自抓得到什麼*：寫入失敗讓 App 閃退（現行程式的行為，見 `spec.md`「這次會踩到的既有事實」第 7 條）；失敗時沒有任何告知；一次失敗的寫入弄丟已存的 P。
  3. **（v2 依 D1 移除，編號保留不遞補。）** 原本要求：資料庫層「寫入失敗不毀掉已存的」自動化測試。**已知缺口**，由驗收 2 的「P 仍在」部分承接，以及單一指令存檔的結構保證；見「明確不做」的 D1 例外。

## 任務 7：回歸驗證（每輪必做）

- **說明**：本輪換掉的是每一條存檔與讀取都會經過的那一層，並改了清單的來源。下面是另兩份規格裡**會因為換儲存而受影響**的行為，**以不綁儲存形式的寫法**在本輪各驗一次。**測資與「儲存的內容」照本檔「測資與讀取的約定」**：App 做得出來的對話用正常操作建立、判讀完才清理；判「儲存的內容」是 App 停止時唯讀資料庫檔。
- **對應功能模組**：所有會存檔、讀歷史的路徑。
- **驗收標準**：
  1. **停止當下就存下（`docs/specs/stop-generation/spec.md` R5「停止當下就必須落盤」）**：回覆生成中按停止，**不做任何其他操作**，立刻結束 App 的行程、冷啟動 → 續接到那段，那則回覆的文字與停止時相同、以中斷標記結尾。
  2. **存下的是被停止的那段（同一份規格 R6「落盤的必須是「被停止的那一段」」）**：生成中從抽屜開另一段既有對話 B → 儲存裡 A 那段的那則回覆以中斷標記結尾；**B 在儲存裡的內容（每一個欄位、每一則訊息）與切換前相同**。
  3. **切走沒有改到內容的對話，儲存裡的它不變（`docs/specs/conversation-search/spec.md` §8.4「可判定（儲存體裡的時間不動）」）**：一段有內容、最後更新時間早於現在至少 1 分鐘的對話 A 開著，不做任何事，從抽屜開另一段 → 儲存裡 A 的內容（含最後更新時間）與切換前相同。
  4. **新開沒說過話的對話不留（同一份規格 §9.1「儲存一段空白對話等於刪檔，不是寫檔」）**：換人格產生只有開場白的對話，分別用開另一段、開始新的對話、換人格、換模型四種方式離開 → 每一次前後，儲存裡的對話數與每一段的內容都相同。**正向對照**：在一段新開的對話送出訊息、等回覆結束再離開 → 儲存裡多了那一段。
  5. **外面來的空白對話打開再離開就清掉（同一節的決策 J 那一項）**：先用**正常操作**建立一段含使用者訊息的對話 Y 並切走；結束行程，從 App 以外寫入只含助理訊息的 X（v2：只有 X 走第二條路）→ 冷啟動 → 點 X、再從抽屜開 Y → 儲存裡沒有 X、冷啟動後抽屜與搜尋都找不到 X；再開一段新的對話 → **儲存裡 Y 仍在、內容不變**。判讀完照約定清理 Y。
  6. **一段讀不起來不連累其他段（同一份規格 §9.2「一個讀不起來的對話檔，不得讓其他對話消失」）**：從 App 以外讓儲存裡一段對話讀不起來，其餘兩段正常 → 冷啟動後抽屜列出那兩段，App 不閃退。
  7. **刪掉就是真的刪掉（同一份規格 §9.4「使用者從歷史清單刪掉一段對話，就是真的刪掉」）**：開著 A，從抽屜刪 B → 儲存裡少一段、沒有 B、A 的內容不變；冷啟動後抽屜與搜尋都找不到 B。
  8. **回覆結束後直接關 App 仍在；冷啟動回到上次那段**：送出一則訊息、等回覆結束、不做任何事、結束行程再冷啟動 → 續接到那段，使用者那句與完整回覆都在。再換人格產生一段沒說過話的對話、結束行程再冷啟動 → 以記住的人格與模型開新的一段。
  9. **搜尋與點命中列不改動儲存（同一份規格 §1.10「搜尋全程不觸發推論、不產生檔案讀寫」與 §6.2–§6.4）**：取一次儲存的內容當基準（**前置擺設都做完之後才取**，被點到的那段要含使用者訊息；**測資的清理排在判讀之後**）→ 進搜尋、打字到有結果、點另一段的命中列開啟它、再進搜尋點回原本那段 → 儲存裡的對話數與每一段的內容都與基準相同。
  10. **聊天流程照常**：送出、串流、停止、刪除、切換人格／模型、冷啟動續接，每一項做得完並出現直接結果（送出後使用者那句與回覆出現；串流時回覆逐步增加直到結束；停止後回覆不再增加；刪除後那一列消失；切換後開了一段新的、頂端換成選的人格或模型；冷啟動後回到上次那段）。任一項做不完、出錯或閃退即 fail。
  11. **除本輪新增之外，專案既有的測試全部通過**（標準測試指令）。
  12. **（v2 依使用者裁決移除，編號保留不遞補。不要再驗它。）** 原本要求：`docs/specs/stop-generation/spec.md` 的任務 2、3、4 在本輪整組重跑。
      - **裁決（2026-09-17）**：那一輪的 S3 觸發條件（程式再被動到）在本輪**確實成立**，使用者知道這一點，**仍決定本輪不重跑**。
      - **現在誰在守**：與儲存有關的那幾件 —— 停止當下就存下、存的是被停止的那段、切換觸發的停止也存下 —— 由本任務驗收 1、2 與任務 2 驗收 3 以不綁儲存的寫法驗。
      - **知情接受的缺口**：`stop-generation` 其餘的裝置端行為（停止不是錯誤、中斷標記逐字、停止後不再變動、零文字、立刻可再說話、兩種自動中斷）這一輪沒有在模擬器上重驗，而本輪動到了它們所在的聊天狀態。
      - **之後什麼時候跑**：`stop-generation` 那份規格下一次被修訂時；或任何一輪改動停止、回覆收尾、中斷標記那一段程式時。屆時照那一份自己的 R3 註記處理時序競爭的歸類。
  - *這一組為什麼不直接指向那兩份規格的條文*：那些條文的可觀察物寫的是 JSON 檔，本輪之後照字面做不出來（`spec-appendix.md`／「跨輪衝突清單」）。這裡驗的是**同一件事的使用者後果**，不是另寫一份規則。

# 明確不做

每條附「什麼時候該回來處理」。

**不搬遷舊對話。** 使用者裁決：這是資料庫的第一版，舊的 JSON 對話全部清空。
- **後果（使用者知情接受）**：**升級之後，使用者原本的對話會全部不見**；而且舊檔在第一次啟動時就被刪掉（`spec.md` §4.2），**之後也無法再救回**。
→ 觸發：使用者表示要保留或匯入舊對話。那必須在**發佈這一版之前**決定 —— 發佈之後舊檔已經刪了。

**資料庫結構的版本升級機制。** 這是第一版，沒有舊結構要升。
→ 觸發：下一次要改儲存的結構時。屆時「升級時不得弄丟既有對話」是那一輪的核心規則，不能沿用本輪「全部清空」的做法。

**同一段對話同時被存入「不同」內容時的先後保證。** 今天唯一實際會發生的並發是相同內容（停止與切換）。理論上，一次回覆收尾的存檔若慢到被下一次回覆的收尾超過，較舊的內容可能最後落地；兩次收尾之間至少隔一整次生成，本輪判斷走不到。
→ 觸發：新增任何「在前一次存檔可能還沒完成時，存下同一段的不同版本」的路徑（例如生成中定時存檔）；或有人回報重開 App 後少了最後一輪對話。

**生成途中每段文字即時存檔。** 生成中 App 被系統殺掉，那一輪的回覆會不見（使用者那句也還沒存）。這是既有行為。
→ 觸發：使用者回報「切出去再回來，剛才的回覆不見了」（與 `stop-generation`「明確不做」的同一條觸發一致）。

**寫不進去的那段，被切走之後不留在清單上。** `spec.md` §5.2 只要求告知。讓它在本次執行中仍留在清單上，需要一份「沒存成的對話」的記憶體清單，本輪不做。
→ 觸發：使用者回報「看到沒存成的提示之後，那段對話就找不到了」。

→ 觸發：任何一輪要移除或改名一個模型或人格。
