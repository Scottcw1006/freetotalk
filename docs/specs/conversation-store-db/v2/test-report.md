# 邊界情況檢查

spec 沒有一節叫「已知衝突與邊界情況」，所以把行為規格 §1–§5 的每一條規則，以及「明確不做」裡碰得到的幾條，當成邊界情況逐一檢查。

- **§1.1 生成中的訊息讀回不是生成中**：單元測試有；`toStored()` 不存 `streaming`。
- **§1.2 以同一個 id 存空白對話要移除既有那筆**：單元測試（判成 Delete）加上裝置（任務 7 驗收 5）。
- **§1.3 刪除不存在的 id**：畫面上做不出來，spec 已知情不驗。靜態上，`DELETE … WHERE id = :id` 對不存在的 id 是 no-op，而且 `delete()` 被 `attempt` 包住，不會丟例外。
- **§1.4 同內容並發存兩次**：B1b、B2c、B3、B4b 每次切換都會存兩次（停止一次、切換一次），DB 裡都恰好一列、內容完整。靜態上，每次存檔只有一個 `@Insert(REPLACE)`。沒有自動化測試，這是 spec 知情接受的缺口。
- **§1.5 一列壞資料**：單元測試加上裝置（K1）。
- **§1.6 同一段存兩次（內容不同）仍是一段**：任務 4 驗收 2 (v) 那段先存開場白加一問一答、之後又被存；B 系列的 A 被存兩次。DB 裡每個 id 都只有一列（主鍵）。
- **§2.1 清單反映最新狀態、不被舊清單蓋掉**：資料面成立。靜態上，清單是 `combine` 加上 `update` 時再用當下的 `conversation.id` 過濾一次。**使用者看得到的層面有前述的捲動問題。**
- **§3.1 三種不在儲存裡的東西**：
  - 只有開場白的對話：H1 成立。
  - 已送出、回覆還沒結束的那句：H2 成立。
  - 生成中已顯示的部分：本輪沒有單獨攔到「生成中的回覆文字本身命中」。H2 命中的是使用者那句；Qwen 那次的回覆命中，無法確認當時是否仍在生成。靜態上，搜尋的資料來源是 `allThreads`（記憶體），生成中的訊息就在 `conversation` 裡。任務 3 沒有要求這一項。
- **§3.2 兩邊都有時以記憶體為準**：靜態上，`allThreads` 是 `listOf(conversation) + history` 再去重，註解也寫明留記憶體那份。沒有在裝置上造出重疊。
- **§4.2 舊位置**：
  - 不存在時不出錯：本輪每次冷啟動都是這種情況，沒有閃退。
  - 刪不掉時：只由單元測試判，裝置上沒有造。
  - 只刪它：單元測試加上 A1 的模型檔比對。
- **§5.1 使用途中才發現**：spec 已知情不驗。靜態上，`all` 流的 catch 與 `attempt` 都會觸發 `reset`，提示也不綁啟動流程。靜態讀到兩個值得注意的地方，本輪沒有實測，不改變判定：
  1. `automaticResetsLeft = 1`：同一個行程裡第二次損毀不會再重來，也不會再提示。
  2. `meansStoreIsUnreadable` 把所有 `IllegalStateException` 都當成「整份讀不起來」，範圍很寬；任何來自 Room 的 ISE（不一定是損毀）都會導致整份資料被刪。
- **§5.1 「結構不認得」**：沒有在裝置上造。靜態上有 `fallbackToDestructiveMigration` 與 `onDestructiveMigration`，會把 `wasReset` 設成 true。
- **§5.2**：見任務 5 驗收 2。唯讀造出的是「開不起來」，App 沒有把它歸到 §5.1，也沒有照 §5.2 保留讀取。
- **明確不做：「寫不進去的那段被切走之後不留在清單上」**：M1 裡確實如此，符合知情留白。
