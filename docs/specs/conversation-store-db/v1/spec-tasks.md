## 任務 1：對話儲存換成資料庫

- **說明**：把對話的儲存從舊位置的 JSON 檔換成資料庫，提供 `spec.md` §1 的全部性質，並讓儲存能通知「有變動」（§2 要用）。**用哪個程式庫、結構長什麼樣、怎麼切類別，由 RD 決定。** 存檔的**時機與次數**本輪不要求改動；若判斷非改不可，**先寫進本 slug 的 `pm-inbox.md`**（那兩件事受另兩份規格保護，改了會變成跨輪待決事項）。
- **對應功能模組**：對話儲存。
- **測試環境**：依 D1。
- **驗收標準**：
  1. **讀回來的就是存進去的（§1.1）**。一支在標準測試指令下執行的測試：一段對話含 `spec.md` §1.1 第一條可判定列出的每一種文字，存入後，**依 id 取**與**取全部再挑出它**兩條路讀回來，每一個欄位、每一則訊息都與存入的**完全相等**（不是「不為空」、不是 `contains`）。同一支測試另存一則被標成「生成中」的訊息 → 讀回來不是生成中。
     - *獨自抓得到什麼*：讀取時對文字再加工（現行的讀取修復會把兩個字元的 `\n` 變成換行、去掉前後空白）；任一欄位漏存或存錯（例如模型、建立時間、訊息順序）。
  2. **重現案例成為永久測試：並發存同一段不會讓讀取讀不到它（§1.4，H2）**。一支測試：先存好非空白對話 C 與 D；接著**至少兩個執行緒反覆存入 C 的相同內容**，同時**至少一個執行緒反覆取全部、並反覆依 C 的 id 取**。斷言**每一次**取全部都恰好含 C、D 各一次，**每一次**依 id 都取得到 C，取到的 C 與存入的完全相等。
     - **鑑別力要求**：把「一次存檔」改成**先刪掉那一筆、再另外寫入，兩步各自生效**時，這支測試用標準測試指令**連續執行 5 次，5 次都必須變紅**；未改動時連續 5 次全綠。
     - **這一半由誰做、驗得到什麼（依使用者 2026-09-16 對這類條文的裁決標明）**：由 **QA 以突變模式**在專案的暫存複本上執行（不動專案原始碼），5 次的結果寫進報告。QA 驗得到的是那 10 次執行的結果；**RD 事先在本機跑過與否，不構成這件事的證據。**
     - *獨自抓得到什麼*：「跑得太短、執行緒太少、斷言太弱」而恰好通過的測試 —— 它在正確與錯誤的實作上都會是綠的。
  3. **一段讀不起來不連累其他段（§1.5，H3）**。一支測試：在儲存裡造出一段讀不起來的對話 X（方式不限，例如某則訊息的作者欄是不存在的值），另外存好正常的 E、F。斷言：取全部**在測試時限內結束**，結果**恰為 E、F**；依 X 的 id 取 → 找不到；依 E 的 id 取 → 取得 E 且內容相等；對一個從來不存在的 id，兩條路都找不到。
     - *獨自抓得到什麼*：一筆壞資料讓整份讀取失敗（使用者看到整份歷史不見）；依 id 直接查詢而繞過容錯（兩條路答案不同）；把「讀不起來」當成「稍後再試」而卡住。
  4. **空白對話不留（§1.2）**。一支測試：存一段只有開場白的對話 → 取全部沒有它；儲存裡先造一段只含助理訊息、id 為 X 的對話，再以 X 存一段沒有使用者訊息的版本 → 取全部沒有 X。**正向對照**：存一段有使用者訊息的對話 → 取全部有它。
     - *獨自抓得到什麼*：空白對話被寫進儲存（歷史長出空殼）；或「外面來的只含助理訊息的那段」打開再離開後沒有被清掉（`conversation-search` 決策 J 的行為被默默改掉）。**這一條同時是 `docs/specs/conversation-search/spec-tasks.md`／「明確不做」裡「任務 16 的行為不要求自動化測試」那條的觸發條件所要求的存取層那一半。**
  5. **刪除只刪那一段、儲存不多不少（§1.3、§1.6，H4）**。一支測試：存 A、B，刪 B → 取全部恰為 A、A 與刪除前完全相等、依 B 的 id 找不到；刪一個不存在的 id → 不出錯、A 不變；A 以不同內容再存一次 → 取全部仍恰一段 A，內容是第二次的。
     - *獨自抓得到什麼*：刪錯範圍（整份清空也會讓「B 不在」成立 —— 所以要斷言 A 不變）；同一段存兩次變成兩段。
  6. **變動通知（§2.1 的儲存那一半）**。一支測試訂閱儲存的變動：訂閱一開始就拿到現有的全部；之後依序做「存一段新的」「以不同內容改存一段既有的」「刪一段」，**每一步之後**，訂閱者在 5 秒內拿到的最新一份清單與當下的「取全部」相同。
     - *獨自抓得到什麼*：某一種寫入不發通知（例如刪除不發）—— 清單會停在舊的樣子，就是那個 bug 的第二個成因換個形狀回來。驗收 1–5 都只看一次性的讀取，看不到通知。
  7. **除本輪新增之外，專案既有的測試全部通過**（標準測試指令；一支都不得變紅、停用或刪除）。

## 任務 2：歷史清單跟著儲存走

- **說明**：讓抽屜上的歷史清單＝儲存裡的所有對話 − 開著的那段，並隨兩者任一變動更新（`spec.md` §2）。現行「存完之後讀一次全部」的做法要不要留，由 RD 決定，只要 §2 成立。
- **對應功能模組**：歷史清單的組合、聊天狀態。
- **驗收標準**：
  1. **組合本身可被直接驅動（可驗證性要求；不需要資料庫，不等 D1）**。一支不依賴 Android、在標準測試指令下執行的測試，給這個組合一個可控的「儲存裡的全部對話」來源與一個可控的「開著的 id」，斷言：
     - (i) 每一份輸出都等於**最新**的來源扣掉**最新**開著的那段；
     - (ii) 來源變動（新增、改內容、刪除）與開著的 id 變動，**各自**都會讓輸出更新；
     - (iii) **重現這個 bug 的順序**：開著 A（來源裡沒有 A）→ 開著的換成 N → 之後來源才出現 A → 最新輸出含 A、不含 N。
     - **鑑別力**：把組合改成「只在開著的 id 變動時重算、來源變動不重算」，(ii) 與 (iii) 必須變紅；把「扣掉開著的那段」拿掉，(i) 必須變紅。
     - *獨自抓得到什麼*：清單在某一刻讀一次就存起來（晚於那一刻的存檔永遠不會出現）；忘了扣掉開著的那段（`conversation-search` §5.2 的「歷史列表不含目前開著的那段」會被打破）。
  2. **接上真的儲存（等 D1）**。一支測試把驗收 1 的組合接到任務 1 的儲存：開著 N、在儲存裡存入 A → 5 秒內輸出含 A；刪掉 A → 5 秒內輸出不含 A。
     - *獨自抓得到什麼*：組合接的來源不是儲存的變動通知（例如接成一次性讀取）。驗收 1 用的是假來源，任務 1 驗收 6 沒有組合，兩條都看不到接錯。
  3. **在裝置上：串流中切換，被切走的那段立刻在清單上（§2.2，H1）**。照 `spec.md` §2.2 的前置與預期：
     - 四個入口（切換人格、切換模型、開始新的對話、開啟另一段對話）**各做一次**，每一次預期 1–5 全部成立；
     - 零文字變體用「切換人格」做一次，預期 1–3 成立；
     - **這一次算不算數**：切換之後打開 A，那則回覆結尾是中斷標記才算「切換時還在生成」；結尾是完整回覆或其他收束標記 → 那一次不算，重做。零文字變體則看那則空回覆沒有留下、使用者那句還在。
     - 模型與提示由驗的人選（`spec.md` §2.2 給的提示加上 Gemma3 1B 是一組起點，不是要求）；報告寫明用了什麼、每次切換時回覆大約出現幾個字。**攔不到「還在生成」時**記「本環境無法觀察」，並寫明試過的模型、提示與串流大約持續多久 —— 不得只寫這幾個字。
     - **次數的理由**：這個 bug 在新做法下不再是競態，而是「每個入口有沒有接上」—— 每個入口一次就照得出來。**「並發不會讓讀取漏掉」由任務 1 驗收 2 證明，不由這一條證明。**
  4. **在裝置上：其他會改變儲存的動作，清單也立刻跟著變（§2.3）**。同一次執行裡依序：不在生成時從抽屜開另一段 → 打開抽屜，剛才那段在；刪掉清單上的一段 → 那一列立刻消失，不必關再開；送出一則訊息、等回覆結束、切走 → 打開抽屜，那段在，預覽是完整回覆的開頭。
     - *獨自抓得到什麼*：只有串流中那條路接上了、一般的切換或刪除仍靠舊的重讀（或根本沒更新）。驗收 3 只走串流中那條。

## 任務 3：還沒存下的東西仍然搜得到

- **說明**：`spec.md` §3。本輪改了清單的來源，搜尋不得跟著變成只看儲存。
- **對應功能模組**：聊天狀態、搜尋（不改搜尋本身）。
- **驗收標準**：
  1. **在裝置上：從未存下的新對話搜得到**。在一段有內容的對話裡切換人格，產生只有開場白的新對話 N → 從抽屜進入搜尋，查 N 開場白裡的一個詞 → N 的分組出現，而且排在最前。
     - *獨自抓得到什麼*：搜尋改成讀儲存（N 永遠不會被存下，所以永遠搜不到）。
  2. **在裝置上（盡力）：已送出、還沒收尾的那句搜得到**。在一段新開的對話送出一句含有獨特詞（例如 `harborlight`）的訊息，**回覆還在生成時**進入搜尋、查那個詞 → 那段的分組出現。之後回到聊天，確認那則回覆結尾是中斷標記（進入搜尋不會停止生成時，改以「進入搜尋當下回覆還在增加」的截圖為證）。
     - 攔不到「還在生成」時記「本環境無法觀察」，寫明試過的模型、提示、串流持續多久。**不判 fail**：驗收 1 已經判得出「搜尋改讀儲存」這一型。
     - *獨自抓得到什麼*：搜尋來源是「儲存 ＋ 開著的那段在儲存裡的版本」而不是記憶體裡的即時版本 —— 驗收 1 的 N 整段不在儲存，照不出這一型。

## 任務 4：舊資料：不搬遷、刪掉舊位置

- **說明**：`spec.md` §4。
- **對應功能模組**：舊資料清理、聊天狀態（啟動）。
- **驗收標準**：
  1. **清理的範圍（不經過裝置，不等 D1）**。一支不依賴 Android、在標準測試指令下執行的測試，在暫存目錄裡模擬 App 的檔案目錄：舊位置底下有三個 `.json`；舊位置旁邊有一個名稱以 `.task` 結尾的檔、一個以 `.task.part` 結尾的檔、一個名為 `profileInstalled` 的檔、另一個含檔案的子目錄。對它執行清理 → 舊位置不存在；**旁邊每一個檔的位元組都與清理前相同**，子目錄與其中的檔仍在。另外三個案例：舊位置本來就不存在 → 不出錯、旁邊的東西不變；舊位置裡有一個刪不掉的檔（把舊位置設成不可寫）→ **清理不丟出錯誤**、旁邊的東西不變；舊位置恢復可寫之後再清理一次 → 舊位置不存在。
     - **可驗證性要求**：清理必須能對任意一個目錄執行，才寫得出這支測試。
     - *獨自抓得到什麼*：刪錯一層（模型檔被刪，使用者要重新等 GB 級的解壓；偏好被刪，忘記上次停在哪）；刪不掉時讓啟動失敗。
  2. **在裝置上：升級情境（§4.1、§4.2）**。新建置已安裝、至少一個模型已經解壓過。結束 App 的行程，把三個**舊格式**的對話檔放進舊位置（格式照舊版程式：commit `a4c7b20` 的 `app/src/main/java/com/example/demo/data/ConversationStore.kt`，可用 `git show a4c7b20:<路徑>` 查），其中一個的 id 寫進「上次停在哪」的偏好，人格與模型也寫進偏好（各選一個非預設值）。冷啟動：
     - (i) 抽屜顯示「還沒有其他對話。」；搜尋那三段裡的詞都找不到；
     - (ii) 聊天畫面是一段只有開場白的新對話，頂端的人格與模型是寫進偏好的那一組；
     - (iii) 舊位置不存在；
     - (iv) 沒有出現「正在把 AI 模型解壓到裝置上」的橫幅，App 檔案目錄裡原有的模型檔仍在（以檔案清單與大小判定）；
     - (v) 送出一則訊息、等回覆結束，再冷啟動一次 → 續接到那段、內容都在、舊位置仍不存在。
     - **做不到「把檔放進舊位置」時**：記「本環境無法觀察」並寫明原因；(iii) 與 (iv) 的範圍由驗收 1 承接，(i)(ii) 仍可用「清空資料後第一次啟動」的畫面判一半，報告要明講只判了一半。
     - *獨自抓得到什麼*：新建置把舊檔讀進來（搬遷或顯示了）、升級後因為「上次停在哪」指到不存在的對話而卡住或閃退、清理在真的裝置目錄上刪錯東西。

## 任務 5：儲存壞掉或寫不進去

- **說明**：`spec.md` §5。**§5.1 的處置等 D3**；§5.2 現在就可以做。
- **對應功能模組**：儲存故障的呈現、對話儲存、聊天狀態。
- **驗收標準**：
  1. **在裝置上：整份讀不起來（§5.1，等 D2；後半等 D3）**。結束 App 的行程，照任務 6 的方式把儲存換成無法讀取的內容（例如整份覆寫成亂碼），冷啟動：
     - 前半（任何 D3 選項都成立）：不閃退；聊天畫面出現；沒有出現解壓橫幅；可以送出訊息、收到回覆、按停止；畫面上出現告知對話紀錄讀不出來的文字；「上次停在哪」的偏好內容與冷啟動前相同。
     - 後半：D3 拍板時寫定（提示的確切字串、原本那份要不要保留、之後的對話存不存得下）。**拍板前不判後半。**
  2. **在裝置上（盡力，等 D2）：寫不進去（§5.2）**。先存好一段對話 P。用任何能讓儲存寫入失敗的方式（例如把儲存設成唯讀）→ 在另一段對話送出訊息、等回覆結束 → 不閃退；出現「有一段對話沒能存下來。」且至少停留 3 秒；那段內容仍在畫面上、可以再送出；P 仍在抽屜上、內容不變。恢復可寫之後再送出一則並等回覆結束 → 冷啟動後那段在。
     - **環境做不出「寫入失敗」時**：記「本環境無法觀察」並寫明試過的方式與結果；存取層那一半由驗收 3 承接，**畫面那一半這一輪沒有判到**，報告要明講，不得寫成 pass。
     - *獨自抓得到什麼*：寫入失敗讓 App 閃退（現行程式的行為，見 `spec.md`「這次會踩到的既有事實」第 7 條）；失敗時沒有任何告知。
  3. **不經過裝置：寫入失敗不毀掉已存的（等 D1）**。一支測試：存好 A；讓儲存的下一次寫入失敗（方式不限）→ 存 B 的呼叫端**得知這次沒存成**；A 仍讀得回來且完全相等；恢復之後存 B → 取全部為 A、B。
     - *獨自抓得到什麼*：一次失敗的寫入把儲存弄成讀不起來、或弄丟已存的對話；失敗被默默吞掉（呼叫端無從告知使用者）。

## 任務 6：驗收環境看得到儲存（等 D2）

- **說明**：本輪之後，另兩份規格與本規格的一批裝置端條文，都需要**從 App 以外讀出儲存的內容、寫入自訂內容的對話、以及把儲存弄壞**。這個任務交付的是讓 QA 做得到這三件事所需的東西；**形式等 D2**（D2 選 (a) 時，交付物是 `plan/architecture.html` 儲存那一節裡的位置與結構說明）。
- **對應功能模組**：文件（依 D2 可能含程式）。
- **驗收標準**（由 QA 照交付物實際做一次）：
  1. **讀得出來**：照交付物，在不改專案原始碼的前提下，從 App 以外列出儲存裡每一段對話的每一個欄位與每一則訊息；列出的結果與 App 畫面上看得到的一致（至少兩段對話、其中一段含 emoji 與換行）。
  2. **寫得進去**：照交付物，寫入一段只含助理訊息的對話 X → 冷啟動後 X 出現在抽屜上，標題是「還沒說話」；寫入一段含使用者訊息的對話 Y → 冷啟動後 Y 的標題是 Y 的第一句。
  3. **弄得壞**：照交付物，讓儲存裡**一段**對話讀不起來（其餘照常），以及讓**整份**儲存讀不起來。
  - 三件事任一做不到即 **fail**，並寫明卡在哪一步。**這一條驗的是交付物夠不夠用，不是環境能力** —— 若卡住的原因確實是環境（例如主機上沒有需要的工具），寫明原因，由 PM 判斷交付物要不要補。

## 任務 7：回歸驗證（每輪必做）

- **說明**：本輪換掉的是每一條存檔與讀取都會經過的那一層，並改了清單的來源。下面是另兩份規格裡**會因為換儲存而受影響**的行為，**以不綁儲存形式的寫法**在本輪各驗一次。判「儲存的內容」照任務 6 的方式（等 D2）。
- **對應功能模組**：所有會存檔、讀歷史的路徑。
- **驗收標準**：
  1. **停止當下就存下（`docs/specs/stop-generation/spec.md` R5「停止當下就必須落盤」）**：回覆生成中按停止，**不做任何其他操作**，立刻結束 App 的行程、冷啟動 → 續接到那段，那則回覆的文字與停止時相同、以中斷標記結尾。
  2. **存下的是被停止的那段（同一份規格 R6「落盤的必須是「被停止的那一段」」）**：生成中從抽屜開另一段既有對話 B → 儲存裡 A 那段的那則回覆以中斷標記結尾；**B 在儲存裡的內容（每一個欄位、每一則訊息）與切換前相同**。
  3. **切走沒有改到內容的對話，儲存裡的它不變（`docs/specs/conversation-search/spec.md` §8.4「可判定（儲存體裡的時間不動）」）**：一段有內容、最後更新時間早於現在至少 1 分鐘的對話 A 開著，不做任何事，從抽屜開另一段 → 儲存裡 A 的內容（含最後更新時間）與切換前相同。
  4. **新開沒說過話的對話不留（同一份規格 §9.1「儲存一段空白對話等於刪檔，不是寫檔」）**：換人格產生只有開場白的對話，分別用開另一段、開始新的對話、換人格、換模型四種方式離開 → 每一次前後，儲存裡的對話數與每一段的內容都相同。**正向對照**：在一段新開的對話送出訊息、等回覆結束再離開 → 儲存裡多了那一段。
  5. **外面來的空白對話打開再離開就清掉（同一節的決策 J 那一項）**：從 App 以外寫入只含助理訊息的 X 與含使用者訊息的 Y（Y 的第一句與 X 不同）→ 冷啟動 → 點 X、再從抽屜開 Y → 儲存裡沒有 X、冷啟動後抽屜與搜尋都找不到 X；再從抽屜開另一段 → **儲存裡 Y 仍在、內容不變**。
  6. **一段讀不起來不連累其他段（同一份規格 §9.2「一個讀不起來的對話檔，不得讓其他對話消失」）**：從 App 以外讓儲存裡一段對話讀不起來，其餘兩段正常 → 冷啟動後抽屜列出那兩段，App 不閃退。
  7. **刪掉就是真的刪掉（同一份規格 §9.4「使用者從歷史清單刪掉一段對話，就是真的刪掉」）**：開著 A，從抽屜刪 B → 儲存裡少一段、沒有 B、A 的內容不變；冷啟動後抽屜與搜尋都找不到 B。
  8. **回覆結束後直接關 App 仍在；冷啟動回到上次那段**：送出一則訊息、等回覆結束、不做任何事、結束行程再冷啟動 → 續接到那段，使用者那句與完整回覆都在。再換人格產生一段沒說過話的對話、結束行程再冷啟動 → 以記住的人格與模型開新的一段。
  9. **搜尋與點命中列不改動儲存（同一份規格 §1.10「搜尋全程不觸發推論、不產生檔案讀寫」與 §6.2–§6.4）**：取一次儲存的內容當基準（**前置擺設都做完之後才取**，被點到的那段要含使用者訊息）→ 進搜尋、打字到有結果、點另一段的命中列開啟它、再進搜尋點回原本那段 → 儲存裡的對話數與每一段的內容都與基準相同。
  10. **聊天流程照常**：送出、串流、停止、刪除、切換人格／模型、冷啟動續接，每一項做得完並出現直接結果（送出後使用者那句與回覆出現；串流時回覆逐步增加直到結束；停止後回覆不再增加；刪除後那一列消失；切換後開了一段新的、頂端換成選的人格或模型；冷啟動後回到上次那段）。任一項做不完、出錯或閃退即 fail。
  11. **除本輪新增之外，專案既有的測試全部通過**（標準測試指令）。
  12. **（依 D4）`docs/specs/stop-generation/spec.md` 任務 2「使用者停止不再走錯誤那條路，且停止後狀態收斂」、任務 3、任務 4「回歸驗證」在本輪整組重跑。** 那一輪的使用者裁決（S3）把重驗的觸發條件定成「程式再被動到」，本輪會動到停止與切換所在的聊天狀態。**D4 拍板前不判。** 那幾條裡以「檔案數」「檔案位元組」為可觀察物的部分，照 D4 的裁決處理。
  - *這一組為什麼不直接指向那兩份規格的條文*：那些條文的可觀察物寫的是 JSON 檔，本輪之後照字面做不出來（`spec-appendix.md`／「跨輪衝突清單」）。這裡驗的是**同一件事的使用者後果**，不是另寫一份規則。

# 明確不做

每條附「什麼時候該回來處理」。

**不搬遷舊對話。** 使用者裁決：這是資料庫的第一版，舊的 JSON 對話全部清空。
- **後果（使用者知情接受）**：**升級之後，使用者原本的對話會全部不見**；而且舊檔在第一次啟動時就被刪掉（`spec.md` §4.2），**之後也無法再救回**。
→ 觸發：使用者表示要保留或匯入舊對話。那必須在**發佈這一版之前**決定 —— 發佈之後舊檔已經刪了。

**資料庫結構的版本升級機制。** 這是第一版，沒有舊結構要升。
→ 觸發：下一次要改儲存的結構時。屆時「升級時不得弄丟既有對話」是那一輪的核心規則，不能沿用本輪「全部清空」的做法。

**同一段對話同時被存入「不同」內容時的先後保證。** 今天唯一實際會發生的並發是相同內容（停止與切換）。理論上，一次回覆收尾的存檔若慢到被下一次回覆的收尾超過，較舊的內容可能最後落地；兩次收尾之間至少隔一整次生成，本輪判斷走不到。
→ 觸發：新增任何「在前一次存檔可能還沒完成時，存下同一段的不同版本」的路徑（例如生成中定時存檔）；或有人回報重開 App 後少了最後一輪對話。

**生成途中每段文字即時存檔。** 生成中 App 被系統殺掉，那一輪的回覆會不見（使用者那句也還沒存）。這是既有行為。
→ 觸發：使用者回報「切出去再回來，剛才的回覆不見了」（與 `stop-generation`「明確不做」的同一條觸發一致）。

**寫不進去的那段，被切走之後不留在清單上。** `spec.md` §5.2 只要求告知。讓它在本次執行中仍留在清單上，需要一份「沒存成的對話」的記憶體清單，本輪不做。
→ 觸發：使用者回報「看到沒存成的提示之後，那段對話就找不到了」。

**某個模型或人格從 App 移除之後，舊對話上的名稱怎麼顯示。** 現行讀取遇到不認得的模型會釘成 Qwen、不認得的人格用預設值；這一輪不定義儲存裡出現不認得的名稱時該怎樣。
→ 觸發：任何一輪要移除或改名一個模型或人格。

**刪除之後的實體殘留。** 資料庫刪掉一段之後，那段的位元組可能在檔案的空閒區留一陣子，直到被覆寫；本輪只保證 App 讀不到它（`spec.md` §1.3）。
→ 觸發：出現「刪除必須不可還原」的隱私需求，或有人回報刪掉的內容還能從手機裡撈出來。

**匯出、備份、跨裝置同步、加密。** 全部不在範圍內。
→ 觸發：使用者提出。

**改寫 `conversation-search` 與 `stop-generation` 的條文、刪除 `history-missing-after-switch` 目錄。** 本輪不得動那些檔案；建議與清單在本輪的回報與 `spec-appendix.md`。
