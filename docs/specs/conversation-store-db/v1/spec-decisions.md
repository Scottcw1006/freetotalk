## D1 存取層的自動化測試跑在哪裡

### 為什麼需要你決定

bug 的規則要求重現案例成為永久測試，而那個 bug 的根因（並發存檔時讀不到）在存取層。**我實際跑過（不是讀設定推論）**：Android 內建的 SQLite 介面在 JVM 測試裡是空殼，跟上次的 JSON 程式庫一樣一碰就失敗；**但有兩條路跑得起來，兩條都要引進專案現在沒有的測試相依**（現在只有 JUnit）。完整紀錄在 `spec-appendix.md`／「查證：資料庫能不能在 JVM 單元測試裡跑」。

### 選項

| | 做法 | 實測結果 | 代價 | 碰到什麼 |
|---|---|---|---|---|
| **(a) JVM ＋ 測試專用的主機端 SQLite** | 測試時用 AndroidX 的 SQLite 驅動加上給電腦用的原生程式庫 | **跑得起來**（這台 Mac、JDK 25）；並發探針 75 萬次讀取 0 次讀不到；若用 Room，變動通知在測試裡也收得到 | 多幾 MB 的測試相依；**若 RD 選 Room**，測試端需要兩個替身，依賴 Room 2.8.5 的內部行為，升版可能要跟著調；若正式程式用 Android 內建的 SQLite，測試跑的與手機上的不是同一份實作 | `conversation-search`「明確不做」預言過「裝置端測試是這一層唯一合理的自動化形式」—— 這個選項推翻那句預言；`stop-generation` 那一輪「不為了測試把儲存改成可注入」的範圍線形狀相同（那是那一輪的邊界，不是永久規則） |
| **(b) JVM ＋ Robolectric** | 在測試裡模擬一個 Android 環境 | **跑得起來，但要先加兩個 JVM 參數**（這個專案用的 JDK 25 預設不讓它進去）；第一次執行下載約 208 MB、花 31 秒，之後約 3 秒 | 一整套新框架；JDK 或 Android 版本升級時可能再壞（專案 compileSdk 37，它最高只到 36，要釘版本） | 同 (a) |
| **(c) 裝置端測試** | 測試跑在模擬器上 | **沒有實測**（本輪不接裝置） | QA 每輪的標準流程多一個要接裝置的指令，要改 QA 的角色定義；只有記得跑那個指令時才真的在守 | 與 `conversation-search` 的預言一致 |
| **(d) 不寫存取層的自動化測試** | 只靠裝置上的驗收 | — | 違反「重現案例進測試套件」；並發這種事在裝置上點幾次證明不了它不存在 | 無 |

### 我的傾向（有把握的程度：中）

**(a)**。理由只有一個：**QA 每輪都會跑的那個指令，才是真的在守的測試**，而 (a) 不改那個指令、成本最小。(b) 的優點是測試跑的就是 Android 自己的 SQLite，但它的脆弱度（JDK 參數、SDK 版本）在這次實測就撞到一次。我不建議 (d)。

### 拍板之後

`spec-tasks.md` 的「標準測試指令」照裁決確定（選 (c) 時補寫那個指令）；本項移進附錄。選 (c) 還要改 QA 的角色定義，那不在任何規格裡。

## D2 驗收時怎麼在 App 以外讀寫對話儲存

### 為什麼需要你決定

有一大批裝置端驗收（本規格的，加上 `conversation-search`、`stop-generation` 的）要做三件事：**讀出儲存裡每一段對話的內容**（比對操作前後有沒有被改）、**寫進一段 App 自己寫不出來的對話**（例如只含助理訊息的）、**把儲存弄壞**。以前 QA 直接推拉 JSON 檔，工具也是照 JSON 寫的。換成資料庫之後要換一種做法，而**其中一種會在產品程式碼裡多一段只為測試存在的東西**，那是這個專案現在沒有的模式。

### 選項

| | 做法 | 得到 | 代價 |
|---|---|---|---|
| **(a) QA 直接讀寫資料庫檔** | App 停止時把資料庫檔拉出來、用電腦上的工具讀寫、再推回去。RD 在 `plan/architecture.html` 寫明位置與結構 | 產品程式碼不為測試多任何東西；造得出任何形狀的資料（包括 App 自己會拒絕的） | QA 的工具要重寫；**RD 每次改結構，QA 的腳本就要跟著改**；推拉時要處理資料庫的日誌檔這類陷阱 |
| **(b) debug 建置專用的匯入／匯出入口** | 只有 debug 建置有：例如把某個目錄裡的 JSON 匯入、或把全部對話匯出成 JSON | QA 沿用現有的 JSON 工具 | 產品程式碼裡多一段測試專用的路徑，**要保證永遠不進正式版**；匯入若走 App 自己的存檔邏輯，**造不出只含助理訊息的對話**（會被當成空白對話丟掉），還得另開後門；它長得很像「搬遷」，而搬遷是這一輪明確不做的 |
| **(c) 用裝置端測試程式當造資料的工具** | 透過測試執行器在模擬器上讀寫 | 產品程式碼不動 | 同 D1 的 (c)：多一套要接裝置的流程 |

### 我的傾向（有把握的程度：中）

**(a)**。它唯一的長期成本是「結構一改、QA 腳本要跟著改」，而結構變動本來就是要寫規格的大事（`spec-tasks.md`「明確不做」第二條）。(b) 會把一個「只為了測試」的東西放進產品，而且造不出最需要造的那種資料。

### 拍板之後

任務 6 的交付物形式確定；任務 8 驗收 9 跟著確定；QA 依裁決更新 `docs/qa-environment.md` 與 `docs/qa-tools/`（那歸 QA）。

## D3 儲存整份讀不起來時，使用者看到什麼

### 為什麼需要你決定

你要求把這件事寫清楚。**不論怎麼選都成立的部分我已經寫進規格**（`spec.md` §5.1：不閃退、仍能聊天、模型不重新解壓、畫面上有告知）。剩下的是一個產品取捨：**原本那份壞掉的資料怎麼辦**。另外要知道：**Android 內建的開法遇到損毀時，預設會直接把整個資料庫檔刪掉**，換別的做法則不一定 —— 所以不寫清楚的話，行為會隨 RD 選的程式庫而變。

### 選項

| | 使用者看到什麼 | 之後的對話 | 原本那份 | 代價 |
|---|---|---|---|---|
| **(a) 默默重來** | 歷史是空的，**沒有任何說明** | 照常存 | 丟掉 | 使用者會以為 App 自己把對話弄丟了，而且不知道為什麼 |
| **(b) 告知後重來** | 一次提示：「之前的對話紀錄讀不出來，已經清空，從這裡重新開始。」歷史是空的 | 照常存 | 丟掉 | 壞掉的資料沒有任何救回的機會 |
| **(c) 保留壞掉的那份，這次不存** | 提示：「對話紀錄讀不出來，這次的對話不會被保存。」歷史是空的 | **這次打開 App 期間的對話全部不存**，關掉就沒了；下次啟動再試一次 | 原封不動 | 只要那份一直壞著，**之後每一次的對話都存不下來**；而手機上沒有任何工具能修它 |

### 我的傾向（有把握的程度：中高）

**(b)**。在手機上，一份壞掉的資料庫沒有使用者能用的修復方式，(c) 保住的是一個幾乎用不到的可能性，換來的是之後每一段對話都存不下來；(a) 與 (b) 的差別只有那句提示，而那句提示決定使用者會不會以為 App 有 bug。

### 拍板之後

`spec.md` §5.1 補上提示的確切字串與處置；任務 5 驗收 1 的後半寫定；`docs/product/features.md` 補保存-08（任務 9 驗收 4）。本項移進附錄。

## D4 另兩份規格裡以「JSON 檔」為可觀察物的條文，什麼時候、由誰改寫

### 為什麼需要你決定

這是**跨輪衝突**。換資料庫的方向是你定的，另兩份規格要守的**行為**在新儲存上都仍然成立；但它們有一批條文的**可觀察物**寫的是 JSON 檔（「對話目錄的檔案數多 1」「檔案位元組完全相同」「把一個檔放進對話目錄」），本輪之後照字面做不出來，**正確的實作會被判 fail 或「無法觀察」**。清單與建議改法在 `spec-appendix.md`／「跨輪衝突清單」。**我這一輪不得動那兩份檔案**，所以要由你決定怎麼同步。

另外一件相連的事：`stop-generation` 的裁決 S3 把裝置端重驗的觸發條件定成「**程式再被動到**」，而本輪會動到停止與切換所在的聊天狀態 —— **條件成立了**。

### 選項

| | 做法 | 代價 |
|---|---|---|
| **(a) 本輪 QA 驗收之前，先把那兩份的相關條文改成不綁儲存形式** | 由那兩輪的 PM、或授權本規格的 PM 照清單改；只改可觀察物的寫法，不改任何規則 | 多一步、要排在 QA 之前；那兩份各出一個新版號 |
| **(b) 那兩份暫不改，本輪 QA 以本規格任務 7 的對應條文代替判定** | 那兩份記「等改寫」 | 規格之間有一段時間互相矛盾；**由一份規格替另一份決定怎麼判**，正是跨輪規則要避免的 |
| **(c) 不改** | — | 那些條文在正確的實作上判 fail，一直到有人改 |

**另一個子題**：`stop-generation` 的任務 2、3、4 要不要在本輪整組重跑（S3 的觸發條件成立）。

### 我的傾向

**(a)，而且重跑。** 改寫的內容是機械的（清單已列好），而且只有 (a) 讓 QA 驗本輪時讀到的規格是一致的。重跑時要記得 `stop-generation` R3 那段註記：那個時序競爭在模擬器上是第一次被驗。

### 拍板之後

任務 7 驗收 12 寫定；本項移進附錄。若選 (a)，需要你指定誰去改那兩份。

## 本輪我自己做的判斷（不擋工，你可以推翻）

1. **舊的 JSON 檔在啟動時刪掉，而不是留著不管**（你交給我判斷）。
   - **使用者會怎樣**：升級後，舊對話在畫面上本來就看不到；刪掉之後手機上也不再有。
   - **為什麼刪**：(i) **留著的話，手機上會有一批使用者看不到、也刪不掉的私人對話**（只能清除整個 App 的資料），這與功能清單保存-05「刪掉就是真的刪掉，手機上不會再留著」的精神相反；(ii) 沒有任何程式會再讀它們，留著只會讓之後每一輪都要考慮「這批東西還在不在、要不要管」；(iii) 空間不是理由（幾 KB 級）。
   - **反方向的代價，老實講**：刪掉是**不可逆的**。留著的唯一好處是：如果你之後改變主意想搬遷，資料還在。**若你想保留這個可能，要在這一版發佈之前告訴我** —— 改成「留著不管」只是拿掉一條規則（`spec.md` §4.2）。
   - **我特別寫死的一件事**：清理**只刪舊位置那一個子目錄**，因為模型檔就在它的上一層，刪錯一層使用者要重新等 GB 級的解壓。
2. **讀回來的文字必須與存進去的逐字相同，讀取時不再做「模型輸出修復」**（`spec.md` §1.1）。那個修復是為舊檔存在的，而舊檔不再被讀；留著它，使用者打的 `C:\new` 重開後會變成兩行（違反功能清單聊天-14）。這會改變一個既有行為（變成符合功能清單的描述），所以列在這裡。
3. **一次存檔寫不進去時，不得閃退、要出現「有一段對話沒能存下來。」**（`spec.md` §5.2）。我判斷這裡沒有第二種合理答案，所以沒有升級；寫不進去的那段在切走之後不留在清單上，列進「明確不做」。**現行程式在這種情況下會閃退**（讀程式碼推出來的，沒有在裝置上做過）。
4. **那個 bug 在裝置上的重現，每個切換入口只做一次**（原本的 bug 規格是每個入口三次）。新做法下它不再是機率性的競態，而是「每個入口有沒有接上」；「並發不會讓讀取漏掉」改由自動化測試證明。
5. **存檔的時機與次數本輪不要求改**；RD 若要改，先寫收件匣（那會變成跨輪待決事項）。與 `stop-generation`、`conversation-search` 保護存檔時機的範圍線一致。
6. **`docs/product/features.md` 的人格-04、模型-04、保存-04 改指本規格 §2.2**，不再指 `history-missing-after-switch`，為那個目錄日後被收掉做準備；另新增保存-07（升級不搬遷）。保存-08（儲存讀不起來）等 D3。
7. **JVM 查證時我連了網、跑了建置**：這是你交辦的查證，全部在暫存目錄的複本裡做，專案原始碼與工作區沒有被動到。
