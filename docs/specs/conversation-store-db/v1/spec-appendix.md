## 查證：資料庫能不能在 JVM 單元測試裡跑

**結論：跑得起來，但每一條走得通的路都要引進專案現在沒有的測試相依**（現在只有 JUnit）。Android 內建的 SQLite 介面在 JVM 測試裡是空殼，與 2026-09-14 RD 實測的 JSON 程式庫同一型。選哪條路是 D1。

### 怎麼做的（2026-09-16，PM 執行，使用者交辦）

- **專案原始碼一個字都沒有動**：`git clone` 專案（HEAD `a4c7b20`）到本 session 的暫存目錄，在複本上開分支做實驗，複製 `local.properties` 過去。專案工作區在實驗前後都只有本規格的新目錄是未追蹤的。
- 環境：macOS、arm64；JDK 為 Android Studio 內附的 openjdk 25.0.2；Gradle 9.5.0；AGP 9.3.1（內建 Kotlin 2.2.10）。
- 指令：`./gradlew testDebugUnitTest --tests '<探針類別>'`，結果讀 `app/build/test-results/testDebugUnitTest/*.xml`（不靠 console）。需要的新相依從 Google Maven 與 Maven Central 下載。
- 基準：未改動的複本跑整套測試 → 9 個測試類別、136 個測試、0 失敗。

## 決策歷程

### 本輪的使用者裁決（2026-09-14、2026-09-16，原意保留）

- **對話儲存改成資料庫，這是第一版，不做搬遷。** 既有的 JSON 對話可以全部清空；「不搬遷」寫進「明確不做」，並寫明後果：升級之後原本的對話會全部不見。
- **舊 JSON 檔刪掉還是留著，由 PM 判斷並寫出理由。** PM 的判斷：刪（理由與反方向代價在 `spec-decisions.md`「本輪我自己做的判斷」第 1 項）。
- **歷史清單直接跟著資料庫的變動更新**；串流中切換，被切走的那段要立刻回到清單上。
- **還沒存檔的新對話、生成中的回覆必須仍然搜得到**；資料庫不能是唯一的來源。
- **資料庫壞掉或讀不起來時會怎樣要寫出來。** 共同的部分寫進 `spec.md` §5；有取捨的部分升級成 D3。

- **寫入權限**：只能寫本 slug 與兩份共用文件；不得改另兩份規格與那個 bug 的目錄。所以跨輪衝突只能列清單、交給 D4。

- **沒有把「寫不進去時那段仍留在清單上」寫成規則。** 那需要一份「沒存成的對話」的記憶體清單，等於在清單的組合裡多一個來源；而寫不進去在這個 App 的實際機率不高（最可能的原因是空間不足）。先告知，等有人回報再做。

## 已知取捨與風險

- **刪舊檔是不可逆的。** 發佈之後，改變主意要搬遷也來不及。觸發條件寫在「明確不做」第一條。
- **裝置上的重現只做一次一個入口。** 它證明的是「每個入口都接上了變動通知」，不是「不會漏」；後者靠任務 1 驗收 2 與任務 2 驗收 1。若 D1 拍成 (d)，這個分工就不成立，裝置那一條會變成唯一的證據，而它證明不了並發性質。
- **測試跑的 SQLite 可能與手機上的不是同一份**（D1 選 (a)、而正式程式用 Android 內建的時）。本規格用到的功能很基本（交易、依主鍵讀寫、變動通知），差異風險低，但**沒有查證**。
- **「整份讀不起來」在裝置上怎麼造，依賴 D2。** 若 D2 的做法造不出來，§5.1 這一輪在裝置上判不到，只剩存取層那一半。
- **§5.2 寫不進去的情境，模擬器上不一定做得出來**（條文允許記「本環境無法觀察」並要求明講畫面那一半沒判到）。
- **另兩份規格在 D4 落實之前，與本規格對同一件事的「怎麼看」不一致。** QA 在那段期間可能在那兩份規格上判出假的 fail。
- **變動通知的延遲沒有量化**：`spec.md` §2.2 用的是「使用者切換後打開抽屜所需的時間內」，任務 1 驗收 6 的 5 秒是測試時限，不是產品要求。若 QA 覺得清單出現得明顯慢，記下來回報，不直接判 fail。
