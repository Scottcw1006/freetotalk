# 架構決策（對話儲存改為資料庫 spec 的第四節）

> 入口與檔案地圖見 `spec.md`。
>
> **這一整份是給 RD 的建議，不是裁決。QA 不驗這一節。** 你用了不一樣的做法、滿足了 `spec.md` 的行為規格、也通過了 `spec-tasks.md` 的驗收 —— 那就是完成，不是缺陷。**若你決定不照這裡的某一條走，請寫進本 slug 的 `pm-inbox.md`**，講一句為什麼。
>

## §A 清單是持續算出來的，不是讀一次存起來的

**§A.1 讓歷史清單由「儲存的變動通知」與「開著的是哪一段」持續組合出來，任一邊變動就重算。**
- **理由（使用者後果）**：只要清單是「某一刻讀一次、寫進狀態」，就一定存在一種順序：讀取早於某次存檔、而那份讀到的結果最後才落地 —— 被切走的那段就不在清單上，直到下一次別的動作觸發重讀。那就是 `history-missing-after-switch` 的第二個成因（`spec.md` §2.1）。
- **換成持續組合之後，現行那幾處「存完之後重讀一次」就不再承擔正確性。** 留著或拿掉是你的判斷；若留著，確認它不會把較舊的結果蓋回去。
- **建議把這個組合放在不依賴 Android 的地方**：`spec-tasks.md` 任務 2 驗收 1 要求一支能直接驅動它的測試（可驗證性要求）。怎麼切由你決定。

**§A.2 變動通知要涵蓋 App 裡所有的寫入者。**
- **理由**：一個行程裡若有兩份各自獨立的資料庫實例，其中一份寫入時，另一份的訂閱者可能收不到通知 —— 清單又會停在舊的樣子。最簡單的保證是整個行程只有一份；若你有理由不這樣做，確認通知跨得過去。
- **這一條與 `docs/specs/conversation-search/spec-architecture.md` §E.4「生命週期：不要做成跨畫面共享的實例」的建議方向相反**（見下面 §E）。

## §B 寫入是整筆的

**§B.1 一次存檔整筆生效。**（v2 改寫：原本寫「在一個交易裡完成」，那是手段。）
- **理由**：「先刪掉舊的、再寫入新的」若是兩個各自生效的步驟，中間那一瞬間讀取的人會讀不到那一段 —— 形狀與舊的「先截成空檔再寫入」一模一樣（`spec.md` §1.4）。2026-09-16 的探針量過：在交易裡改寫，752,118 次並發讀取沒有一次讀不到（`spec-appendix.md`／「查證」）。
- **RD 採用的形式（2026-09-17 RD 回報，記錄，不是請示）**：一段對話存成一列，訊息整包放在那一列的一個文字欄位裡；存檔是**一個**「新增或覆寫」指令，刪除是一個指令，取全部是一個查詢。單一指令本身就是整筆生效，**沒有「忘了包交易」這種錯法** —— D1 拍板不做資料庫層測試之後，這一點是 §1.4 與「寫入失敗不毀掉已存的」唯一的保證，所以**日後若改成多個指令，必須同時補回交易與測試**（`spec-tasks.md`「明確不做」的 D1 例外那一條的觸發條件）。
- **連帶的好處**：訊息的解析留在不碰資料庫的純邏輯裡（§C.1），而那正是 D1 要求要能直接測的地方。
- **同一段對話同時被存兩次（內容相同）時，不要去拿掉其中一次**：那兩次各自受另兩份規格保護（`spec.md`「這次會踩到的既有事實」第 2 條）。讓它們無害就夠了。**若你判斷非改存檔時機或次數不可，先寫進收件匣** —— 那會變成跨輪待決事項。

## §C 讀取要容錯，而且兩條讀取路徑同一個答案

**§C.1 一筆資料讀不起來時，只丟掉那一筆，不要讓整次讀取失敗。**
- **理由**：一次把整張表映射成物件的寫法，遇到一筆無法映射的資料會讓整份讀取丟出例外 —— 使用者看到的是整份歷史不見（`spec.md` §1.5）。
- **（v2）RD 的形式**：Room 只交出每一列的原始字串，解析在純邏輯裡一列一列做、解不開的那一列丟掉。解析**不要用 Android 的 JSON 程式庫**（它在 JVM 測試裡是空殼，那樣 `spec-tasks.md` 任務 1 驗收 1、3 就寫不出來）。

**§C.2 「依 id 取一筆」若改成直接查詢，要套用與「取全部」相同的容錯與相同的讀取規則。**
- **理由**：兩條路徑答案不同的樣子是「從抽屜打得開的對話，從冷啟動續接卻打不開」（或反過來）。`conversation-search` §E.6 警告過同一件事（當時的手段是「用 id 拼檔名」）。

**§C.3 讀取時不要再做「模型輸出修復」。**
- **理由**：它是為舊檔存在的，而舊檔不再被讀（`spec.md` §1.1）。留著它，使用者打的反斜線與前後空白在重開後會被改掉；而且修復不保證冪等，同一段助理訊息每重開一次都可能再變一次。生成當下的修復照舊。

## §D 搜尋與清單的來源

**§D.1 搜尋照舊在「開著的那段（記憶體）＋ 歷史清單」上比對，不要把比對搬進資料庫查詢，也不要讓清單或搜尋只讀資料庫。**
- **理由**：還沒存下的對話、已送出但回覆還沒結束的那句、生成中的回覆，都不在資料庫裡（`spec.md` §3.1）。`conversation-search` 的 §B.2 與它「明確不做」裡「沒有索引、沒有快取」那條給過同樣的建議，理由相同。
- **資料庫帶來的查詢能力，這一輪只用在「取全部、依 id 取、存、刪、訂閱變動」。**

## §E 與 `conversation-search` 的架構建議方向相反的地方（知情）

使用者 2026-09-14 已知道這件事（`history-missing-after-switch` 收件匣第一筆第 5 點），並說明那是建議不是規定。這裡列出本規格的建議會與哪幾條相反，讓你寫收件匣時不必自己去找：

| `docs/specs/conversation-search/spec-architecture.md` | 那裡建議的 | 本規格建議的 |
|---|---|---|
| §E.3「保持零狀態的純轉發：不快取、不合併、不持有推送式的資料流」 | 存取層零狀態、沒有推送式資料流 | 儲存要能發出變動通知（§A.1），而且清單是持續組合的 |
| §E.4「生命週期：不要做成跨畫面共享的實例」 | 存活範圍就是持有它的狀態層 | 一個行程一份資料庫實例較不容易漏通知（§A.2） |
| §E.5「對外只保留目前有呼叫端的四件事」 | 取全部、依 id 取、存、刪 | 多一件：訂閱變動 |
| §E.1「分層一致性，不是搜尋的需要」 | 這一層對搜尋的淨技術效果是 0 | 這一層開始有邏輯（整筆寫入、容錯、變動通知），`conversation-search`「明確不做」裡「對話存取層沒有自動化測試」的觸發條件因此成立 |

**§B.2（不要在存取層開查詢方法、搜尋路徑上不要有持久化呼叫）與本規格一致**，不在上表。

**（v2，D4 已拍板）本輪不改那幾條，也不另排時間改。** 那份規格下一次被修訂時，以 `plan/architecture.html`（本輪任務 8 會更新成新的儲存方式）為準改寫；改寫清單在 `spec-appendix.md`／「跨輪衝突清單」。

## §F 舊資料清理

**§F.1 清理只認舊位置那一個子目錄，而且要能對任意目錄執行。**
- **理由**：模型檔就在它的上一層（`spec.md`「這次會踩到的既有事實」第 1 條）。刪錯一層，使用者要重新等 GB 級的解壓。能對任意目錄執行，`spec-tasks.md` 任務 4 驗收 1 才寫得出不經過裝置的測試。

## §G 壞掉或開不起來時：Room 的預設行為只做到一半

**§G.1 讓「整份讀不起來」的每一種樣子都走到同一個結果：丟掉、重新開始、提示一次。**（v2 依 D3 (b) 與「使用者指定 Room」改寫。）
- **Room 預設會做的**：用 Android 內建的開法時，偵測到檔案損毀就刪掉整個資料庫檔、重建一份空的 —— **不會通知 App**。這一半剛好符合 D3 的「壞掉的那份不保留」。
- **Room 預設不會做的**：(i) 讓 App 知道發生過這件事，所以 `spec.md` §5.1 的提示不會出現；(ii) 結構版本對不上（例如日後裝回舊版）時，它是丟出錯誤而不是重來；(iii) 其他開檔失敗（例如權限）同樣是丟出錯誤 —— **（v3）這一種不屬於本條，不要丟掉重來，見 §G.2。** 本條說的「每一種樣子」只指內容本身壞了的那些（`spec.md` §5 開頭那張表）。
- **理由（使用者後果）**：只靠預設，使用者看到的是抽屜突然空掉而沒有任何說明（使用者沒有選的那個 (a)），或者 App 在結構對不上時閃退。怎麼偵測、在哪裡接，由你決定。
- **損毀可能在使用途中才被發現**（不一定在啟動時），所以提示不要只綁在啟動流程上（`spec.md` §5.1 寫的是「不論在啟動時還是使用途中發現」）。

**§G.2（v3 新增）分辨「內容壞了」與「開不起來」時，判不出來就當成開不起來：不丟。**
- **理由（使用者後果）**：丟掉是不能復原的。把一份內容完好、只是暫時開不起來的資料庫當成壞了，使用者完好的紀錄就沒了（`spec.md` §5.4）；反方向判錯的後果只是這次啟動讀不到、下次再試。
- **現況（讀 `6b284d1` 的程式碼）**：縮小之後的判定已經不把一般的錯誤算成壞了，唯讀那一種也確實不會被刪（v2 驗收實測恢復可寫後資料都在）。**但 Android 回報「開不了檔」的那一類錯誤仍在「壞了」的清單裡**（`spec.md`「這次會踩到的既有事實」第 15 條）。那一類錯誤說的是開不了，不是內容壞了；Android 自己遇到真的損毀時，本來就會刪檔重建，那條路已經由「偵測到資料庫被重新建立」接住。要不要把它移出清單，由你判斷；任務 5 驗收 4 的造法 (ii) 會照這一點。
- **§5.4 要的另外兩件事，`6b284d1` 的實作還沒有**（RD 在收件匣也這樣回報）：開不起來時的提示、抽屜上那句「目前讀不到之前的對話紀錄。」（v2 驗收時抽屜只是默默變空）。「下次啟動再試」現在是自然成立的（每次啟動重新開檔），不要因為加提示而把它弄掉。怎麼讓畫面知道「現在是開不起來的狀態」，由你決定。

## §J（v3 新增）取消生成之後，等推論真的停下來才讓出引擎

**§J.1 保留 `6b284d1` 的做法：取消只是發出請求，要等原生推論真的結束，才關掉 session、才讓出引擎。**（記錄 RD 已做的修正，不是新要求。）
- **理由（使用者後果）**：推論執行緒還在讀模型時，切換模型把模型關掉，App 會在原生程式裡閃退（`spec.md`「這次會踩到的既有事實」第 16 條；任務 7 驗收 13）。
- **代價要看著**：等待的這段時間，引擎不能開始下一次生成。正常的收尾很短；卡住時最多多等 10 秒，使用者會感覺「停止之後再說話，回覆很久才出來」（任務 7 驗收 14）。等待上限要不要調，由你判斷。
- **這段程式是 `stop-generation` 重驗的觸發條件**（`spec-tasks.md`「明確不做」）。之後再動它，先寫進收件匣。

## §H 測試的形狀

**§H.1（v2，D1 已拍板）不要替資料庫層引進任何測試相依；本輪的自動化測試只用現有的 JUnit。** 要測的純邏輯（讀回不加工、空白對話的處置、一列一列容錯、兩條讀取路徑同一個答案、清單組合、舊目錄清理）都不碰資料庫。
- **（降級成觸發時的參考）** 日後出現意料外的資料庫 bug、要把它加成測試時，起點在 `spec-appendix.md`／「查證：資料庫能不能在 JVM 單元測試裡跑」。其中 Room 搭配主機端 SQLite 那條路，測試端要兩個替身、依賴 Room 2.8.5 的內部行為；若那時選它，讓儲存層可以直接用一個路徑或驅動建起來，會比較不脆弱。
