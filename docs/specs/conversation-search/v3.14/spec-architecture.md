> ## 這一整份檔案是建議，不是裁決
>
> **（v3.11 起）這裡的每一條都是給 RD 的建議。QA 不驗這一節。**
> **如果你用了跟這裡不一樣的做法、滿足了 `spec.md` 的行為規格、也通過了 `spec-tasks.md` 的驗收 —— 那就是開發完成，不是缺陷。**
> 必須成立的東西全部在**行為規格**與**驗收標準**裡；這一節寫的是「為什麼當初是這樣切的」，它的用途是讓下一個人在改動之前知道自己會踩到什麼。
>
> **本輪為什麼要重新分類**：這份檔案成形的時候，「說得出使用者後果的才寫成規則、其餘最多是建議」這條准入判準還不存在。當時沒有做錯，要處理的是規則生效前留下的存量。依使用者裁決，本輪逐條重判：**說得出使用者後果的搬進行為規格或驗收條文，說不出來的留在這裡當建議，已經是別處通則的整條收掉。**
> **搬走的規則一個字都沒有改**，改的只是它寫在哪一份文件裡、以及誰負責驗它。
>
> **（v3.14）每一條建議的標號前面補上「§」**（例如「B.3」→「§B.3」），**內容一個字都沒有動**。理由：本規格各處引用這些建議時都寫成「§B.3」，別的文件也照這個寫法指過來，而標號本身沒有「§」，照字面 grep 不到。補一個字之後，寫成「B.3」的舊引用照樣 grep 得到。

## §F 為什麼整節不見了

**§F 那七條寫的是每一份規格都適用的通則**（誰負責驗什麼、可自動化的條文必須指得出測試、規則必須指得出條文、實機條文不得預設環境能力、實機判讀前要先證明建置、兩輪之間的衝突由使用者裁決）。**它們的權威在 PM 與 QA 的角色定義裡，不在本規格裡。**

**這裡刻意不留摘要，只留這句指路。** 抄一份進來就會出現第二個版本，而「同一件事被寫成兩份、兩份遲早分歧」正是本規格從頭到尾在防的那個失效模式（見 `spec.md` §2.11、附錄／決策歷程）。

**本規格自己依賴、而且是本規格特有的那兩件事，已經寫進條文本身**：比對語意的權威落在不經過實機的測試上（原因是這台裝置送不了非 ASCII，而 U+00A0、零寬字元這些素材在實機畫面上根本看不出差別）→ 寫在**任務 3 的說明**；實機負責的是算繪與版面而不是算對 → 寫在**任務 7、9、13 的說明**。

# 架構決策（以下全部是建議）

## §A 比對邏輯的位置

**§A.2（建議）畫面端只負責把算好的區間上色，不要在畫的那一邊再判斷一次什麼算命中。** 包含子字串搜尋、大小寫或全形折疊、去空白、正規表示式。
- **理由**：一旦畫的那一邊需要自己判斷什麼算命中，比對規則就出現了第二份，而第二份是測試看不到的那份。
- **界線**：這條講的是「什麼算命中」，不是「有幾個命中」。摘要那兩個數字的加總不在此列（見附錄／已知取捨與風險）。
- **為什麼它只是建議**：違反它不一定會讓使用者遇到任何事 —— 第二份寫法可能剛好也是對的。真正會被使用者看到的是「標示蓋錯字」與「該命中的沒命中」，那些有行為條文在守。

**§A.4（建議）跨層交出去的命中結果，讓接收端不必自己再算一次。** 對每一則命中，接收端拿得到：命中的訊息本身、可直接顯示的片段、指向片段的標示區間（語意見 `spec.md` §4.5）；對每一段對話，還拿得到**未截斷的**命中訊息總數。
- **理由**：使用者看到的文字不是被拿去比對的那份文字（中間隔著整形與折疊）。索引只有在算出它的地方才有意義，讓接收端自己重算等於複製規則。
- **保留完整訊息而不只是文字**，是為了日後「跳到那一則訊息」的接縫（見「明確不做」）。**今天沒有人用到它，所以它是建議** —— 把它改成只交出文字，今天不會有任何使用者察覺。

## §B 搜尋看的是畫面上有什麼，不是磁碟上有什麼

**§B.2（建議）不要在對話存取層上開查詢 / 搜尋 / 過濾方法；搜尋路徑上不要出現持久化呼叫。** 理由有四層，前兩層是正確性：

1. **存取層的世界是「磁碟上有什麼」，搜尋的世界是「使用者在螢幕上看得到什麼」。** 兩者差的正好是開啟中的那段對話 —— 它可能整段還沒存檔，也可能是永遠不會被存檔的空白對話。走存取層查詢，會讓使用者正在看的那段永遠搜不到（那個後果本身是 `spec.md` §1.8，它有條文在守）。
2. **生成中的回覆不在磁碟上。** 串流期間每個片段都只在記憶體裡。
3. 即時搜尋每按一鍵就變成「列目錄 + 解析所有檔案」。這是效能理由，排第三。
4. 一旦存取層上出現查詢方法，下一個想讓它變快的人會直接去掃檔案內容 —— 而**磁碟上的文字不等於使用者看到的文字**（讀出時才會做文字修復：磁碟上是字面的兩字元轉義與 byte-level 替身字元）。方法不存在，這個誘惑就不存在。

**§B.3（建議）「所有對話」值得只有一個組裝處，而且合併順序就是語意。** 它是兩個來源的合併：歷史來自磁碟，開啟中的那段是記憶體裡的即時版本。這兩個來源在原理上就可能描述同一個 thread。**「同一段出現兩次時該用哪一份」的答案是規範，已經寫在 `spec.md` §3.5**（記憶體那份；先決定留哪份、再排序）。這裡剩下的是給實作者的三句話：
- **去重不是防禦性程式碼，是把合併語意寫出來。**
- **值得同時寫下「今天為什麼不會重複」**：那個不變式目前靠的是重新整理歷史時的過濾、以及切換對話時兩次狀態更新的先後順序 —— 那是下一個修改切換邏輯的人不會知道自己踩到的東西。不寫下來，去重那一步會變成一句沒人知道為什麼存在的話。
- **這裡我與 RD 的傾向不同，兩邊理由都留著**：RD 傾向只寫明不變式、不加去重，理由是「加去重會把真正的答案藏起來」。這個顧慮成立。我仍傾向加去重，因為失敗模式是列表 key 撞號**直接崩潰**，而且崩潰點離成因很遠（崩潰本身有條文在守：`spec.md` §3.6）。

**§B.4（建議）讓搜尋結果是衍生值，不是被寫進狀態的欄位。**
- **判斷方式**：任何會改變「開啟中的對話」或「歷史」的地方（送出訊息、串流更新、重新整理歷史、刪除對話、切換人格 / 模型 / 對話、停止生成），都不需要額外補一行去更新結果。
- **理由**：刪掉一段對話、串流進一個字，都會改變什麼算命中，而這兩件事都不會經過搜尋的程式碼。做成衍生值，就沒有人有機會忘記重算。代價（每次狀態變動都重算全部結果）見附錄／已知取捨與風險。
- **為什麼它只是建議**：搜尋是全螢幕獨立畫面，大部分「忘記重算」的路徑在搜尋畫面上根本走不到，使用者看不到差別。**看得到的那一條是串流** —— 它有條文在守（`spec.md` §1.8、任務 5 驗收 2）。

**§B.6（建議）「所有對話」的組裝留在狀態層，不是存取層。**
- **理由**：開啟中的那段是**會話狀態**不是持久化狀態。要存取層組這份清單，就得由狀態層把當前對話推進去 —— 反向依賴，而且製造第二個真相來源。**存取層管磁碟，狀態層管使用者看得到什麼。**

## §C 文字管線：一個座標系

**§C.1（建議）步驟順序。**
1. **整形**（`spec.md` §2.3）—— 這是**唯一**准許改變長度的一步。
2. **折疊**（大小寫與全形）—— 逐字元、長度不變，只用於比對，不用於顯示。
3. 在折疊後的字串上找出所有命中位置。
4. 依第一個命中位置裁切片段視窗。
5. 片段取自**整形後**的字串；標示索引相對於片段。

- **理由**：整形會改變索引，折疊不會。整形排在最前面，之後所有索引才有唯一的座標系。**這個順序的可觀察後果已經寫成規則**（`spec.md` §4.7、§4.8：標示必須落在正確的字上）；換一種達成方式而標示仍然全對，不算違反。

**§C.2（建議）折疊做成長度不變的一對一映射。** 只要長度會變（例如整串小寫化遇到 U+0130），標示就會錯位。可觀察面同 C.1。

**§C.5（建議）什麼時候該共用程式碼，什麼時候不該。** 這份規格出現過方向相反的指示，判準寫在這裡 —— **不是「看起來像不像」，而是「這兩邊是否必須永遠相等」**：
- **必須共用**：查詢端與訊息端的正規形式、「算不算空查詢」、欄位規則所用的空白集合。**它們在定義上必須永遠相等**，一旦不相等，比對或畫面狀態就壞了。這種關係該由同一份程式碼保證，讓「不相等」變成不可能發生。（**這一項不只是建議** —— 它必須成立的那個性質已經寫成 `spec.md` §2.11，有條文在守。）
- **不得共用**：搜尋的訊息取捨，與「送進模型的上下文」的訊息取捨。前者回答「使用者在螢幕上看過哪一句話」，後者回答「模型看什麼才答得好」——**在定義上是兩個不同的問題**，今天答案剛好都跟開場白有關，明天可以各自改變。共用會把兩個獨立的判斷綁死。**不要為了「看起來一致」把它們抽成共用過濾器。**
- **一個具名的例外**：摘要的兩個數字與命中結果的關係，同樣屬於上面第一類，但使用者裁決保留兩份寫法。**這是例外，不是判準改變。** 代價與觸發條件見附錄／已知取捨與風險。

**§C.7（建議）在折疊那一步的說明裡寫明「U+3000 不歸這裡，歸整形」。**
- **理由**：第一輪的缺陷成因正是「兩邊都以為對方處理了」。這句註解是防止同一個 bug 再犯最便宜的機制。
- **為什麼它從硬性條文降成建議（v3.11）**：這句註解在不在，使用者感受不到差別。**它要防的那個 bug 本身有條文在守**（任務 3 驗收 18、19：訊息端 U+3000 配半形空白查詢必須命中，且四個端到端案例都要走完整入口）。**降級沒有放寬那些條文。**

## §D 搜尋是獨立畫面

**§D.3（建議）搜尋畫面不要自己持有狀態來源，由外部把資料與回呼交給它。**
- **理由**：搜尋的資料來源就是聊天那一份狀態。若它自己去取一個狀態來源，會產生第二份對話清單，且與聊天那份不同步 —— 那份會少掉還沒存檔的對話與正在串流的回覆（那個後果是 `spec.md` §1.8，有條文在守）。既有的比較畫面可以那樣做，是因為它的資料完全是自己的。
- **順帶一提，為什麼當初不是「把整個抽屜改成單一捲動容器」**：(a) 那會動到一個正常運作、與搜尋無關的介面，是附帶損害且需要自己的回歸驗證；(b) 那需要新增「取得焦點時自動捲到搜尋框」這個會失敗的時序行為，而獨立畫面的「輸入框在最上面」是**由結構保證**的；(c) 獨立畫面有既有前例；(d) 順帶解掉寬度疑慮。

## §E 對話存取的分層

**§E.1（建議）在這一層的說明裡誠實寫出它的定位：分層一致性，不是搜尋的需要。**
- 技術分析本身仍然成立：搜尋的資料來源是記憶體中的狀態，完全不產生新的 IO 需求，所以「存取層沒有查詢能力」**不是搜尋暴露出來的缺口**，這一層對搜尋的淨技術效果是 **0**。**使用者在知情的前提下裁決納入，理由是分層一致性本身。**
- **為什麼值得寫下來**：寫成「為了搜尋」之類的假理由，會誤導下一個想在這裡加查詢方法的人（B.2 不建議那麼做）。
- **換到的東西**：重複的「依 id 找一段對話」收斂成一處；狀態層少一個直接持有的 Android 相依；日後要加快取或索引時接縫已在正確位置。**代價**：多一層轉發、沒有自動化測試守著它、搬動時有把既有行為改壞的風險（那個風險的三個具體樣子已經寫成 `spec.md` §9.1–§9.3）。

**§E.2（建議）它只包「多筆對話語料」的存取，不包「使用者上次停在哪」那個游標。**
- **理由**：前者是多筆、非同步、檔案 IO；後者是三個純量、同步存取。包在一起會逼其中一方遷就另一方的存取風格，並讓這一層有兩個不相干的變更理由。

**§E.3（建議）保持零狀態的純轉發：不快取、不合併、不持有推送式的資料流。**
- **理由**：這是結構搬移，唯一的驗收方式是「行為與搬移前一模一樣」。加了快取就同時改變了「什麼時候會看到新資料」的語意 —— 而且不會有任何呼叫端改變，沒有人看得出來。
- **因為它沒有邏輯，所以不需要自動化測試；反過來說，哪天它開始有邏輯，那天就欠一個測試。** 這兩件事綁在一起（見「明確不做」）。

**§E.4（建議）生命週期：不要做成跨畫面共享的實例** —— 不是全域單例、沒有全域取得點，存活範圍就是持有它的那個狀態層。不引入相依注入框架。
- **理由**：引擎做成單例，是因為它持有數百 MB 原生記憶體且必須跨畫面序列化存取；這一層沒有狀態、只有一個消費者，做成單例等於宣告一份沒人需要的契約，日後只會被誤解成「這裡有快取」。

**§E.5（建議）對外只保留目前有呼叫端的四件事**：取全部、依 id 取一筆、儲存、刪除。不要新增目前沒有呼叫端的方法，尤其不要有查詢方法（見 B.2）。排序留在下層。

**§E.6（建議）不要把 id 當成檔名去信任檔案系統。**「依 id 取一筆」直接用 id 拼出路徑去讀，是「讓它變快」最自然的第一步，而它會同時繞過壞檔容錯。
- **必須成立的那一半已經是規則**：兩條路徑必須得到同一個答案（`spec.md` §9.3），以及壞檔不得讓其他對話消失（§9.2）。這裡寫的是最容易踩到的那個手段。

## §G 最後更新時間

**§G.1（建議）讓「什麼算一次更新」只有一個回答的地方。** 所有會把對話寫回狀態的路徑，都經由同一個地方回答「這一次算不算更新」，而不是由各條路徑各自決定要不要蓋上時間。
- **理由**：這與空白定義是同型的問題 —— 一個規則被第二次、用不同的方式回答，兩個答案遲早會分岐。而這次的成因正是它的反面：一條「把對話寫回去」的共用路徑**無條件**蓋上現在時刻，於是所有經過它的動作都被記成一次更新，包括根本沒有改到任何訊息的那些。
- **它守的那些行為是規則**（`spec.md` §8.1、§8.2），由任務 13 驗收 6 承接：所有寫回對話的路徑都經過同一個判斷。**這也是為什麼 §8.1 底下「訊息被移除要讓時間前進」那一項不必再寫一條自己的驗收。**
- **一件事後收到的回報**：把規則寫成「內容有沒有改變」而不是「哪些動作要排除」，讓 v3.6 那次規則改動（停止生成從「不算」換到「算」）的實作成本變成零 —— 那個唯一的判斷處本來就沒有針對停止的特例。
