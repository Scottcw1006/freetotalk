## 任務 2：比對與片段的純邏輯
- **驗收 1**：pass。`ConversationSearch.kt` 沒有 import 任何東西，它相依的 `Conversation.kt`、`Persona.kt`、`ModelSpec.kt` 也都不 import Android。測試相依只有 `junit`；探針用純 JVM 就能編譯執行。
- **驗收 2**：pass。測試 `an empty query is not a search`，涵蓋 U+3000 與 U+00A0，並以碼位確認。
- **驗收 3**：pass。測試 `conversations come back newest first and hits stay in the order they were said`。
- **驗收 4**：pass。測試 `a conversation shows at most three hits but reports the true total`（3 / 5）。
- **驗收 5**：pass。測試 `a conversation with no matching message is left out entirely`。
- **驗收 6**：pass。測試 `highlights stay inside the snippet and never overlap`。
- **驗收 7**：pass。`flattenToLine`、`normalizeForSearch` 是 `internal`，測試直接呼叫並單獨斷言。
- **驗收 8**：pass（靜態＋探針）。四個使用點都呼叫同一個 `isFlattenableSpace`：
  - 訊息端與查詢端都走 `flattenToLine`。
  - 算不算空查詢是 `isActive = query.flattenToLine().isNotEmpty()`。
  - 欄位規則是 `withoutLeadingSpace` / `withoutTrailingSpace`。

  探針實測：
  - U+0020 與 U+00A0：兩端整形都得到 `a b`；單獨一個字元時 `isActive=false`；放在欄位開頭與尾端都被移除。
  - U+001C：兩端整形都得到 `a<1C>b`，沒有被收合；單獨一個字元時 `isActive=true`，而且結果為空，會走「找不到」那一支；放在欄位開頭與尾端都留著。
- **驗收 9**：pass。測試 `every unicode separator is collapsed`（BMP 掃描）、`zero-width characters are not whitespace`、`a run of mixed whitespace becomes exactly one space`。
- **驗收 10**：pass（靜態＋實機）。`onSearchQueryChange` 只呼叫 `withoutLeadingSpace`，沒有把整形後的字串寫回欄位。實機上「北京 天氣」中間的空白、`zebra  ` 的尾端兩個空白，在打字過程中都逐碼位留著。
- **驗收 11**：pass。`isActive` 用的是整形判斷；測試 `isActive agrees with flattening about what counts as empty`。

- **驗收 16 的說明**：兩個方向都有獨立的測試。
  - 起點方向 `cropping never splits a surrogate pair`：測資是 15 個 emoji＋1 字＋北京＋尾巴，查詢詞起點在索引 31，引子想從 11 開始，而索引 11 是第 6 對的低位代理。
  - 尾端方向 `cropping never splits a surrogate pair at the window end`：測資是 30 字＋北京＋7 字＋20 個 emoji，視窗想在 70 結束，而索引 69 是某一對的高位代理。
  - 兩者都斷言片段含「北京」（正向對照），並逐一檢查每個代理字元都有配對，所以首尾兩個 code unit 都涵蓋在內。
  - **兩者互不干擾**（手算）：起點案例的視窗尾端落在 BMP 字上，有沒有尾端保護都一樣；尾端案例的視窗起點在索引 10，也是 BMP 字，有沒有起點保護都一樣。所以拿掉某一側的保護，只會讓對應的那一個案例變紅。本輪沒有做突變執行（非本輪要求），這一點停在推導層次。
