## 任務 3：比對語意的單元測試

- **說明**：這個任務是比對語意的**唯一權威**，任何一條都不要求在裝置上重驗。

- **對應功能模組**：比對純邏輯
- **驗收標準**（每條一個測試）：
  1. 使用者訊息與助理訊息都能被搜到（各一個案例）。
  2. 大小寫不敏感：`hello` 命中 `Hello world`；`HELLO` 亦然。
  3. 全形折疊：`ABC` 命中 `ＡＢＣ`；`ｈｅｌｌｏ` 命中 `Hello`。
  4. 不做繁簡折疊：「台」不命中僅含「臺」的訊息。
  5. **(v3 修訂)** 查詢前後空白被去除：`"  北京  "` 與 `"北京"` 結果相同，**且兩者都不得為空**（測資必須讓「北京」確實命中，並斷言命中筆數 > 0）。理由見 §2.7。

  8. 折疊長度不變：直接呼叫折疊步驟，對含 U+0130 的字串斷言長度不變。
  9. 標示位置正確：含換行的訊息命中時，片段中被標示的那段恰等於原文對應的字（§4.8）。
  10. 同一則訊息中落在視窗內的每一個命中都有標示（§4.6）。
  11. 長訊息裁切：命中在第 100 字時，片段以「…」開頭、長度符合 §4.1–§4.3、標示位置正確。
  12. 每對話上限：5 則命中時只顯示 3 則，回報總數為 5（§3.3）。
  13. 開場白可以被搜到，且命中的是該對話第 0 則、作者為助理（§1.1）。
  14. 只有開場白的空白對話也會產生命中：顯示 1 則、總數 1；不命中時完全不出現（§1.8、§3.1）。
  15. 重複開場白會產生多筆結果：三段同人格的對話全部出現（§3.7）。
  16. **(v3.11 改寫：指定測資形狀，並補上尾端那個方向)** **片段裁切不得從 surrogate pair 中間切開（§4.4）。兩個方向各要一個案例，而且測資必須真的碰得到邊界。**
      - **這一條原本沒有鑑別力，那是實測出來的**：舊測資的形狀（一長串 BMP 字元 + 查詢詞 + 排在後面很遠的一串 emoji）在數學上永遠碰不到任何一個保護 —— 視窗尾端與 emoji 起點的距離恆為偶數，視窗起點又永遠落在 BMP 區間裡。**把兩處保護整個拿掉（直接回傳原本的索引），全套單元測試仍然全綠。**
      - **起點方向的測資性質**：讓「命中起點往前 20 個 code unit」那個位置**落在一對代理對的後半**。
        - 可用的形狀：連續 15 個 emoji（每個佔 2 個 code unit）＋ 1 個 BMP 字 ＋ 查詢詞 ＋ 足夠長的 BMP 尾巴。查詢詞起點落在索引 31，引子想從索引 11 開始，而索引 11 是第 6 對的後半。
      - **尾端方向的測資性質**：讓「視窗起點往後 60 個 code unit」那個位置**落在一對代理對的中間**（也就是視窗最後一個 code unit 是某一對的前半）。
        - 可用的形狀：30 個 BMP 字 ＋ 查詢詞 ＋ 7 個 BMP 字 ＋ 連續 20 個 emoji。查詢詞起點落在索引 30，視窗想在索引 70 結束，而索引 69 是某一對的前半。
      - **兩個案例的預期（都要斷言）**：片段逐碼位讀出來，**第一個 code unit 不得是落單的低位代理，最後一個 code unit 不得是落單的高位代理**；**且片段裡仍然完整含有查詢詞**（正向對照不得省略 —— 只斷言「沒有半個字元」的話，一個回傳空片段的實作也會通過）。
      - **兩個案例必須各自獨立**：只讓起點那一側的保護失效時，**只有**第一個案例變紅；只讓尾端那一側失效時，**只有**第二個案例變紅。
      - *為什麼條文要寫到測資這一層*：這一條的鑑別力**完全**來自「測資有沒有碰到邊界」，而那件事光讀條文看不出來。條文不寫清楚，下一個人不會知道該用什麼形狀 —— **而這正是它腐爛的方式**。
      - *為什麼不指名測試方法的名字*：方法名字是隨時會被改的東西。判斷依據是上面兩個測資性質與預期。
      - **(v3.20)** `spec.md` §4.4 已升級成「片段不得把一個字切成兩半」。**本條一字未改，仍是它的下限**；組合 emoji 由任務 18 驗。測資裡連續的 emoji 要是彼此不會組成一個字的單一 emoji（例如 😀），不能用國旗的區域指示符號 —— 那種符號兩兩組成一個字，會改變邊界落在哪裡。
  17. **整形的規範集合，用掃描式斷言**，三段都要有（§2.3）：
      - **下限**：掃過 BMP 全部 65536 個碼位，凡符合 §2.1 者都必須滿足 `整形("a" + c + "b") == "a b"`。**斷言必須是這個字面形式**（理由見 §2.3）。違反數為 0。
      - **上限**：U+200B、U+200C、U+200D、U+FEFF 不被收合；含 ZWJ 的組合 emoji 通過整形後字串不變。
      - **收合與去除**：`"北京\r\n\t (U+0020)(U+3000)天氣"` 收成**一個** U+0020，前後空白去除。
  18. 端到端：訊息端 U+3000 + 半形空白查詢 → 命中。
  19. 端到端：查詢端也整形，四個案例都要走完整的搜尋入口（§2.3）：
      - 訊息 `"北京\n天氣"`、查詢 `"北京(U+3000)天氣"` → 命中。
      - 訊息 `"北京(U+0020)天氣"`、查詢 `"北京(3 個半形空白)天氣"` → 命中。
      - 訊息 `"北京(U+00A0)天氣"`、查詢 `"北京(U+0020)天氣"` → 命中。
      - 查詢只有一個 U+3000 → 空結果。
  20. 標示長度等於整形後查詢的長度：查詢「北京(2 個空白)天氣」命中時，標示長度為 5，取出來恰為「北京(1 個空白)天氣」（§4.7）。
  21. 單一子字串而非多詞 AND：查詢「北京 天氣」**命中**「我在北京 天氣很好」、**不命中**「北京很大，天氣很好」（§1.3）。
  22. 「算不算空查詢」與整形用同一個定義：U+3000、U+00A0、`" \t\n"` 皆為非搜尋狀態，`"a"` 為搜尋狀態；並斷言**不存在**「畫面認為在搜尋、但整形後為空」的字元（BMP 掃描，§2.5）。
  23. **(v3.3 新增) §4.2 的視窗選取分支，三個案例缺一不可**（L = 59 / 60 / 61）。測資形狀與預期輸出見 §4.2 的三條可判定條文；**L = 59 與 L = 60 的預期片段必須不同**（59 的片段含 20 個引子字元，60 的片段第一個字元就是命中的第一個字元）。
      - *為什麼三個都要*：只測「一個很長的命中」，判斷式寫成 `≥ 61` 或 `≥ 59` 都會通過 —— 要驗的是**界線本身**，所以界線兩側各要一個案例，加上界線上那一個。
      - *為什麼這條是新加的*：舊的 22 條裡沒有任何一條會造出「命中長度 ≥ 視窗」的輸入，所以 §4.2 的第二個子句從來沒有被任何條文覆蓋過（見附錄／決策歷程）。
      - 測資只用 BMP 字元，避免與 §4.4（不得切開 surrogate pair）互相干擾 —— 那條允許視窗邊界移動一個 code unit，會讓本條的預期值變得需要額外解釋。
  24. **(v3.3 新增) §1.2 的元資料不參與比對。** 一段對話的人格顯示名為「老師」、模型顯示名為「Qwen2.5 0.5B」，而它所有訊息本文都不含這兩個字串 → 查「老師」、查「Qwen」、查「qwen」（大小寫不敏感的那個方向，§1.4）都**不得**命中該對話；**同一段對話用它訊息本文裡確實存在的字查，必須命中**。
      - *正向對照不得省略*：只有否定斷言的話，一個永遠回空的實作也會通過 —— 同 §2.7 的教訓。
      - *為什麼值得一條*：人格名稱與模型名稱是**印在分組標頭與命中列上的字**（§3.8），而 §1.1 的語氣是「使用者看得到的都搜得到」。這條擋的是一個很自然的後續改動（「讓使用者用『老師』找出所有老師人格的對話」），而那個改動不會讓任何既有測試變紅。
  25. **(v3.5 新增) 該有省略號與不該有省略號兩個方向都要驗（§4.3）。** 一則**整則放得進視窗**的短訊息命中時，片段的前後**都不得**出現「…」；同一個測試方法裡對照驗收 11 的長訊息案例（該出現時必須出現）。
      - *補這一條的理由*：驗收 11 只驗了「該出現時有出現」。§4.3 的第二條可判定（短訊息不得出現省略號）從來沒有被任何驗收指名，而**一個無條件在頭尾補上「…」的實作會通過原本全部 24 條**。這是「只有單向斷言」那一型。
  26. **(v3.7 新增，§1.2 的第三條可判定：對話標題不參與比對) 一段只有開場白的空白對話，其標題為「還沒說話」→ 查「還沒說話」不得命中該對話；同一段對話查它開場白裡確實有的字，必須命中。**
      - *正向對照不得省略*：只有否定斷言的話，一個永遠回空的實作也會通過（同 §2.7、§1.2 的教訓）。
      - *補這一條的理由*：§1.2 有三條可判定（人格名稱、模型名稱、標題），**驗收 24 只覆蓋了前兩條**。標題是一段對話的**衍生**屬性，對有內容的對話而言它等於使用者的第一句話（拿它比對看不出差別），**只有空白對話的標題是一個合成出來的字串**——所以「標題有沒有被拿去比對」這件事，只有在這個情境下觀察得到。
      - *這一條不要求任何新的實作*：核對時那個測試已經存在且兩半都在斷言。**判斷依據是上面那兩句可判定，不是那個測試方法的名字。**

## 任務 5：狀態層的搜尋入口與衍生結果

- **說明**：提供「查詢字串變更」與「清空搜尋」兩個入口，結果為衍生值。
- **對應功能模組**：聊天狀態
- **驗收標準**：
  1. **（v3.11 移除，編號保留不遞補。）** 原本是一條結構驗收：任何會改變開啟中對話或歷史的地方都不需要額外補一行更新結果。**移除理由**：條文自己就寫著「搜尋是全螢幕獨立畫面，『搜尋中刪除對話』『搜尋中收到新回覆』在畫面上不可達」—— 也就是說**違反它的那些路徑，使用者看不到**。看得到的那一條是串流，由下面的驗收 2 與 §1.8 守。建議仍在 `spec-architecture.md` §B.4。

  5. 旋轉後仍停留在搜尋畫面，查詢與結果都在（§5.6）。
  6. 搜尋期間送出訊息、停止生成、切換人格 / 模型等既有行為不受影響。
  7. 切換人格 / 模型後的空白對話，可用其開場白搜到（證明搜尋走記憶體而非磁碟，§1.8）。

## 任務 6：抽屜入口與搜尋畫面外殼

- **對應功能模組**：畫面切換點、搜尋畫面
- **驗收標準**：
  1. **(v3.15 依使用者裁決（決策 I）改寫) 抽屜符合 §5.2 列出的每一項。** 逐項判，任一項不符即 fail，並指出是哪一項：
      - (i) 上半部依序有：模型清單、「並排比較所有模型」、「歷史紀錄」標題與「每段對話各自獨立，不會互相影響」、「開始新的對話」、「搜尋對話內容」。捲動歷史列表時上半部不動，抽屜裡只有歷史列表可以捲動（歷史列表要長到需要捲動，這一項才判得出來）。
      - (ii) 三個入口都是點下去就動作的列，不是輸入框：「並排比較所有模型」進入比較畫面；「開始新的對話」開一段新的對話，人格與模型不變；「搜尋對話內容」進入搜尋畫面。三者點下去抽屜都關閉。

        - **(v3.17 補寫) 省略號兩個方向都要看，而且長句要用對的測資**：造一段第一句與最後一則都是**很長的英文句子**的對話（例如 `this is a very long first sentence used as a title that should not fit on one line at all`）→ 標題與預覽都看不到整句，**尾端都看得到「…」**；另一段第一句與最後一則都是**短到整句顯示得完的句子**（例如「你好」）→ 標題與預覽都是整句，**尾端都沒有「…」**。以截圖或畫面上的文字判定皆可，要看的是使用者看到的那一列。

      - **環境攔不到「回覆還在串流時切走」**（每一次的結尾都不是中斷標記）：可判定一記「本環境無法觀察」，**不得只寫這幾個字** —— 寫明試過的模型、提示、串流大約持續多久、每次切走花了多久。可判定二照判。
  8. 回歸：送出、串流、停止、刪除、切換人格 / 模型、冷啟動續接全部照常。

  3. 每一條配了正向對照的（任務 3 驗收 25、任務 5 驗收 8、任務 6 驗收 9、任務 7 驗收 11、任務 8 驗收 11、12），**正向與否定兩半都要被執行到**，不得只做否定那一半。
  4. **（v3.12 移除，編號保留不遞補。）** 原本要求：這些條文不得要求任何行為改變；若執行過程中有任何一條變紅，回報它、不要改條文去遷就實作。

      - **缺口，誠實寫**：沒有任何一條驗收在檢查「有沒有人為了讓某條通過而改了條文」。**這與任務 11 那兩條是同一個知情取捨。**
  5. **（v3.11 移除，編號保留不遞補。）** 原本要求：本任務不改動在 v3.5 補掃之前就已經存在的那些驗收條文的要求。**移除理由**：那是 v3.5 那一輪的範圍界線，已經過去；而本輪正是一次刻意的、經使用者裁決的全面重掃，那條界線若留著會與本輪的事實矛盾。

## 任務 15：`docs/product/features.md` 指向本規格的引用仍然追得到

- **說明**：那份產品功能清單的用途是「**從一個功能追到它的規格**」—— 使用者、QA、RD 看到某一項功能出問題時，照那一欄跳過來判對錯。v3.12 把那些引用改成「slug 目錄 + 檔名 + 節號 + 節名」的寫法，**但沒有任何一條驗收在問它們對不對**；有人改壞了不會有人發現。這個任務補的就是那個洞。
  - **為什麼選「補一條驗收」而不是「寫進明確不做」**（本輪要在兩者之間選一個）：**這件事說得出使用者後果** —— 節名 grep 不到、或節號落在一個講別件事的節上時，讀的人**追不到規格**，而追不到的時候他手上正好有一個要判對錯的問題。既然說得出後果，依准入判準它就該是驗收條文，不是一句「我們知道有這個缺口」。
  - **成本已經量過**：本任務全部靠 grep，不需要建置、不需要裝置。
  - **這個任務每一輪都要做。** 它守的東西會因為**別人在別輪改寫本規格的節名**而壞掉，而那正是不會有人回來通知的那一型。
  - **範圍只到「指向本規格的引用」。** 那份文件裡也有指向別輪 spec 的引用，**不歸這裡**（見「明確不做」）。
  - **這個任務守的不是 §1–§9 的任何一條規則，這是刻意的**：它守的是**文件之間追不追得到**，而那不是產品行為，寫不進行為規格。**它仍然通過「每一條驗收都要指得出它守的規則、而那條規則要說得出使用者會遇到什麼」那把尺** —— 那把尺真正在問的是**被違反時使用者會遇到什麼**，這裡答得出來（追不到規格）。**任務 10 是同一個形狀的既有前例**（它守的是 `plan/architecture.html`，也不對應 §1–§9 的任何一條）。
- **對應功能模組**：文件
- **驗收標準**：
  1. **每一處都追得到。** 把 `docs/product/features.md` 裡每一處路徑含 `docs/specs/conversation-search/` 的引用列出來（含同一格裡有多個節號的情形，逐個算一處）。對每一處，到本規格**版號最大的那個版號目錄**底下、該引用寫出的那一份檔案裡，判三件事：(i) 它寫的**節號存在**；(ii) 它寫的**節名在該檔案裡 grep 得到**；(iii) 節號與節名**落在同一節**。
      - **三件事任一不成立即 fail**，並指出是哪一列（用 `features.md` 的編號，例如 `搜尋-13`）、對不上的是節號、節名、還是兩者指到不同的節。
      - **不必判「這一列指得對不對題」** —— 那是內容判斷，不在本條範圍內；本條只問「指過去找不找得到」。
  2. **正向對照：不得靠把引用刪光而通過。** 下面三列的「對應 spec」欄必須**仍然帶著指向本規格的引用**，不得改成「尚無 spec」、也不得留空 —— `搜尋-02`、`搜尋-13`、`搜尋-20`。
      - **這一條獨自抓得到什麼**：驗收 1 只問「留下來的那些指得對不對」，**把引用全部刪掉或全部改寫成「尚無 spec」，驗收 1 會全數通過**。這一條擋的就是那個。
      - **為什麼可以指名這三個編號**：`features.md` 自己寫著「編號一旦給出去就不會再動」（見該檔／「編號怎麼看」），所以編號是穩定的指法；而這三列對應的是本規格三條使用者裁決過的核心規則（即時無送出鈕、只有訊息本文參與比對、查詢欄位裡留下什麼）。
  3. **不得指進版號目錄。** 每一處引用的路徑都是 `docs/specs/conversation-search/<檔名>`，中間**不含版號目錄**（形如 `v3.13/`）。任一處含版號目錄即 fail。

## 任務 17：抽屜標題／預覽截短不得把一個字切成兩半（v3.19 新增，bug 修正）

- **說明**：
  - **現象與重現**：見 `docs/specs/drawer-cut-splits-emoji/findings.md`「現象」「重現步驟」。摘要：一段對話的最後一則訊息，截點剛好落在 🌧 的兩個 code unit 中間，抽屜那一列的預覽是落單的高位代理（U+D83C）接「…」。使用者看到一個壞掉的字；uiautomator 在那一列出現在畫面上時整個崩潰。
  - **機制（PM 讀過程式碼確認）**：標題與預覽超過上限時，以 UTF-16 code unit 截取再補「…」，沒有檢查截點是不是落在一個字的兩半之間。v3.16 補「…」之前同樣會留下落單代理，只是後面沒有接「…」。
  - **這是不是 bug**：**規格從來沒規範過**（`spec.md` §5.2 只寫單行、超出以省略號截斷）。本輪在 §5.2 補上「截短不得把一個字切成兩半」，這個任務照那一項修。為什麼當初會漏、同一類的洞還有沒有，寫在 `spec-appendix.md`／決策歷程。
  - **修正範圍，修到哪裡算修好**：抽屜標題與預覽在截短時不再把一個字切成兩半（`spec.md` §5.2 的定義；v3.20 起含組合 emoji），其餘一切不變。具體來說，**截點不在一個字中間時，截出來的文字不因這次修正而改變**；上限的數字、換行換成空白、「還沒說話」、有截才補「…」都不動。截點遇到一個字時，要往前退還是往後把整個字包進來，由 RD 決定；使用者看不出差別，規格不規定。
    - *為什麼「截點不在中間時不變」寫在這裡、不寫成驗收*：寫成驗收就要把上限的數字寫進規格，而 v3.17 刻意沒寫（那兩個數字使用者感受不到）。**RD 若認為上限或截法本身該改，那是另一件事，寫進收件匣，不要在這個任務裡順手做。**
  - **不在範圍內**：搜尋片段的截短（v3.20 起由任務 18 處理，用同一個「一個字」）；驗收裝置不認得的較新 emoji（見「明確不做」）；標題／預覽改用搜尋的整形（見「明確不做」裡「對話標題 / 預覽的攤平規則與搜尋不同，不統一」）。
  - **（v3.20）決策 M 已拍板為 (c)**：驗收 6、7 補上。**驗收 1–5 仍然有效、不必改寫**：它們是 (c) 的下限；改成以一個字為單位時實作會換掉，這五條照判。斷字結果不一致時兩層各判什麼，見 `spec.md` §4.4「片段不得把一個字切成兩半」。
  - **可驗證性要求**：驗收 1–3 要求不需要裝置就能跑的測試。本專案沒有裝置端測試；若 RD 想改成完全交給畫面截短、使這些測試寫不出來，**先寫進收件匣**（建議見 `spec-architecture.md` §H.1）。
- **對應功能模組**：聊天狀態（對話的標題與預覽）、畫面切換點（抽屜那一列怎麼顯示）
- **驗收標準**：
  1. **重現案例成為永久測試。** 一支不需要裝置、每次跑單元測試都會執行的測試，標題、預覽各一個案例，**測資必須讓截點真的落在一個 emoji 的兩個 code unit 中間**。
      - **測資性質**：原文長到一定要截，而且沒有保護的截法會在截點留下一個高位代理。以現行上限（標題 26、預覽 40 個 code unit）為例，可用的形狀是：標題用「第一則使用者訊息 = 25 個 BMP 字 ＋ 🌧 ＋ 任意尾巴」，預覽用「最後一則訊息 = 39 個 BMP 字 ＋ 🌧 ＋ 任意尾巴」。**上限若改了，形狀跟著改，性質不變。**
      - **預期（都要斷言）**：標題與預覽逐碼位讀出來，**任何位置都沒有落單的代理字元**；**尾端是「…」**；「…」前面那一段是原文的開頭一段，而且**那個 emoji 之前的字全部都在**。
      - *正向那一半不得省略*：只斷言「沒有落單代理」的話，一個回傳空字串或把整個 emoji 之前的字也一起丟掉的實作也會通過。
      - *這一條獨自抓得到什麼*：截點落在 emoji 中間時留下半個字，也就是這個 bug 本身。**把保護拿掉（直接以 code unit 截），這兩個案例必須變紅**；做不到，就代表測資沒有碰到截點。
  2. **剛好放得下的 emoji 不截、不補「…」（不經過裝置）。** 一句話的長度剛好等於上限，而最後一個字是 emoji（以現行上限為例：標題 24 個 BMP 字 ＋ 🌧，共 26 個 code unit）→ 標題是整句、emoji 完整、尾端**沒有**「…」。預覽同理。
      - *這一條獨自抓得到什麼*：修的時候把判斷「要不要截」的界線弄錯，例如看到最後一個字是 emoji 就先退一格，於是一句整句放得下的話被截短並補上「…」。使用者會以為後面還有字。
  3. **不得修過頭（不經過裝置）。** 同一組測試裡，下面幾件事都要成立：
      - 一句長到一定要截、截點附近沒有 emoji 的一般文字 → 尾端有「…」；一句長度剛好等於上限的一般文字 → 整句、沒有「…」。
      - 含換行的文字 → 換行變成空白（仍是單行）；含 U+3000 的文字 → U+3000 原樣保留，**沒有被收成半形空白**（標題與預覽不套用搜尋的整形）。
      - 沒有任何使用者訊息的對話 → 標題是「還沒說話」。
      - *這一條獨自抓得到什麼*：修同一段程式時把旁邊的行為改壞。例如為了處理 emoji 改寫截短時丟了「有截才補『…』」，或順手改用搜尋的整形把 U+3000 收掉。驗收 1、2 只看 emoji 截點，看不到這些。
  4. **在裝置上：抽屜那一列看不到壞掉的字。** 把一段形狀同驗收 1 的對話放進對話所在的目錄（它不能是目前開著的那段），打開抽屜：
      - 那一列的標題、預覽尾端是完整的字接「…」，沒有方框、問號這類壞掉的字；emoji 之前的字都在。以逐碼位讀取節點文字或截圖判定。**若讀取畫面的工具在那一列可見時崩潰（例如 logcat 出現 `Bad surrogate pair`），即為 fail 的證據。**
      - *這一條獨自抓得到什麼*：畫面顯示的不是修好的那個字串。例如截短被搬到別處、或畫面另外又截了一次。
      - 環境做不出「把檔放進對話所在的目錄」時，記「本環境無法觀察」並寫明原因；語意由驗收 1、2 承接。
  5. **在裝置上：省略號兩個方向沒有被改壞。** 同一次操作裡，第一句與最後一則都是很長的英文句子（例如 `this is a very long first sentence used as a title that should not fit on one line at all`）的對話 → 標題與預覽尾端都看得到「…」；都是短到整句顯示得完的句子（例如「你好」）的對話 → 整句、尾端沒有「…」。
      - 與任務 6 驗收 1 (iii)、任務 9 驗收 5 重疊，**是刻意的**：每一個任務都要能單獨跑完，而這個任務動的正是那一段。
  6. **(v3.20 依使用者裁決（決策 M 選 (c)）補上) 組合 emoji 不被切開（不經過裝置）。** 三類字各一個案例，標題與預覽各做一次：ZWJ 序列（👨‍👩‍👧）、國旗（🇹🇼）、帶膚色的 emoji（👍🏽）。**測資必須讓截點落在那一個字裡、而且不在任何一對代理字元中間**，所以只保護代理字元的做法照不出來。
      - **可用的形狀**（以現行上限為例；上限改了形狀跟著改，性質不變）：標題用「第一則使用者訊息 = 24 個 BMP 字 ＋（👨‍👩‍👧、🇹🇼 或 👍🏽）＋ 任意尾巴」，預覽用「最後一則訊息 = 38 個 BMP 字 ＋（同上）＋ 任意尾巴」。截點落在那個字的第一個 code point 之後。
      - **預期**：尾端是「…」；「…」前面是那 24（或 38）個 BMP 字接**完整的那一個字**，**或者**只有那 24（或 38）個 BMP 字。**不得只剩 👨、🇹、或沒有膚色的 👍。** 預期要直接寫在測試裡，不得用被測的同一份斷字去算（`spec.md` §4.4）。
      - **前面那個字也要在**：另一個標題案例用 21 個 BMP 字 ＋ 👍🏽 ＋ 👨‍👩‍👧 ＋ 任意尾巴 →「…」前面至少有那 21 個 BMP 字接完整的 👍🏽。
      - **剛好放得下的組合 emoji**：第一句是 18 個 BMP 字 ＋ 👨‍👩‍👧（共 26 個 code unit）→ 標題是整句，尾端沒有「…」。預覽同理（32 個 BMP 字 ＋ 👨‍👩‍👧）。
      - **極端輸入**：第一句是「e」後面接 40 個 U+0301（組合重音符號）再接幾個字 → 標題**不得只剩「…」**，必須完整含有「e」與那 40 個 U+0301。預覽同理（最後一則訊息，接 60 個）。
      - *正向那一半不得省略*：只斷言「不得只剩 👨」的話，一個把標題截成空字串的實作也會通過。
      - *這一條獨自抓得到什麼*：只保護代理字元的實作，也就是 v3.19 下限的做法。**把以字為單位的保護拿掉、只留代理字元的保護，三類字的案例必須變紅。** 三類各一個，是因為它們在 UAX #29 裡由不同的規則黏在一起，只處理其中一類的實作會漏掉另外兩類。「前面那個字也要在」抓往前退過頭；「剛好放得下」抓看到結尾是組合 emoji 就先退；「極端輸入」抓一律往前退、把整句退光。
  7. **(v3.20 新增) 在裝置上：抽屜那一列的組合 emoji 是完整的。** 把兩段對話放進對話所在的目錄（都不能是目前開著的那段）：一段的第一句是驗收 6 的 👨‍👩‍👧 標題形狀，另一段的最後一則是驗收 6 的 🇹🇼 預覽形狀。打開抽屜：
      - 標題「…」前面不是落單的 👨，預覽「…」前面不是落單的 🇹；兩者都是驗收 6 預期的其中一種。以逐碼位讀取節點文字判定；只能看截圖時，看得出來的照判，看不出來的記「本環境無法觀察」。
      - **與驗收 6 的預期不同即 fail**，即使驗收 6 的測試是綠的（`spec.md` §4.4：斷字結果不一致時以裝置為準）。報告寫明讀到的碼位。
      - *這一條獨自抓得到什麼*：跑測試的環境與裝置斷字結果不一致。驗收 4 只看代理字元，照不出組合 emoji。
      - 環境做不出「把檔放進對話所在的目錄」時，記「本環境無法觀察」並寫明原因。**這時裝置那一層這一輪沒有判到**，報告要明講，不得寫成 pass。

## 任務 18：搜尋片段不得把一個字切成兩半（v3.20 新增，依決策 M 選 (c)）

- **說明**：
  - **使用者裁決（決策 M 選 (c)）**：搜尋片段與抽屜標題／預覽用同一個「一個字」。`spec.md` §4.4 從「不得從 surrogate pair 中間切開」升級成「片段不得把一個字切成兩半」。
  - **這是不是 bug**：**不是，是規格升級。** 現行片段只保證不留半個 code point，那正是舊的 §4.4。從現在起，它在組合 emoji 上的行為（例如片段以 ZWJ 開頭、結尾只剩 👨）不符合規格。
  - **修正範圍，修到哪裡算修好**：只改「§4.2 算出來的起點或終點落在一個字中間時怎麼移」。什麼算命中、60 與 20、省略號、標示區間、整形與折疊**一律不動**。**使用者知情接受這是修過頭風險最高的選項**：同一段程式同時決定視窗與標示（§4.2–§4.6），所以驗收 3 把那幾條在 BMP 測資上的結果再驗一次。
  - **不在範圍內**：命中落在一個字中間時的標示（例如查 👨 命中 👨‍👩‍👧 的第一個人）；60／20 改成以字計；驗收裝置不認得的較新 emoji。三者都在「明確不做」。
  - **為這次查證過的事實**：`java.text.BreakIterator` 從 JDK 20 起才依 UAX #29 的延伸字位叢集斷字，之前的版本大多只在 code point 邊界斷（JDK 20 的 release note，JDK-8291660）；Android 上同名的 API 由 ICU 實作。**本規格沒有查證這個專案跑單元測試時用的是哪一版 JDK。** 這是「跑測試的環境與裝置斷字不一致」的一個具體來源，也是驗收 1 要求把預期直接寫在測試裡的原因。怎麼切出一個字由 RD 判斷，但比對純邏輯仍不得依賴 Android（任務 2 驗收 1）；若判斷需要引入新的相依，先寫進收件匣。
  - **斷字結果不一致時兩層各判什麼**：`spec.md` §4.4「片段不得把一個字切成兩半」。驗收 1–4 是不經過裝置的那一層，驗收 5 是裝置那一層。
  - **可驗證性要求**：驗收 1–4 要求不需要裝置就能跑的測試，理由同任務 3 的說明。
- **對應功能模組**：比對純邏輯（片段怎麼裁）、搜尋畫面（命中列怎麼顯示）
- **驗收標準**：
  1. **起點落在一個字中間（不經過裝置）。** 三類字各一個案例：ZWJ 序列（👨‍👩‍👧）、國旗（🇹🇼）、帶膚色的 emoji（👍🏽）。**測資必須讓 §4.2 算出來的起點落在那一個字裡、而且不在任何一對代理字元中間。**
      - **可用的形狀**（查詢「kiwi」）：👨‍👩‍👧 → 5 個「甲」＋ 👨‍👩‍👧 ＋ 14 個「乙」＋ kiwi ＋ 50 個「丙」（起點想從索引 7 開始，那是家庭裡第一個 ZWJ）；🇹🇼 → 5 個「甲」＋ 🇹🇼 ＋ 18 個「乙」＋ kiwi ＋ 50 個「丙」（索引 7 是 🇼 的開頭）；👍🏽 → 5 個「甲」＋ 👍🏽 ＋ 18 個「乙」＋ kiwi ＋ 50 個「丙」（索引 7 是膚色符號的開頭）。
      - **預期（每個案例都要斷言）**：片段以「…」開頭；「…」之後是**完整的那一個字**接那一串「乙」，**或者**直接從第一個「乙」開始，兩者擇一，看 RD 往哪邊移；片段完整含有「kiwi」，標示恰好蓋住「kiwi」。
      - **預期要直接寫在測試裡**（例如把兩種可接受的片段字串都寫出來），**不得用被測的同一份斷字去算**。
      - *正向那一半不得省略*：只斷言「不以 ZWJ／🇼／膚色符號開頭」的話，一個回傳空片段、或把引子整個丟掉的實作也會通過。
      - *這一條獨自抓得到什麼*：只保護代理字元、沒有以字為單位的實作 —— 片段開頭會是 ZWJ 接 👩‍👧、落單的 🇼、或落單的膚色色塊。**把以字為單位的保護拿掉、只留代理字元的保護，這三個案例必須變紅。** 三類各一個的理由同任務 17 驗收 6。
  2. **終點落在一個字中間（不經過裝置）。** 同樣三類字各一個案例，**測資必須讓 §4.2 算出來的終點落在那一個字裡、而且不在任何一對代理字元中間。**
      - **可用的形狀**：30 個「甲」＋ kiwi ＋ 34 個「乙」＋（👨‍👩‍👧、🇹🇼 或 👍🏽）＋ 30 個「丙」。起點是索引 10，終點想在索引 70 結束，而索引 70 落在那個字的第一個 code point 之後。
      - **預期**：片段以「…」結尾；「…」之前是**完整的那一個字**，**或者**是它前面的最後一個「乙」；片段完整含有「kiwi」，標示恰好蓋住「kiwi」。預期的寫法同驗收 1。
      - *這一條獨自抓得到什麼*：只處理起點那一側的實作，片段結尾會是 👨、🇹、或沒有膚色的 👍。**只讓終點那一側的保護失效時，只有這一條變紅，驗收 1 不變紅。**
  3. **不得修過頭（不經過裝置）。** 同一組測試裡，下面幾件事都要成立：
      - **截點本來就在兩個字之間時不移動**：起點方向用 3 個「甲」＋ 👍🏽 ＋ 👍🏽 ＋ 16 個「乙」＋ kiwi ＋ 50 個「丙」→ 片段是「…」＋ 第二個 👍🏽 ＋ 16 個「乙」＋ kiwi ＋ 後面的字 ＋「…」（起點就是索引 7，不往前多包第一個 👍🏽，也不往後丟掉第二個）。終點方向用 30 個「甲」＋ kiwi ＋ 32 個「乙」＋ 🇹🇼 ＋ 🇯🇵 ＋ 30 個「丙」→ 片段結尾是完整的 🇹🇼 接「…」（終點就是索引 70，落在兩面國旗之間）。
      - **§4.2 的三條界線不變**：`spec.md` §4.2 那三條可判定（L = 59／60／61，只用 BMP 字元）的片段與標示，與該節寫的預期輸出完全相同。
      - **§4.3 不該補的不補**：整則放得進視窗的短訊息，片段前後都沒有「…」。
      - **下限仍成立**：連續 15 個單一 emoji 的起點形狀、連續 20 個單一 emoji 的終點形狀（`spec.md` §4.4 的下限那一條）→ 片段頭尾沒有落單的代理字元，而且完整含有查詢詞。
      - *這一條獨自抓得到什麼*：修的時候把旁邊的行為改壞。例如把一整串相鄰的 emoji 當成一個字而多移、把相鄰兩面國旗的區域指示符號配錯對、或改寫視窗時弄壞了 60／20 的界線或省略號。驗收 1、2 只看落在一個字中間的截點，看不到這些。
  4. **一個字長到視窗裝不下（不經過裝置）。** 100 個「甲」＋「e」後面接 80 個 U+0301（組合重音符號）＋ kiwi ＋ 30 個「丙」，查「kiwi」。§4.2 算出來的起點落在那個長字的中間，而那個字比整個視窗還長。
      - **預期**：片段**不為空**，**含有命中起點那個字「k」**（`spec.md` §4.4 的極端輸入那一條要求的就是這個字），而且沒有把那個長字切成兩半（片段裡要嘛完整含有「e」與 80 個 U+0301，要嘛完全沒有它們）。片段長度不判。
      - *這一條獨自抓得到什麼*：起點與終點都往前退的實作。在這個形狀上，它會把片段退成空的、或只剩那個長字而看不到命中。使用者會看到一列沒有命中字的結果。
  5. **在裝置上：搜尋命中列上看到的是完整的字。** 把一段對話放進對話所在的目錄，其中兩則訊息分別是驗收 1 的 👨‍👩‍👧 形狀與驗收 2 的 🇹🇼 形狀。進入搜尋，查「kiwi」：
      - 起點形狀那一列，「…」之後不是 ZWJ 或 👩；終點形狀那一列，「…」之前不是落單的 🇹。兩者都是驗收 1、2 預期的其中一種。**以逐碼位讀取命中列的文字判定**；只能看截圖時，看得到的那一端照判，被單行省略遮住的那一端記「本環境無法觀察」。
      - **與驗收 1、2 的預期不同即 fail**，即使驗收 1、2 的測試是綠的（`spec.md` §4.4：斷字結果不一致時以裝置為準）。報告寫明讀到的碼位。
      - *這一條獨自抓得到什麼*：跑測試的環境與裝置斷字結果不一致，或畫面另外又截了一次。驗收 1–4 在不經過裝置的環境跑，照不出這兩種。
      - 環境做不出「把檔放進對話所在的目錄」、或輸入框送不進「kiwi」時，記「本環境無法觀察」並寫明原因。**這時裝置那一層這一輪沒有判到**，報告要明講，不得寫成 pass。

## 任務 19：`docs/product/features.md` 的「未經查證」不綁死在某一種驗收裝置上（v3.22 新增）

- **說明**：那份產品功能清單裡「「※未經查證」是什麼意思」那一節，原本寫著這份文件「**沒有實機跑過**」。**驗收環境 2026-09-16 起改用模擬器**，那句話會讓讀的人以為**在模擬器上確認過的不算查證** —— 於是一個已經有人開 App 確認過的項目，標記永遠拿不掉；或有人為了清掉標記去湊一台特定型態的裝置。
  - **這件事說得出使用者後果**（標記的意思被讀錯 → 那份清單對「哪些還沒人確認過」的回答是錯的），所以依准入判準寫成驗收條文，不是一句「我們知道」。
  - **這個任務不改產品行為、不改任何一條規則**，只改那一節的措辭：**查證與否看的是「有沒有人實際開 App 確認過」，不看那是什麼裝置。**
  - **範圍只到那一節。** 那份文件裡別處若日後為了別的理由提到某種裝置，不歸這裡。
  - **它守的不是 §1–§9 的任何一條規則，這是刻意的** —— 和任務 10（守 `plan/architecture.html`）、任務 15（守那份清單指向本規格的引用）同一個形狀：守的是文件之間讀不讀得對，而那不是產品行為，寫不進行為規格。
  - **這個任務每一輪都要做**，成本是冷讀那一節（幾行字），不需要建置也不需要裝置。它會因為**別人在別輪改寫那一節、或驗收環境又換了一種型態**而壞掉，而那正是不會有人回來通知的那一型。
- **對應功能模組**：文件
- **驗收標準**：
  1. **那一節不以裝置型態界定「查證」。** 冷讀 `docs/product/features.md` 標題為「「※未經查證」是什麼意思」的那一節，回答一個問題：**「某一項如果有人在模擬器上開 App 確認過，它算不算已經查證？」**
      - **該節必須給得出答案，而且答案必須是「算」。** 答案是「不算」，或該節寫得讓人讀不出答案（例如只說這份文件「沒有實機跑過」、再沒有別的說明），即 **fail**，並引出該節裡造成這個讀法的那一句。
      - **不用 grep 某幾個詞來判，也不禁止任何字詞出現**：一句「不論實體手機或模擬器都算」同時提到兩種裝置，卻正是本條要的結果。**禁止字詞會把正確的寫法判成 fail** —— 這份規格撞過同型（條文描述的形狀與正確實作的形狀對不起來，見 `spec-appendix.md`／決策歷程）。
      - **不限制整份文件**：別的節若為了別的理由提到某種裝置，不在本條範圍內。
  2. **正向對照：不得靠刪掉那一節而通過。** 該節必須仍然存在，而且仍然說出兩件事：(i) 標了 `※未經查證` 的項目是**還沒有人實際開 App 確認過**的；(ii) 沒標的那些是怎麼來的（讀程式碼與既有文件寫出來的）。**以意思判，不以字面判**；少任一件即 fail，並指出少的是哪一件。
      - **這一條獨自抓得到什麼**：**把整節刪掉，驗收 1 會空過** —— 沒有那一節，也就沒有任何一句話會讓人讀出「模擬器上確認過的不算」。那時讀者看到 `※未經查證` 這個標記，無從知道它是什麼意思，也不知道要做什麼才能拿掉它。

**橫向 + 鍵盤彈出時，結果區幾乎沒有空間。** 實測橫向且鍵盤彈出時可視區只剩約 100px，只看得到摘要那一行。這是 §7 的成因在橫向的重演，但**不是同一個嚴重度**：原本的問題發生在直向（主要使用方向）且結果完全不可達；橫向下使用者仍可捲動或收鍵盤看到結果，而且手機橫向打字時鍵盤佔掉大半螢幕是所有 App 的共同狀況。
→ 觸發：使用者回報「橫向搜尋不能用」，或這個 App 要支援平板 / 折疊機（橫向變成主要方向）。**最便宜的第一步是橫向時不畫摘要行**，但那是屆時的設計決定，不在這次定案。

**對話標題 / 預覽的攤平規則與搜尋不同，不統一。** 那兩個既有屬性只換掉換行字元，不收合連續空白、不處理 tab 或 U+3000。所以同一則訊息在歷史列表預覽與搜尋片段裡，空白呈現可能略有不同（例如標題顯示「北京(U+3000)天氣如何」而搜尋片段顯示「北京(U+0020)天氣如何」）。
→ 這次不動的理由：它們不參與比對（§1.2），改了等於在這次的改動裡混入無關的顯示變更。
→ 觸發：這兩者要被拿來互相對照時（例如搜尋結果改用標題當標頭）。

**對話存取層沒有自動化測試。** 可接受的前提正是「它沒有邏輯」（建議見 `spec-architecture.md` §E.3）。抽介面 + 假實作只能斷言「轉發有沒有呼叫對」，對零邏輯的類別是過度設計；裝置端測試可行但會開先例。
→ 觸發：這一層開始有邏輯的那一天。**裝置端測試是它未來唯一合理的自動化形式。**

**（v3，v3.1 改寫）摘要的兩個數字與「還有 N 則符合」都留在畫面上自己算，本輪不搬。** 摘要那兩個數字是使用者知情裁決保留重複；「還有 N 則符合」的減法本來就只有一處定義，搬它是為了對稱而不是為了解決問題。
→ 觸發：見附錄／已知取捨與風險「摘要的兩個數字保留了兩份寫法」那一條的觸發條件。

**（v3.12，內容原封來自任務 11 被移除的驗收 1 與 4）比對層那兩個派生的量：留著，也不要順手改用它們。** 這是使用者一次裁決劃出的範圍界線（他在知道「保留 method 卻不用它，重複依然存在」這個代價之後選了 (c)：就只是留著、不動 UI）。要保留的三件事：
- **那兩個派生的量是知情保留的，不是沒清乾淨。**
- **不要順手刪掉它們，也不要順手把畫面改成呼叫它們** —— 那兩件事正是使用者在看過代價之後決定不做的（選項 (a) 與 (b)，他選 (c)）。
- **想收斂就走 `spec-decisions.md` 重開一次**，不要在別的輪次順手做掉。**這道門要留著。**

**代價，誠實寫**：**這件事從 v3.12 起沒有任何一條驗收每輪去檢查它了。** 條文原本在任務 11（驗收 1、4），本輪依使用者裁決移出 —— 它們照字面說不出使用者後果。**使用者要的是「驗收條文裡不留追溯不到使用者後果的東西」，不是「這個決定可以被忘記」**，所以它搬到這裡，而不是消失。
→ 觸發：任一成立就該回頭讀這一條與附錄／已知取捨與風險「摘要的兩個數字保留了兩份寫法」那一條 —— (a) 有人主張刪掉那兩個量或讓畫面改用它們；(b) 摘要顯示的數字與畫面上實際列出的內容出現不一致。

**（v3.12，內容原封來自任務 14 被移除的驗收 4）任務 14 的核對不得要求任何行為改變。** 它做的是「條文 → 測試」的覆蓋核對，不是改實作的授權。**若核對過程中有任何一條變紅，那代表發現了一個既有缺陷 —— 回報它，不要改條文去遷就實作**（§4.2 的 off-by-one 就是這樣被抓到的）。
- **為什麼它從驗收搬到這裡**：它問的是「這個任務的範圍到哪裡、變紅時該怎麼辦」，不是「系統必須是什麼樣」；冷讀時它答不出「被違反時使用者會遇到什麼」。
- **代價**：**沒有任何一條驗收在檢查它。** 與上面那條是同一個知情取捨。
→ 觸發：真的發生一次「條文被改成遷就實作」—— 屆時要補的是**那個被放掉的行為**的條文，而不是把這句話加回驗收清單。

**（v3.12）不回頭替這份 spec 內部的每一處引用補上節名。** 從 v3.12 起，**跨文件的引用**寫成「slug 目錄 + 檔名 + 節號 + 節名」（見 `spec.md` 的檔案地圖），**本輪新寫的文字都照它寫**；但這五份檔案裡既有的內部引用（形如「§2.11」「任務 8 驗收 5」）有數百處，本輪不逐處補節名。
- **理由**：它們指的是**同一個版號目錄裡的同一份檔案**，節號指錯時 grep 得到旁證的成本很低；而一次改數百處會製造數百個新的可出錯點，那正是這份 spec 反覆記錄的失效模式。**這是編輯取捨，不是說那些引用不會腐爛。**
- **它的殘留風險**：spec 內部若日後又搬動一條規則的編號，指向它的內部引用會**靜靜地指到別的節**（節號指錯是靜靜失敗，這正是決策 H 要防的事）。
→ 觸發：真的發生一次「內部引用指到一個存在、但講的是別件事的節」；或有人要求全面補齊 —— 那是一次獨立的整理，不要混在別的輪次裡順手做。

**（v3.13）`docs/product/features.md` 裡指向 `stop-generation` 那一輪的引用，不由本規格的驗收守。** 任務 15 的範圍只到「指向本規格的引用」。
- **理由**：那些引用指的是另一輪的規格，**判它們對不對要拿那一輪的定版來對** —— 由本規格立一條驗收去管別人的節名，等於替另一輪決定它的驗收該長什麼樣，而那一輪隨時可能改寫自己的節。**這是分工，不是漏掉。**
- **代價，誠實寫**：那份文件是**跨 slug 的單一份文件**，v3.12 一次把兩邊都改了；但**從此只有一半有驗收在守**。另一半壞掉時，本規格的 QA 照任務 15 走不會碰到它。
→ 觸發：那一輪自己補上等價的驗收（屆時這條就結束了）；或有人回報 `features.md` 裡指向那一輪的某個節名 grep 不到 —— 那時要做的是**把事實寫進那一輪的收件匣**，不是在本規格擴大任務 15 的範圍。

**（v3）不新增「最後開啟時間」這第二個時間概念。** 決策 A 已裁決 (a)：系統裡只有一個時間，語意是「內容最後一次改變」（§8.1）。
→ 觸發：使用者回報「我找不到剛才看過的那段對話了」。屆時要做的是明確地新增第二個時間概念（各自儲存、各自命名、各自顯示），**不是**讓現在這個時間退回去被閱讀行為推動。

**（v3）尾端空白的移除只綁在「失去焦點」，不追加其他時機**（例如按下鍵盤上的搜尋鍵、或閒置幾秒後）。使用者裁決講的就是失焦。
→ 觸發：使用者回報「打完字空白一直留著很奇怪」。

**（v3，v3.11 從架構決策 §G.3 搬進來）時間戳這件事只改「寫下去的時間值怎麼來」，不改「什麼時候寫檔」。**
- **理由**：切換對話時把當前對話存起來是既有的正確行為 —— 它保住了尚未落盤的內容。修 bug 最常見的災難是修過頭：動到存檔時機會影響一條與搜尋無關、而且正在正常運作的路徑。**修正範圍的邊界就在這裡**，由任務 13 驗收 7 守。
- **另一輪確實跨過了這條線，而兩邊的說法對得起來**：`stop-generation` 要動的存檔時機恰恰是那條**沒有在正常運作**的（按下停止那一次根本沒寫檔），而這條線保護的那條（切換對話時的存檔）該輪明文排除、並且另有驗收專門守住不動到它。兩輪加起來，「什麼時候寫檔」只被改了一處。
→ 觸發：有人要動「切換 / 切人格 / 送出後收尾」這三個既有的存檔時機。

**（v3.2 列出、v3.6 使用者已裁決）不把「規格裡引用既有函式／環境行為的宣稱都必須有測試釘住」升格成硬性條文。**
- **現行結論（v3.6，使用者裁決）：不升格。** 分工是：**規則**由「條文 → 測試」與「規則 → 條文」兩個方向守（那兩條通則的權威在 PM 的角色定義裡）；**規則之間的衝突**由 QA 反應、PM 判斷、必要時升級給使用者。也就是說這一型交給那條升級路徑，不另外用條文去防。**這個分工本身就是裁決的理由。**
- **一併更正一個計次（v3.6）**：v3.5 這條寫著「這是**第三次**出現同型」，**那個計次是錯的，它把兩種不同的東西數在一起**：
  - **A 型（理由錯了、規則沒事）：2 次** —— 輸入法打不出 U+3000、Kotlin 內建 trim 的空白集合。兩次都只更正文件，產品毫髮無傷。
  - **B 型（前提錯了、規則因此自相矛盾）：1 次** —— §8.2 第三點讓 §8.1 與 §8.2 對同一個動作給出相反答案。**這是 B 型的第一次，不是同型的第三次。**
- **什麼時候該回來重看**：**B 型再發生一次**，而且那一次是在「QA → PM → 使用者」這條升級路徑**沒有把它接住**的情況下被發現的。

**（v3.7 列出、v3.11 更新現行結論）這份 spec 不自己登記檔案的基準雜湊。**
- **現行結論（v3.11）**：**這一題的原始理由已經消失。** 它原本是「一字未改」類條文的補丁 —— 而那七條已在本輪整批處理掉（見任務 1、任務 9 的說明），因為**程式碼被動了而行為沒變，使用者什麼都感受不到**。
- **使用者已決定這個專案會接版本控制，但不是為了那七條** —— 那七條就算有版本控制也仍然答不出「使用者會遇到什麼」。**版本控制的理由換成純工程安全網**（本專案曾把一個含數十支測試的檔案誤寫成 0 bytes，靠反編譯 build 產物救回）。**這一點寫下來，是因為不寫的話，下一個讀附錄的人會以為版本控制是為了那七條。**
- **（v3.14）版本控制已經接上。** 上面的結論沒有因此改變。**它帶出的一件事要知道**：版本控制歷史的第一個版本就已經含搜尋功能，所以「跟加搜尋之前比」這種基準，用版本控制也拿不到（見 `spec-decisions.md`／決策 I）。
→ 觸發：有人主張要把「某個既有檔案未被改動」這一類條文加回 spec —— 屆時要先回答的是「它被違反時使用者會遇到什麼」，而不是「我們現在有沒有工具可以驗它」。
