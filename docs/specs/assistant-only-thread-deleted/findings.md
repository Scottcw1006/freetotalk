# 只含助理訊息的對話檔，打開再切走就被刪掉

> 階段 0 的產出（RD，2026-09-14）。**程式碼行號對應 commit `1a683d3`**，行號會隨改動飄移，要對照請用 `git show 1a683d3:<檔案>`。

---

# 現象

**使用者會遇到的**：手機上有一段對話檔，裡面只有助理說的話、沒有任何一句使用者說的話。從歷史清單或搜尋結果打開它，再切到別的對話（或換人格、換模型、開新對話），**那個檔就從手機上消失了**，而且沒有任何提示。

**發現者**：QA 驗 `conversation-search` v3.13（受測 commit `7b50b16`）時，用自己推進去的測資撞到。這是條文範圍外的觀察，**不是那一輪的回歸**。

**QA 的原始觀察（原樣保留，出處 `git show 59e596a:docs/specs/conversation-search/v3.13/test-report.md`「條文範圍外的觀察」）**：

> - 推入的「只含助理訊息」的對話檔（qa-onlybot），被從搜尋結果點開、之後再切到別段對話時，**整個檔被刪掉了**。它被讀成空白對話，切走時的存檔依 §9.1「空白對話存檔等於刪檔」處理。
> - §6.1 自己寫著這種舊檔「會被讀成空白對話並進入歷史」，但沒有任何規則或驗收說「開啟再離開之後它還在不在」。
> - 若真實使用者有這種舊檔，開一次就會消失。本輪只影響測資；使用者原有資料經雜湊確認完全還原。

---

# 重現步驟

1. 在 App 的對話資料目錄放一個對話檔，`messages` 裡**只有 `author: "Assistant"` 的訊息**（id 與目前開著的那段不同）。
2. 冷啟動 App，打開歷史抽屜，點那一列（或在搜尋畫面搜它裡面的字，點那一筆）。畫面換成那段對話。
3. 切走：點抽屜裡另一段對話，或「開始新的對話」，或「換人」，或換模型。
4. 看資料目錄：那個檔**不見了**。

**沒有競態，每次必中**，原因見診斷。

**RD 沒有在實機上親自重現。** 依據是 QA 在 Pixel 9 上的一次實際觀察（上面原文），加上下面這條每次都會走到的程式碼路徑。沒有自己重現，是因為這台裝置上有使用者的真實資料，而這個機制沒有時序或環境因素，自己再做一次換不到新資訊。

# 診斷

**一句話**：這種檔被讀進來時算「空白對話」；切走時 App 會先存當下開著的那段，而「存一段空白對話」的實作是**刪掉它的檔**。這條規則原本是為了「沒說過話的新對話不要留下空殼」，但它不分「本來就沒有檔」和「磁碟上本來就有一個檔」。

## 1. 只含助理訊息的對話會被判成空白

`app/src/main/java/com/example/demo/chat/Conversation.kt:40–41`

```kotlin
val isBlank: Boolean
    get() = messages.none { it.author == Author.You }
```

`Author` 只有 `You` 與 `Assistant` 兩種（同檔 :6）。所以不管助理說了幾句，只要沒有 `You`，就是空白。

## 2. 切換入口都會先存「當下開著的那段」

`app/src/main/java/com/example/demo/chat/ChatViewModel.kt`

| 入口 | 存檔 |
|---|---|
| `switchModel` | :120 `repository.save(_uiState.value.conversation)` |
| `switchPersona`（`startNewThread` :148 也走這裡） | :139 |
| `openThread` | :154 |

打開那個舊檔之後，它就是 `_uiState.value.conversation`。下一次任何切換，存的就是它。

## 3. 存一段空白對話＝刪掉它的檔

`app/src/main/java/com/example/demo/data/ConversationStore.kt:35–42`

```kotlin
suspend fun save(conversation: Conversation) = withContext(Dispatchers.IO) {
    // A thread the user never wrote in is noise in the history list.
    if (conversation.isBlank) {
        delete(conversation.id)
        return@withContext
    }
    ...
}
```

`delete` 在 :44–46 直接 `fileFor(id).delete()`。**沒有檢查這個檔是不是本來就在磁碟上、裡面有沒有東西。**

這個判斷從專案最早的快照（`706f93d`）就在了（`git log -S "conversation.isBlank" -- ConversationStore.kt` 只有這一筆）。

## 4. 這個 App 自己寫不出這種檔

- `ConversationStore.save` 本身就擋掉了空白對話的寫入（第 3 點），所以 App 寫出來的檔一定至少有一句 `You`。
- App 裡會把訊息從對話拿掉的只有兩處，拿掉的都是**助理的回覆**，不是使用者的訊息：`ChatViewModel.kt:315`（`filterNot { it.id == replyId }`）與 `:349`（`filterNot { it.id == streaming.id }`）。

所以這種檔只會從 App 以外來：測試推進去的資料、快照之前的舊版 App 寫的、或手動搬進來的。

## 5. 但規格明文承認這種檔存在

`docs/specs/conversation-search/v3.13/spec.md`：

- §6.1（:364）「一個只含助理訊息的舊檔會被讀成空白對話並進入歷史」，:365 還要求「點擊那一列必須切換到那段舊對話」。
- §9.1（:464）「儲存一段空白對話等於刪檔，不是寫檔。一段沒有任何使用者訊息的對話被『存起來』時，磁碟上不得因此多出一個檔。」

§9.1 的可判定只講「不得**多出**一個檔」，沒有講「本來就在的檔可不可以因此**少掉**」。§6.1 讓使用者點得進去，但沒有任何一條說點進去再離開之後它還在不在。

`docs/product/features.md` 保存-02「一句話都沒說過的對話**不會被存起來**，也不會出現在歷史清單裡」。這句跟現況也對不上：這種檔**會**出現在歷史清單裡（§6.1），只是一碰就沒了。

## 6. 目前真實資料的影響範圍

2026-09-14 在使用者的 Pixel 9 上**唯讀**檢查（`run-as` 逐檔讀、數作者），`files/conversations/` 底下 14 個對話檔**每一個都至少有一句 `You`**。**這台裝置目前沒有會被這個 bug 刪掉的真實資料。**

# 要不要 PM

**要。** 修法本身很小，但「什麼算對」有三個互相排斥的答案，每個的使用者後果都不同，而且都會動到 `conversation-search` 規格裡已經寫死的規則：

- **保留**：本來就在磁碟上的檔，打開再離開不得被刪（空白對話仍然不得「新增」檔）。對應要改的是 §9.1 的適用範圍。
- **不讓它出現**：讀取歷史時就把這種檔排除，使用者看不到也點不到。這會跟 §6.1 那條「必須切換到那段舊對話」直接衝突。
- **維持現狀**：認定這種檔不是 App 的合法資料，碰了就清掉。那要把這個決定寫進規格，並修正保存-02 的描述。

另外要回答的是**範圍**：`deleteThread`（使用者主動按垃圾桶）不在這個 bug 裡，保存-05 的「真的刪掉」必須不受影響。

**跟 `history-missing-after-switch` 不是同一個決定。** 那一個是兩個協程同時寫同一個檔的競態，問的是「存好的對話要在清單上看得到」；這一個問的是「空白對話的存檔可不可以刪掉已經存在的檔」。所以分開成兩輪。
