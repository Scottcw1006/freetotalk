# 現象

按下「停止生成」之後，兩件事沒有照預期發生。**兩者都是既有行為，不是任何一次改動造成的。**

## 一、部分回覆被錯誤訊息取代

停止之後，畫面上原本正在串流的那則回覆**整則變成**：

```
出錯了：StandaloneCoroutine was cancelled
```

已經生成出來的文字全部消失。使用者按停止的意圖是「就到這裡」，得到的卻是「這次失敗了」。

## 二、按停止的那一次不會存檔

停止之後那段對話**不會被寫進儲存體**。實測：一段有內容的對話（開場白 + 使用者訊息 + 回覆）在按下停止後，`files/conversations/` 的檔案數完全沒有增加。

內容仍在記憶體裡，所以畫面看起來正常；直到後續某個動作（切換對話等）才會被存下來。**如果在那之前 App 被關閉，那次對話就消失了。**

## 兩者的關聯

第一個 bug 讓第二個很難被發現：畫面上「有東西」（雖然是錯誤訊息），使用者不會懷疑它沒被存下來。

# 重現步驟

環境：Pixel 9、debug build、任一 persona。

1. 開一段新對話
2. 送出一則會產生較長回覆的訊息（例如 `tell me a long story about a cat`）
3. 回覆開始串流後 **3–5 秒內**按下輸入列右側的停止鈕（生成中該鈕會變成轉圈的停止鈕）
4. **現象一**：畫面上該則回覆變成「出錯了：StandaloneCoroutine was cancelled」
5. **現象二**：此時執行
   `adb shell run-as com.example.demo ls files/conversations | wc -l`
   檔案數與步驟 1 之前相同 —— 這段對話沒有被存檔
6. 切換到另一段對話，再數一次 —— 此時才會多一個檔案

**注意**：現象二的症狀是「什麼都沒發生」，不做步驟 5 的檔案數比對就不會發現它。

# 診斷

兩個現象出自同一段程式：`app/src/main/java/com/example/demo/chat/ChatViewModel.kt` 的 `send()`。

## 現象一

`stop()` 呼叫 `replyJob?.cancel()`。被取消的 coroutine 會拋出 `CancellationException`，而 `send()` 內的

```kotlin
} catch (e: Exception) {
    updateMessage(replyId, "出錯了：${e.message ?: e.toString()}", streaming = false)
}
```

**`CancellationException` 是 `Exception` 的子類別**，所以這個 catch 接住了它，把整則回覆覆寫成錯誤字串。`stop()` 自己做的「把 streaming 標記關掉」隨即被這次覆寫蓋過。

正常結束與被取消走的是同一條路，而程式沒有區分兩者。

## 現象二

同一個 `try` 的 `finally` 區塊裡呼叫

```kotlin
repository.save(_uiState.value.conversation)
```

`save()` 是 **suspend 函式**。在已被取消的 coroutine 裡，`finally` 區塊本身會執行，但其中的 suspend 呼叫會**立刻再次拋出 `CancellationException` 而不執行** —— 除非包在 `withContext(NonCancellable)` 裡。

所以按停止的那一次，存檔沒有發生。

# 要不要 PM

**需要，而且兩個 bug 應該在同一輪處理。**

PM 要回答的是同一個問題：**「按下停止之後，這段對話應該留下什麼？」**

回答了它，兩個 bug 的正確行為同時被定義：

- 留下已經生成的部分文字？還是留下部分文字加一個「已中斷」的標記？（現有程式在**長度上限**與**重複迴圈**兩種自動中斷時，走的是加標記那條路 —— 見 `send()` 裡的 `StopReason`。使用者手動停止要不要一致，是產品決定。）
- 那個結果要不要當場存檔？

拆成兩輪的話，PM 會各自決定一半，而第二個決定會受第一個限制。

**這不是「正確行為自明」的情況** —— 「顯示錯誤訊息」顯然不對，但「該顯示什麼」有真正的取捨。

# 我還沒做的事

- **沒有動任何程式碼。** 兩個 bug 都在 `ChatViewModel.send()` 與 `stop()`，我一行沒改。
- **沒有查證取消後的 `updatedAt` 語意是否該調整。** 現行「最後更新時間」的定義是「內容最後一次改變的時間」；寫入錯誤訊息本身算一次內容變更，所以停止當下時間會前進。若 PM 決定停止不再覆寫內容，這條的行為會跟著變 —— 屆時要一併確認，不要事後才發現。
- **沒有檢查 `CompareScreen` 有沒有同樣的問題。** 它有自己的 ViewModel 與取消路徑，看起來會標記「已取消」而不是寫錯誤訊息，但我沒有實際驗證。這屬於「看到了但不在範圍內」，值得 PM 在劃範圍時看一眼。
