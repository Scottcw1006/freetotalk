# PM 收件匣（history-missing-after-switch）

## [2026-09-14 17:20] 使用者決定：這個 bug 與「儲存層改為資料庫」一起往後放

- **來源**：使用者裁決
- **相關條目**：`v1/spec-decisions.md` D1「重現案例用哪一種自動化測試釘住」；`findings.md`
- **狀態**：待處理（**下一次開這個 slug 的輪次時讀**，不是現在）

**內容**：

**v1 規格寫完了，但這一輪不修。** 使用者看過風險評估（中低：不會丟資料、會自行恢復、影響範圍只有這一台手機）之後，決定把它跟一個**還沒拍板的方向**一起往後放：

> **把對話儲存改成資料庫，並且讓歷史清單直接跟著資料庫的變動自動更新。**

**這個方向會從結構上讓這個 bug 不可能發生** —— findings 裡那兩個缺一不可的成因會同時消失：

1. 「讀到寫到一半的檔」→ 資料庫的寫入是原子的，讀的人只會看到寫之前或寫完後
2. 「最後寫進狀態的那份清單贏」→ 清單不再由誰去讀一份再交回來，而是直接跟著資料庫走

### 屆時要重看的五件事

**1. v1 的正確行為不必改，但滿足方式會變。** H2「App 自己正在存的對話，不算讀不起來的檔」刻意寫成不綁做法 —— 資料庫與「先寫暫存檔再改名」都滿足它。

**2. D1 要重看。** 那四個選項是在「繼續用檔案」的前提下列的。換資料庫之後，「Android 的 JSON 程式庫在 JVM 測試裡是空殼」這個障礙會消失（RD 已於 2026-09-14 實測證實它確實一碰就失敗），但會換成「**資料庫能不能在 JVM 上測**」這個新問題，**那需要實際查證，不要讀設定推論**。

**3. v1 的修正範圍沒有「搬遷既有對話」。** 使用者手機上有真實對話在 JSON 檔裡，**搬錯就是資料遺失**。換資料庫要出下一個版號，並把搬遷劃進範圍、寫出它自己的驗收。

**4. 有兩件事做錯會長出一個長得很像的 bug**，寫進規格時要守住：
- **清單 = 資料庫裡的所有對話 − 現在開著的那一段**。「開著哪一段」在記憶體裡。兩個來源要**持續一起算**，不能寫成「讀一次資料庫、把結果存起來」—— 那就回到「交一份舊清單」的形狀。
- **開著的那段與串流中的回覆必須留在記憶體**：`docs/specs/conversation-search/spec.md` §1.8「搜得到的必須等於畫面上看得到的」要求還沒存檔的新對話、正在跑的回覆都要搜得到，而它們不在資料庫裡。**資料庫不能變成唯一的來源。**

**5. 它跟一條架構建議正面相反**：`docs/specs/conversation-search/spec-architecture.md` E.3「保持零狀態的純轉發：不快取、不合併、不持有推送式的資料流」。那是建議不是規定，RD 可以不照，**但要在收件匣講明為什麼**。

### 若最後決定不換資料庫

回到 v1 原樣：拍 D1，檔案做法（先寫暫存檔再改名）仍然成立。**v1 一個字都不必改。**

### 等待期間仍然存在的風險（使用者知情）

- **這個 bug 本身**：串流中切換 → 被切走的那段暫時從歷史清單與搜尋裡消失，下一次重讀清單才回來。
- **一個真的會丟資料的洞**：存檔是「先清空再寫入」，App 若剛好在兩者之間被殺掉，那個檔會永遠是空的、下次開啟被當成壞檔略過。**這是原本就存在的風險**（v1「明確不做」），機率極低；但這個 bug 讓同一段被寫兩次，**等於把那個空窗開了兩次**。換資料庫或暫存檔改名都會補上它。
