# 串流中切換後，被切走的對話不在歷史清單裡

> 階段 0 的產出（RD，2026-09-14）。**程式碼行號對應 commit `7056f24`** —— 行號會隨改動飄移，要對照請 `git show 7056f24:<檔案>`。

---

# 現象

**使用者會遇到的**：回覆還在一個字一個字跑出來的時候按「換人」，被切走的那段對話**從歷史抽屜裡消失**。它其實有存好，但清單上看不到，使用者會以為它不見了。

它違反的是功能總覽上寫給使用者的承諾：

- `docs/product/features.md` 人格-04「換人格會開一段新的對話，**原本那段留在歷史紀錄裡**」
- `docs/product/features.md` 模型-04（同一句承諾，換模型）
- `docs/product/features.md` 保存-04「回覆還在生成中的時候切換⋯⋯被切走的那段會留下已經寫出來的部分文字，**而且已經存好了**」—— 存好了，但使用者找不到

**發現者**：QA 驗 `conversation-search` v3.13 時，在「三項隨機抽測」裡撞到（抽到的是 `聊天-16`／`聊天-05`／`比較-04`）。**不是那一輪的回歸** —— 受測 commit `4b95648` 沒有動任何一行產品程式碼。

**QA 的原始觀察（原樣保留）**：

> 在一段對話裡送出訊息，**在回覆還在串流時**切換人格（或切換對話），那段被切走的對話會被正確地存到磁碟上（內容、時間都對），但**抽屜歷史清單在那之後不會列出它**，直到下一次別的動作觸發歷史重讀（再切一次對話、或重啟 App）為止。

---

# 重現步驟

**QA 在實機上重現 2 次，2 次都成立**（Pixel 9 / Android 16，commit `4b95648`）：

1. 開著任一段對話，送出一則會產生較長回覆的訊息。
2. 約 1 秒後（**回覆仍在串流**）按「換人」切到另一個人格。
3. 打開抽屜 → 剛剛那段對話**不在清單裡**；關掉再打開、等 10 秒都一樣。
4. 看磁碟：那個檔**存在**，`updatedAt` 正確（例：`19:44:29`，抽屜在 `19:44:5x` 打開），內容完整。
5. `am force-stop` 再開 App → 它出現在清單最上面，位置正確。

**必要條件：切換當下回覆必須還在串流。** 理由在診斷第 2 點 —— 不在串流時，這條路徑根本不會出現兩次寫入。

**這是一個競態，不是每次必中。** QA 2/2，但下面的機制表示命中率取決於兩個 I/O 執行緒的排程，換裝置、換檔案大小都可能改變機率。

---

# 診斷

**一句話**：串流中切換時，**同一段對話被兩個協程同時寫進同一個檔**；其中一個協程讀歷史時剛好碰上另一個寫到一半的空檔，把它當成壞檔丟掉；而那個不完整的清單又剛好是最後寫進狀態的那一份。

## 1. 切換時會存一次檔

`ChatViewModel.kt` 三個切換入口的形狀一模一樣 —— 先 `stop()`，再自己起一個協程存「當下開著的那段」、然後重讀歷史：

| 入口 | 呼叫 stop | 存檔 | 重讀歷史 |
|---|---|---|---|
| `switchPersona` | :137 | :139 `repository.save(_uiState.value.conversation)` | :144 |
| `openThread` | :152 | :154 | :158 |
| `switchModel` | :118 | :120 | :125 |

（`startNewThread` :148 就是 `switchPersona`。）

## 2. 串流中的 stop() 也會存一次 —— 同一段

`stop()` :342–343：**沒有正在串流的訊息就直接 return**，不存檔。

有的話，它把部分回覆收尾進狀態，然後 :366–370：

```kotlin
val stopped = _uiState.value.conversation
viewModelScope.launch {
    repository.save(stopped)
    refreshHistory()
}
```

**所以只有在串流中切換，才會同時出現兩個協程**：`stop()` 起的那個（存 `stopped`）與切換入口起的那個（存 `_uiState.value.conversation`）。兩者存的是**同一段對話、同一個 id、同一個檔**，而且因為兩個 `launch` 緊接著發生，切換入口讀到的 `_uiState.value.conversation` 就是剛收尾完的那一段。

**這解釋了必要條件**：不在串流時 `stop()` 早退，只剩一次寫入，不會出事。這也是為什麼 `conversation-search` 任務 13 驗收 4（**收到完整回覆之後**的排序）一直是 pass —— 那條走的是不串流的路。

## 3. 寫檔不是原子的，而且兩次寫入跑在不同執行緒

`ConversationStore.kt` :35 `save` 包在 `withContext(Dispatchers.IO)` 裡 —— 兩個協程的寫入**可以同時跑在兩條 I/O 執行緒上**。

:41 `fileFor(conversation.id).writeText(...)`：`writeText` 是**先以截斷模式開檔、再寫入**。開檔那一刻檔案變成 0 byte，寫完才恢復。**兩次寫入交錯時，這個 0 byte 的空窗會出現兩次。**

## 4. 讀到空檔會被靜默丟掉

`ConversationStore.kt` :29–33 `loadAll`：

```kotlin
.mapNotNull { file -> runCatching { file.readConversation() }.getOrNull() }
```

一個 0 byte 的檔，`JSONObject("")` 會丟例外 → `runCatching` 吃掉 → `mapNotNull` 丟掉。**那段對話從這一次讀到的快照裡消失。**

**這個靜默丟棄本身是規格要求的**：`docs/specs/conversation-search/spec.md` §9.2「一個讀不起來的對話檔，不得讓其他對話消失」—— 為了一個真的損毀的檔，不讓整份歷史一起不見。**問題是它分不出「真的壞了」與「別人正在寫」。**

## 5. 最後寫進狀態的那份清單贏，不管它讀得多早

`ChatViewModel.kt` :211–218 `refreshHistory`：

```kotlin
val all = repository.all()          // 讀快照（會掛起）
_uiState.update { state ->
    state.copy(history = all.filterNot { it.id == state.conversation.id })
}
```

先讀、後寫進狀態。兩個協程各跑一次，**誰的 `update` 最後落地，清單就是誰的快照** —— 即使那份快照比另一份更早讀、或讀到了空檔。

**於是會出現**：協程甲的讀取碰上協程乙寫檔的空窗 → 甲的快照少了這段；乙的讀取在寫完之後 → 乙的快照是完整的；**乙先寫進狀態、甲後寫進** → 清單停在甲那份不完整的。之後沒有任何動作再觸發重讀，所以它一直缺著。

## 6. 為什麼光是「兩次重讀交錯」不夠解釋

QA 的推測是「兩個 `refreshHistory` 交錯，晚回來的那個帶著較舊的快照覆蓋回去」。**那是後半段，但單靠它不會少掉這一段**：兩個協程都是「先寫、後讀」，如果寫入是原子的，兩份快照讀的時候檔案都已經完整存在，都會包含它。**讓某一份快照真的缺這一段的，是第 3、4 點那個截斷空窗** —— 而那個空窗只有在同一個檔被兩個執行緒同時寫的時候才會被別人讀到。

**所以兩個成分缺一不可**：同檔並發寫入（讓快照缺一段）＋最後寫入者贏（讓缺的那份留下來）。

## 7. 與觀察到的終態逐項對得起來

| QA 看到的 | 這條機制預測的 |
|---|---|
| 磁碟上的檔存在、內容完整、時間正確 | 兩次寫的是同樣內容，都寫完之後檔案是對的 ✓ |
| 抽屜清單缺這一段 | 最後落地的是讀到空檔的那份快照 ✓ |
| 關掉再打開、等 10 秒都一樣 | 開抽屜不觸發重讀，狀態裡的清單沒變 ✓ |
| `force-stop` 再開就出現 | 冷啟動重新 `loadAll`，此時檔案完整 ✓ |
| 只在串流中切換才發生 | `stop()` :342 不在串流時早退，沒有第二次寫入 ✓ |

## 8. 機制的關鍵一步，在 JVM 上獨立驗證過

**問題**：兩個執行緒把**同樣的內容**同時 `writeText` 進同一個檔時，第三個執行緒讀得到空檔嗎？

**做法**：暫時的 JVM 測試（跑完已刪除，不在 repo 裡）。內容 4,814 bytes（約一段對話的大小），2 條執行緒不停寫、1 條不停讀並比對，跑 3 秒。

**結果**：

```
讀取 119,439 次
內容不符 39,042 次（33%）
其中讀到空檔 39,042 次 —— 每一次不符都是空檔，沒有讀到「寫一半」的
```

**它證明的**：截斷空窗真的存在，而且很寬；讀到的不是半截內容，而是 0 byte —— 正好是 `JSONObject("")` 會失敗的那一種。

**它沒有證明的**：實機上那兩次到底是哪一種交錯。緊密迴圈會把機率放大很多，App 裡每次切換只有一組寫入。**命中率以 QA 的實機 2/2 為準，機制以上面的程式碼與這個探針為準。**

# 為什麼當初會漏

**兩輪各自做了正確的決定，而沒有人規定這兩個決定同時發生時要怎樣。**

- `stop-generation` 修 B2（按停止那一次不存檔）時，在 `stop()` 裡**加了一次存檔**，並明文要求由切換隱含觸發的停止也要落盤：`docs/specs/stop-generation/spec.md` R5「停止當下就必須落盤」、R10「由切換隱含觸發的停止，行為與手動停止一致」。
- 同一份 spec 的修正範圍**明文保留**切換時既有的那次存檔：`docs/specs/stop-generation/spec.md`「修正範圍」—— 「不改切換對話／人格／模型時既有的那次存檔。那條路正在正常運作」。
- `conversation-search` 也保護那次存檔：`docs/specs/conversation-search/spec-tasks.md` 任務 13 驗收 7「存檔時機未被改動」，以及同檔「明確不做」裡「只改寫下去的時間值怎麼來，不改什麼時候寫檔」那一條。

**兩條規則加起來 = 串流中切換時同一段對話存兩次。** 兩份 spec 都當時核對過彼此「說法對得起來」（`stop-generation` spec「對 conversation-search 的影響」一節），**核對的是規則文字，不是兩個存檔在同一個瞬間發生會怎樣**。

**驗收也剛好都繞過它**：

- `docs/specs/stop-generation/spec.md` R6「落盤的必須是『被停止的那一段』」**正是在測串流中切換** —— 但它的可觀察物是**兩個檔的內容**，不是歷史清單。檔案內容是對的，所以 R6 過。
- `docs/specs/conversation-search/spec-tasks.md` 任務 13 驗收 4 測歷史排序，但情境是**收到完整回覆之後** —— 不串流，沒有第二次寫入。
- **沒有任何一條驗收的可觀察物是「切換後，被切走的那段在歷史清單上」**。

**同一類洞可能不只這一個**：任何「兩個協程對同一個檔寫入」的地方都有同樣的截斷空窗。目前我找到的只有這一處（`deleteThread` 不呼叫 `stop()`；比較畫面不存檔），但**這份診斷沒有系統性地掃過**。

# 要不要 PM

**要。** 使用者後果是自明的（被切走的那段必須在清單上），但**怎麼修會碰到兩份既有 spec 的規則**，而且有一個真的需要定義的「什麼算對」。

## 修法會碰到既有規則

最直覺的修法是「兩次存檔拿掉一次」—— **那就是改存檔時機**，正面撞上：

- `conversation-search` 任務 13 驗收 7「存檔時機未被改動」與「明確不做」那一條
- `stop-generation`「修正範圍」的「不改切換⋯⋯既有的那次存檔」、以及 R5／R10

**這是跨兩輪的規則**，依 PM 定義裡的跨輪衝突規則，不能由單一輪自己選一邊改。

## 修法有好幾種，碰到的規則不一樣

**這張表是給 PM 判斷「會碰到哪些規則、修到哪裡」用的素材，不是 RD 在選做法** —— 機制怎麼選，等 PM 劃出範圍之後由 RD 決定。

| 方向 | 碰到存檔時機？ | 碰到存取層既有行為？ | 解決的是 |
|---|---|---|---|
| 切換入口在 `stop()` 已經存過時不再存 | **是**（兩份 spec） | 否 | 第二次寫入 |
| 寫檔改成原子的（先寫暫存檔再改名） | 否 | **是**（§9 那一層的實作） | 截斷空窗 |
| 同一段對話的寫入排隊，不並發 | 否 | 可能 | 並發寫入 |
| 歷史清單不接受比現在更舊的快照 | 否 | 否 | 最後寫入者贏 —— **只治症狀**，截斷空窗還在 |

## 一個需要定義的「什麼算對」

**一個「正在被寫」的檔，算不算 §9.2 說的「讀不起來的檔」？**

`docs/specs/conversation-search/spec.md` §9.2 規定讀不起來的檔**不得讓其他對話消失** —— 它沒有說**那個檔自己**可以暫時消失。今天的實作把「別人正在寫」和「真的損毀」當成同一件事處理。**要不要分開、分開之後各自該怎樣**，是規格的決定，不是實作的。

## 一個會影響「修好」怎麼驗的限制

**階段 2 規定：這個失敗案例必須進測試套件。** 但它發生在兩個目前**在 JVM 上測不動**的地方：

- `ChatViewModel` —— 相依全部在類別內部從 `Application` 生出來（未結案清單 T1 那一項）
- `ConversationStore` —— 建構子吃 `Context`，但實際只用到 `context.filesDir`

所以要把它釘成一支測試，**要嘛先動其中一個的建構方式，要嘛只能靠實機驗**。PM 定義「修好」的判定時需要知道這件事 —— 它決定驗收條文能不能要求一支會紅的測試。
