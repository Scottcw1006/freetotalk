## D1 重現案例用哪一種自動化測試釘住

### 為什麼需要你決定

bug 修正的規定是：**失敗案例必須成為一支會被自動執行的永久測試**，而且修正前要會紅。這個 bug 的根因在對話存取層（`spec.md`「正確行為」H2「App 自己正在存的對話，不算「讀不起來的檔」」），但**這一層今天在 JVM 上測不動**，兩個原因：

1. 它的建構方式要求一個 Android 的 `Context`（實際上只用到 App 的檔案目錄）。
2. 它用 Android 內建的 JSON 程式庫讀寫檔案。**依 Android Gradle plugin 的預設，JVM 單元測試裡的 Android 程式庫只是空殼**，專案沒有另外設定，現有的 JVM 測試也沒有一支用到它。**這一點我是讀設定推出來的，沒有實際跑過**，RD 開工時要先確認。

四條路都走得通，但每一條都**引入專案現在沒有的東西**，或**碰到另一輪寫過的判斷**，所以不由我選。

### 選項

| | 做法 | 代價 | 碰到什麼 |
|---|---|---|---|
| **(a) JVM 測試** | 讓存取層能在測試裡用一個暫存目錄建出來（正式 App 仍然用 App 的檔案目錄、仍只有一處在用），並加一個只在 JVM 測試裡使用的 JSON 實作 | 正式程式碼改一個建構方式；**第一個 JUnit 以外的測試相依** | `stop-generation` 那一輪的修正範圍寫過「不為了測試把引擎或儲存改成可注入」（那是那一輪的邊界，不是永久規則，但形狀相同）；`conversation-search`「明確不做」寫過「裝置端測試是它未來唯一合理的自動化形式」 |
| **(b) 裝置端測試** | 在 `app/src/androidTest` 寫測試，用真的 App 環境建存取層 | **QA 每一輪的標準流程要多一個需要接著裝置的測試指令**（現在每輪只跑 JVM 測試），執行慢；那個流程規定在 QA 的角色定義裡，**要一併改角色定義**，不是只改這份規格 | 與 `conversation-search` 的預言一致；正式程式碼不必為測試改任何東西 |
| **(c) 不寫自動化測試，只做實機驗收** | 任務 1 驗收 1–5 改成「修正後實機 H1 多次通過」 | **違反 bug 修正的規定**；而且這是競態，實機通過幾次都**證明不了**它已經不存在 —— 等於沒有東西在守根因，下一個加存檔路徑的人會再撞一次 | 無 |
| **(d) 先做 T1 再修** | 先把 `ChatViewModel` 改成可以從外面給相依，再寫端到端的 JVM 測試 | 範圍變成一次狀態層改造；而且**光有 T1 還不夠**：它能測「清單對不對」，但若存取層沒有同時變得可測，根因（截斷空窗）仍要用假的存取層繞過去，測不到真的寫檔 | 未結案清單上的 T1；你還沒決定要不要做 |

### 我的傾向（不確定，寫出來讓你知道）

**略傾向 (a)**，理由只有一個：**QA 每輪都會跑的指令，才是真的在守的測試**。(b) 的測試只有在有人接著裝置、而且記得多跑那個指令時才會執行；那個「記得」正是這個專案的文件反覆失效的地方。

**但 (b) 的優點是真的**：正式程式碼一行都不必為了測試而改，也不必推翻另一輪寫過的判斷。如果你認為「不為了測試改建構方式」比「測試每輪都跑」重要，(b) 是對的選擇。

**我不建議 (c)。** (d) 是一個合理的長期方向，但不是這個 bug 需要的東西。

### 拍板之後要做的事

- 選 (a) 或 (b)：`spec.md` 任務 1 的「標準測試指令」寫定為那個指令，任務 3 驗收 8 與任務 4 驗收 3 跟著確定；這一項移到 `spec-appendix.md`／決策歷程。
- 選 (b)：另外需要改 QA 的角色定義（加入裝置端測試指令），那不在任何一份規格裡。
- 選 (c) 或 (d)：任務 1 要改寫，會出下一個版號。

# 本輪我自己做的判斷（不擋工，你可以推翻）

這幾項我已經照著寫進規格了。寫在這裡，是因為它們回答了「什麼算對」或碰到了其他輪次，你應該有機會說不。

1. **「正在被寫的檔」不算 `conversation-search` §9.2 說的「讀不起來的檔」**（`spec.md` H2）。§9.2 規定壞檔不得連累**其他**對話，沒有說壞檔**自己**可以消失；「App 自己正在寫」與「真的壞了」是兩件事，而**正確的區分方式是讓 App 自己的寫入永遠不會被讀成壞檔**，不是讓讀取去猜。反向對照 H3 保證真正的壞檔照舊被略過。
2. **這個保證由對話存取層負責，不由呼叫端排程負責。** 理由就是這個 bug：兩個呼叫端各自都對，出事的是它們同時發生。**另一種做法**（在 `ChatViewModel` 裡讓所有存檔排隊）在今天會得到同樣的使用者結果，但它在 T1 之前驗不到，而且每一條新的存檔路徑都要記得排隊。
3. **修正範圍不改任何存檔時機或次數，所以與 `conversation-search` 和 `stop-generation` 的存檔規則沒有衝突**，不需要你在兩輪之間選一邊。逐條理由在 `spec.md`「已知衝突與邊界情況」第 1 條。**若 RD 判斷非改不可，他要寫進收件匣，那時才會變成一個跨輪待決事項。**
4. **在 `docs/product/features.md` 的 人格-04、模型-04、保存-04 補上指向本規格的引用，但沒有改「現況」欄的文字。** 那三項的文字描述的是修好之後應有的樣子，這個 bug 是違反它，不是它寫錯。
