# 現象

（照 `findings.md`「現象」與「重現步驟」兩節原樣保留，未改寫。）

**QA 的原始觀察**：

> 在一段對話裡送出訊息，**在回覆還在串流時**切換人格（或切換對話），那段被切走的對話會被正確地存到磁碟上（內容、時間都對），但**抽屜歷史清單在那之後不會列出它**，直到下一次別的動作觸發歷史重讀（再切一次對話、或重啟 App）為止。

**重現步驟**（QA 實機重現 2 次，2 次都成立；Pixel 9 / Android 16，commit `4b95648`）：

1. 開著任一段對話，送出一則會產生較長回覆的訊息。
2. 約 1 秒後（**回覆仍在串流**）按「換人」切到另一個人格。
3. 打開抽屜 → 剛剛那段對話**不在清單裡**；關掉再打開、等 10 秒都一樣。
4. 看磁碟：那個檔**存在**，`updatedAt` 正確（例：`19:44:29`，抽屜在 `19:44:5x` 打開），內容完整。
5. `am force-stop` 再開 App → 它出現在清單最上面，位置正確。

**必要條件：切換當下回覆必須還在串流。** **這是競態，不是每次必中。**

它違反的使用者承諾：`docs/product/features.md` 的 人格-04、模型-04（「原本那段留在歷史紀錄裡」）與 保存-04（「而且已經存好了」—— 存好了，但使用者找不到）。

# 診斷

**我自己讀過程式碼，`findings.md`「診斷」的第 1–7 點全部成立。** 以下只寫確認後的版本與我補查的部分；逐點的程式碼位置見 `findings.md`（它的行號綁在一個 commit 上，本文件不引用行號）。

## 兩個成分，缺一不可

1. **同一段對話被兩個協程同時寫進同一個檔。** 三個切換入口（切換人格——含「開始新的對話」、切換模型、開啟另一段對話）都先呼叫停止，再自己起一個協程「存下當下開著的那段、然後重讀歷史」。停止**只有在有訊息正在串流時**才會另外起一個協程，存下被停止的那段並重讀歷史。兩者存的是同一段、同一個 id、同一份內容。
   - 這個第二次寫入是 `stop-generation` 那一輪修 B2（按停止那一次不存檔）時加進來的。**在那一輪之前，串流中切換只有一次寫入，所以這是那一輪修正與存取層既有寫法疊加出來的回歸**，不是一開始就在的。
2. **寫檔是「先把檔截成 0 byte、再寫入」，而且兩次寫入可以跑在兩條 I/O 執行緒上。** 一個協程寫完、開始讀全部對話時，可能正好碰上另一個協程剛把同一個檔截成 0 byte。
3. **讀全部對話時，解析失敗的檔被靜默略過。** 0 byte 的檔解析失敗 → 那段對話從這次讀到的快照裡消失。這個略過本身是 `docs/specs/conversation-search/spec.md` §9.2「一個讀不起來的對話檔，不得讓其他對話消失」要求的；**問題是它分不出「真的壞了」與「App 自己正在寫」**。
4. **最後寫進狀態的那份快照贏。** 重讀歷史是「先讀、後寫進狀態」，兩個協程各做一次，誰後落地清單就是誰的 —— 即使那份是讀到空檔的那一份。之後沒有動作再觸發重讀，於是一直缺著。

**第 1–3 點讓某一份快照缺這一段，第 4 點讓缺的那份留下來。** 若寫入不會讓讀取看到空檔，兩份快照都讀在「至少一次寫入已完成」之後，都會包含它，第 4 點就沒有東西可以留下（我逐一推過三個切換入口的協程順序，結論相同：切換入口的重讀一定排在自己的寫入之後，停止的重讀也一定排在自己的寫入之後）。

## 我補查的三件事（會影響「正確行為」與「修正範圍」怎麼寫）

- **同型的並發寫入不只串流中切換這一處。** 在不串流的情況下**連續快速觸發兩次切換**（第一次切換的協程還沒把開著的對話換掉，第二次就來了），兩個切換協程會同時存同一段對話 —— 形狀與本 bug 相同，而且**不經過停止**。所以「串流中切換時少存一次」不會堵住它；讓讀取不會看到寫到一半的檔才會。**實機上兩次點擊能不能快到命中，我沒有驗證**（點抽屜裡的一列會關抽屜，要連點得很快）。
- **回覆自然結束、正在收尾存檔的那一瞬間切換，我判斷不會出現這個現象。** 那時停止不會另外存檔（已經沒有串流中的訊息），收尾那次的寫入在切換之前就已開檔截斷，而收尾自己的重讀會隨著工作被取消而不執行；剩下的只有切換入口自己「寫完再讀」。**這是讀程式碼推出來的，沒有實測，我不確定到百分之百。** 它不影響本輪的定義：H2 本來就不分是誰在寫。
- **`findings.md`「診斷」第 8 點的 JVM 探針**（兩條執行緒同時覆寫、一條讀，讀到的不符全部是空檔）**我沒有重跑**，引用 RD 的結果。它只用來證明截斷空窗存在；本輪的判定不依賴它的數字。

# 這是不是 bug

**是 bug，而且同時是規格從來沒規範過的一塊。**

- **是 bug**：`features.md` 對使用者的承諾（人格-04、模型-04、保存-04）明寫被切走的那段「留在歷史紀錄裡」「已經存好了」。沒有任何一份規格說過「串流中切換時，被切走的那段可以暫時或持續不在清單上」。
- **規格從來沒規範過的**有兩件：
  1. **「切換之後，被切走的那段在歷史清單上」從來沒有一條驗收以它為可觀察物。** `stop-generation` 驗串流中切換時看的是**檔案內容**（它的 R6、R10），`conversation-search` 驗歷史排序時看的是**不串流**的情境。
  2. **「App 自己正在寫的檔」讀起來該是什麼樣，從來沒有被定義。** `conversation-search` §9.2 寫的是損毀的檔不得連累其他對話；它沒有說損毀的檔**自己**會怎樣，也沒有區分「損毀」與「正在寫」。今天的實作把兩者當同一件事。本輪由 H2、H3 定義。

為什麼當初兩份規格都沒有接住，完整的回答在 `spec-appendix.md`／「為什麼當初會漏」。**一句話版本**：`stop-generation` 那一輪其實預見了「停止與切換會前後各重讀一次歷史，要確認抽屜內容不缺項」，但那句話寫在它的「已知衝突與邊界情況」第 3 條、指向的任務 4 裡**只有一條不串流的切換回歸**——指得出任務，指不出條文，於是等於沒有覆蓋。

# 正確行為

**每一條都是可判定的。D1 只決定 H2 的測試跑在哪個環境，不改變任何一條的內容。**

### H1 串流中切換之後，被切走的那段在歷史清單上

**共同前置**：引擎已就緒。開著一段對話 A（新開的或既有的都可以），送出 `tell me a long story about a cat`（或任何會產生較長回覆的訊息）。**在回覆畫面上已經出現文字、而且仍在一個字一個字增加時**（通常是開始串流後 1–3 秒內），做下面四種切換之一：

| 入口 | 操作 |
|---|---|
| 切換人格 | 右上角「換人」→ 選一個**不同**的人格 |
| 切換模型 | 抽屜 → 模型區點另一個模型 |
| 開始新的對話 | 抽屜 →「開始新的對話」 |
| 開啟另一段對話 | 抽屜 → 歷史清單點另一段既有對話 B |

**預期**（切換之後等 3 秒再打開抽屜 —— 這 3 秒是給存檔寫完的時間，不是容許清單延遲出現）：

1. **歷史清單裡有 A，而且恰好一列。**
2. **A 那一列是清單的第一列。** 理由：A 的內容在停止那一刻改變了（`stop-generation` R2 追加了中斷標記），它是清單上內容最新的一段；開啟 B 的那一種情形，B 是開著的那段，本來就不在清單上。
3. **不做任何其他動作**（不重啟、不再切換、不刪除），關上抽屜、等 10 秒、再打開 → A 仍在、仍是一列。
4. 從抽屜進入搜尋，查 `long story`（或所送訊息裡的任一個詞）→ **A 的分組出現在結果裡。**（搜尋看的是開著的那段加上歷史清單，清單缺 A 時搜尋也搜不到它，所以這是同一個缺陷的第二個使用者面。）

**零文字的變體**：在回覆**還沒出現任何一個字**時切換（`stop-generation` R4 的情境：那則空回覆不留下，但使用者剛送出的訊息留著，所以 A 仍是一段非空白、會被存下的對話）→ 預期 1–4 同樣成立。

**不串流時的切換**：預期與修正前完全相同（清單上有被切走的那段，除非它是空白對話 —— 見 `conversation-search` §9.1「儲存一段空白對話等於刪檔，不是寫檔」）。

**H1 的判定限制，誠實寫**：這是競態。修正前 QA 命中 2/2，但**實機上一次通過不能證明競態已經不存在**。所以 H1 在實機上以多次重複判定（見任務 2），**「競態已經不存在」這件事由 H2 的自動化測試證明**，不由 H1 證明。

### H2 App 自己正在存的對話，不算「讀不起來的檔」

**定義（回答 `conversation-search` §9.2 留下的那個問題）**：

- 一段對話**只要已經有一次存檔完整結束**，此後任何時刻開始的讀取 —— **讀全部對話**與**依 id 取一筆**兩條路都算 —— **都必須包含它**，讀到的內容必須**等於某一次存檔寫下的完整內容**（每一個欄位、每一則訊息都相同）。
- **不論當下有沒有別的存檔正在寫同一段對話、同時有幾個在寫。**
- 讀取不得因為有存檔在進行，就把這段對話略過、回報找不到、或回傳半截內容。

**本條要守的並發形狀**：同一段對話同時被存下**同樣的內容**兩次以上。這是今天的程式實際走得到的唯一形狀（停止與切換入口存的是同一份；連續快速兩次切換也是）。「同時存下**不同**內容」今天走不到，本輪不定義，見「明確不做」。

**責任邊界**：**這個保證由對話存取層提供，不由呼叫端的排程提供。** 理由就是這個 bug 本身：兩個呼叫端各自都做對了（一個是 `stop-generation` 要求的停止當下落盤，一個是 `conversation-search` 保護的切換時存檔），**出事的是它們同時發生**；把保證放在呼叫端，下一條新增的存檔路徑就會再撞一次，而且沒有任何一個呼叫端會覺得是自己的錯。

**為什麼 H2 要獨立成一條，而不是只靠 H1**：H1 在實機上是機率性的；H2 是唯一可以決定性地判定「截斷空窗已經不存在」的地方，而且它同時蓋住「連續快速兩次切換」那個實機上難以命中的同型情境。

### H3 真正讀不起來的檔，仍然被略過，而且讀取照樣完成

- `conversation-search` §9.2 **一個字都沒有被放寬**：對話所在的目錄裡放一個**內容不是合法對話資料**的檔，以及一個**沒有任何存檔正在寫的 0 byte 檔**，讀全部對話 → 其餘每一段對話都在，讀取正常結束（不會卡住等待、不會重試到逾時）；依 id 取那兩個檔對應的 id → 找不到，與讀全部的結果一致（`conversation-search` §9.3「依 id 取一筆與取全部再挑出同一個 id 必須得到同一個答案」）。
- **為什麼要寫**：H2 最自然的誤修，是把「讀到空的或解析失敗」當成「有人正在寫，等一下再讀」。那樣做在 H2 的測試裡會過，但一個真的壞掉的檔會讓整份歷史卡住或讀不出來 —— **那正是 §9.2 要防的「使用者的整份歷史一次全部不見」**。H3 就是 H2 的反向對照。

### H4 存檔全部結束之後，不多出任何東西

- 所有存檔都結束之後，**歷史清單上每段對話恰好一列、搜尋結果裡每段對話恰好一個分組**，不得出現一段磁碟上不存在的對話、或同一段出現兩次。
- 對話所在的目錄裡，**檔案數等於已存下的非空白對話數**。
  - 這一點本身說得出的使用者後果較弱（多出來的檔若沒有被讀成對話，使用者看不到），**寫進來的真正理由是**：`stop-generation` R5 預期一與 `conversation-search` §9.1 的可判定條文**都是數對話目錄裡的檔案數**；多一個殘留檔，那兩條就會在一個行為正確的 App 上判 fail。修法若在過程中用到任何暫時的東西，結束後不得留下。

# 修正範圍

## 修到哪裡算修好

1. **H2 成立**，而且由對話存取層提供。
2. **H3、H4 成立**（H2 的修法沒有放寬 §9.2、沒有留下殘留）。
3. **H1 在實機上成立**（四個入口、含零文字變體）。
4. **重現案例成為一支會被自動執行的永久測試**，斷言 H2，而且**對修正前的存取層寫法會變紅**。測試跑在哪個環境由 **D1** 決定（見 `spec-decisions.md`）。
5. 下面「為什麼不該再多修」列出的既有規則全部仍然成立（由任務 3 回歸驗證）。

## 為什麼不該再多修

- **不改任何存檔的時機，也不改任何一條路徑存檔的次數。** 停止當下的那次、三個切換入口各自的那次、回覆收尾的那次，全部照舊發生。
  - **這不是保守，是這個 bug 的正確邊界。** 「串流中切換時兩次存檔拿掉一次」治的是第一個成分的**一個實例**：它堵不住「連續快速兩次切換」那一型（那一型不經過停止），也沒有定義「正在寫的檔算不算讀不起來」。H2 成立之後，兩次存檔同時發生是無害的。
  - **而且它是跨輪的規則。** 存檔時機被兩份既有規格明文保護：`docs/specs/conversation-search/spec-tasks.md` 任務 13「對話「最後更新時間」的定義」驗收 7（存檔時機未被改動）與同檔「明確不做」裡「時間戳這件事只改「寫下去的時間值怎麼來」，不改「什麼時候寫檔」」那一條；`docs/specs/stop-generation/spec.md` R5「停止當下就必須落盤」、R10「由切換隱含觸發的停止，行為與手動停止一致」、以及「修正範圍」裡「不改切換對話／人格／模型時既有的那次存檔」。**本輪的範圍不碰其中任何一條，所以與它們沒有衝突**（逐條理由見「已知衝突與邊界情況」第 1 條）。
  - **若 RD 判斷非改存檔時機不可：不要改，寫進 `pm-inbox.md`。** 那會變成一個跨輪待決事項交給使用者，不是本輪能自己決定的事。
- **不修「最後寫進狀態的那份快照贏」。** H2 成立之後，本 bug 的每一份快照都包含被切走的那段（見「診斷」），這個成分就沒有東西可以留下。它還有別的表現形式（見「明確不做」），但那是另一個 bug；在這一輪動它，會碰到每一條會重讀歷史的路徑（送出後收尾、刪除、冷啟動、每一種切換），而那些路徑今天都正常。
- **不做 T1（`ChatViewModel` 的相依改成可從外面給）。** 它會讓 H1 可以在 JVM 上端到端測，但那是一次狀態層的建構方式改造，使用者還沒決定要不要做；本輪用 H2 在存取層釘住根因，H1 留在實機。
- **不改讀不起來的檔怎麼處理**（H3：§9.2 原封不動）。
- **不改其他兩份規格的任何檔案。** 若使用者之後決定要同步那兩份規格的說法，那是另外的輪次。

# 明確不做

| 不做的事 | 為什麼 | 什麼時候回來處理 |
|---|---|---|
| **改存檔時機或存檔次數**（例如串流中切換時只存一次） | 見「修正範圍」：它不是這個 bug 的正確邊界，而且被兩份既有規格明文保護；改它是跨輪決定。 | 有人主張拿掉或合併任何一次既有存檔 —— 寫進收件匣，由 PM 升級給使用者，不在任何單一輪次裡順手做。 |
| **「最後寫進狀態的那份快照贏」的其他表現**：例如一次較早開始的重讀，晚於一次刪除才落地，讓剛刪掉的對話又出現在清單上，直到下一次重讀 | 與本 bug 共用第 4 個成分，但不需要截斷空窗就能發生，觸發條件不同、修法會碰到所有重讀歷史的路徑。**我沒有實機驗證這個情境走得到**，是讀程式碼推出來的。 | 使用者回報「刪掉的對話又冒出來」或「清單顯示的內容比實際舊、而且不會自己恢復」。 |
| **寫到一半 App 被系統殺掉，留下 0 byte 或半截的檔** | 那個檔之後會被 §9.2 靜默略過 —— **那段對話從此在清單上消失，而且沒有任何提示**。這是同一個「非原子覆寫」的另一個後果，但觸發者是行程死亡而不是並發寫入，正確行為要先回答「寫到一半被殺掉時該留下舊版還是什麼都不留」。**RD 為 H2 選的做法可能順帶解決它，但本輪不要求、也不驗。** | 使用者回報「重開 App 之後某段對話不見了」，且那段對話的檔還在但內容是空的或損毀的。 |
| **同一段對話同時被存下「不同」內容** | 今天沒有任何入口走得到（停止與切換存的是同一份，收尾與切換也是）。不可達的情境寫成條文，驗不到東西。 | 新增任何一條「在另一次存檔可能還在進行時，存下同一段對話的不同版本」的路徑（例如串流期間定時自動存檔）。 |
| **T1：`ChatViewModel` 可從外面給相依** | 見「修正範圍」。 | 使用者決定做它；或下一個 bug 的失敗案例只能在狀態層重現。屆時可以把 H1 補成 JVM 測試。 |
| **更新 `conversation-search` 的「明確不做」裡「對話存取層沒有自動化測試」那一條** | 那一條的前提是「這一層沒有邏輯」，本輪修完之後前提很可能不再成立；它還預言了「裝置端測試是它未來唯一合理的自動化形式」，而 D1 的選項之一與此不同。**本輪不動那一輪的檔案。** | 任務 1 通過之後：PM 把「前提已改變、實際採用的是哪一種測試」寫進 `docs/specs/conversation-search/pm-inbox.md`。 |
| **比較畫面** | 它不存檔，沒有這個 bug 的形狀。 | 比較結果開始被保存下來時。 |

  3. **修正後，驗收 1 的測試用標準測試指令連續執行 5 次，5 次全綠。** 正確的做法不會偶爾失敗；偶發的紅就是 H2 沒有成立。

# 已知衝突與邊界情況

**每一條都寫明它碰到誰、為什麼不衝突或怎麼守。**

1. **與兩份既有規格的存檔時機規則：不衝突。**（→ 任務 3 驗收 1、2、5）
   - `conversation-search` 任務 13 驗收 7 與同檔「明確不做」那一條保護的是「切換 / 切人格 / 送出後收尾」三個既有存檔時機 —— **本輪一個都不改**，而且它的可判定（切走再切回內容仍在）由任務 3 驗收 5 照樣驗。
   - `stop-generation` R5、R10 要求停止當下落盤、由切換觸發的停止與手動停止一致 —— **本輪不改停止的存檔**，由任務 3 驗收 1 照樣驗。
   - `stop-generation`「修正範圍」的「不改切換⋯⋯既有的那次存檔」—— **本輪不改**。
   - **本輪改的是「一次存檔進行中，讀取看得到什麼」**，那是上述每一條規則都沒有規定過的東西。
2. **與 `conversation-search` §9.2：不衝突，是補上它沒說的另一半。** §9.2 規定損毀的檔不得連累其他對話；H2 規定 App 自己正在寫的檔不算損毀；H3 保證損毀的檔照舊被略過。**三條合起來，一個讀取遇到解析不了的東西時，答案只有一個：那是真的壞了** —— 因為 H2 保證 App 自己的寫入永遠不會讓讀取遇到它。
3. **與 `conversation-search` §9.3（依 id 取一筆 == 取全部再挑）**：H2 對兩條讀取路徑同時成立（任務 1 驗收 1 兩條都驗）。**最容易打破它的修法**是只保護其中一條路徑，或為了快而讓「依 id 取一筆」繞過讀全部 —— `conversation-search` 的架構建議 §E.6 已經警告過後者。
4. **與 `stop-generation` R6 與 `conversation-search` §8.4（檔案位元組完全相同）**：H2 的修法不得碰到**沒有被存檔**的對話的檔（例如在讀取時順手把舊檔重寫一次）。由任務 3 驗收 2、3 守。
5. **與兩份規格裡「數對話目錄檔案數」的條文**（`stop-generation` R5 預期一、`conversation-search` §9.1 可判定）：修法若在過程中用到暫時的東西，結束後殘留就會讓那兩條在正確的 App 上判 fail。由 H4／任務 1 驗收 5 守；實機上由任務 3 驗收 1、4 守。
6. **與 `stop-generation`「修正範圍」的「不為了測試把引擎或儲存改成可注入」**：那是**那一輪**的修正邊界，理由是不讓兩處的 bug 修正變成一次架構改造。**若 D1 裁決為 JVM 測試，本輪會做一件同樣形狀的事**（讓存取層能在測試環境裡被建出來）。兩者不是同一條規則，但讀的人會看到兩輪對「儲存要不要為了測試改建構方式」給出不同答案 —— **這正是 D1 要使用者決定的原因之一**。
7. **與 `conversation-search`「明確不做」的「對話存取層沒有自動化測試」**：它的前提（這一層沒有邏輯）在本輪之後很可能不成立，它對「未來唯一合理的自動化形式是裝置端測試」的判斷與 D1 的其中一個選項不同。**本輪不改那份檔案**；後續處理見本文件「明確不做」。
8. **讀取變慢或卡住**：若修法讓讀取在有存檔進行時等待，切換、送出後收尾、冷啟動的歷史出現時間都會跟著變。本輪不訂時間上限（沒有既有的基準可比），但**讀取不得因為遇到壞檔而等待**（H3／任務 1 驗收 4），而任務 3 驗收 7 的「全部照常」包含「使用者感受不到明顯的變慢」。**這一項我承認判定偏主觀**；若 QA 覺得有明顯差異，記下來回報，不直接判 fail。
9. **H1 通過不代表競態不存在**：見 H1 末段。實機的 14 次與任務 1 的決定性測試是兩件不同的事，**兩者都要過**。
