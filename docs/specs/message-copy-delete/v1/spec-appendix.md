# 附錄（長按訊息：複製、刪除與復原）

實作與驗收的人不需要讀這一份。它回答「為什麼會變成這樣」。

## 需求來源：使用者裁決（2026-09-18，原樣記錄）

1. 長按一則訊息可以複製：複製的是那個聊天泡泡的文字，整則都要（可能超過一個螢幕），結尾的中斷標記（例如「…（已停止）」）也要一起複製。
2. 長按一則訊息可以刪除，而且可以復原：刪除後那則訊息顯示成「已刪除的對話（復原）」，點復原可以還原。
3. 刪除要讓那段對話的「最後更新時間」前進；復原也要前進。
4. 例外：正在生成中的文字不能長按。
5. 已刪除（未復原）的訊息不再送給模型當上下文；復原之後才又算數。
6. 「已刪除的對話（復原）」佔位永久保留、可隨時復原：刪除狀態要存起來，關 App 重開、切換對話再回來都還在，原文一直留在手機上。
7. 已刪除的訊息在別處一律當作不存在：搜尋搜不到；歷史清單的標題改取下一則沒被刪的「你說的話」；預覽取最後一則沒被刪的訊息。

各條落在 `spec.md` 的哪裡：1 → §1、§2；2 → §3；3 → §5；4 → §1.3；5 → §4.1；6 → §6、§4.5；7 → §4.2–§4.4。

### 二、核對過、對得起來

- **`conversation-search` §9.1「儲存一段空白對話等於刪檔，不是寫檔」與 `conversation-store-db` §1.2「一句話都沒說過的對話不留在儲存裡」**：兩條的字面都是「沒有任何使用者訊息的對話」。本規格 §4.5 判定已刪除的「你說的話」在這個判斷裡照樣算數 —— 那段對話**確實有**使用者訊息（只是已刪除），所以照那兩條的字面它本來就不是空白。不需要改。
- **`conversation-search` §1.2「只有訊息本文參與比對」**：佔位上的「已刪除的對話（復原）」不是訊息本文，搜不到，與 §1.2 一致。
- **`conversation-search` §3.9「命中列不提供刪除或任何會改動資料的操作」**：本輪不在命中列上加長按。一致。
- **`conversation-search` §8.2「不算一次更新」**：清單上沒有刪除或復原；本規格 §5.2（複製、開關選單不前進）與它同方向。
- **`conversation-search` §9.4「使用者從歷史清單刪掉一段對話，就是真的刪掉」**：整段刪掉時已刪除訊息的原文一併消失（本規格 §6.2）。一致。
- **`stop-generation` R2「留下的是…+ 一個固定的中斷標記」、R3「停止之後那則回覆不再變動」**：R3 管的是停止後 5 秒內文字不得自己再變；使用者主動刪除那一則不是 R3 要擋的事，而且復原後文字逐碼位相同（本規格 §3.3）。一致。
- **`stop-generation` R5「停止當下就必須落盤」、`conversation-search`「明確不做」裡「不改什麼時候寫檔」那條範圍線**：本輪**新增**一個存檔時機（刪除與復原當下），沒有拿掉或移動既有的任何一個。`conversation-store-db` 的收件匣寫著「要改存檔的時機或次數，要先寫在這裡」—— 這一筆由 RD 代為留在該 slug 的收件匣，內容是：新增的這次存檔與既有的存檔走同一條單一指令的路（架構建議 §A.3），同一段對話同時被存兩次相同內容的情形由它的 §1.4 涵蓋；生成途中刪除會第一次讓「生成中的對話」被存下來，存下的回覆沒有標記（本規格「明確不做」）。
- **`conversation-store-db` D1（資料庫層不寫自動化測試）、D2（不加測試專用入口）**：本規格照辦（任務 1 全是不開資料庫的純邏輯；任務 4 用唯讀讀資料庫檔）。
- **`conversation-search` 與 `conversation-store-db` 的回歸驗收**：沒有任何一條會造出已刪除的訊息，所以本輪的行為改變不會讓它們變紅。

## 我查證過、值得記下來的事實

- 中斷標記、「出錯了：」、「（這次沒有產生回覆，再說一次試試）」都在回覆收尾時寫進訊息文字（`chat/ReplyEnding.kt` 裡決定回覆最後留下什麼的那個函式）。
- 現行「內容有沒有改變」只比 id 與文字（`chat/Conversation.kt` 裡比較兩個版本的那個函式）；時間只在聊天狀態裡單一的那個更新入口、且這個判斷回答「有改變」時前進。
- 現行存檔呼叫點：回覆收尾、停止、四個切換入口。送出當下不存。
- 資料庫只有一張表、結構版本 1；開法設定了「版本對不上時整個清掉」，並在那時提示一次。訊息以一段 JSON 文字存在一個欄位裡；訊息的儲存形式目前有 id、作者、文字、建立時間四個欄位。
- JSON 的讀法用的是程式庫的預設設定（缺欄位有預設值時讀得起來；多出不認得的欄位時失敗）。**後半句我是依程式庫文件寫的，沒有在這個專案裡實際跑過。** 它只影響「新版寫的資料被舊版讀」的情形，本輪不要求那個方向。
- App 最低支援 Android 12（API 31）；系統自己的剪貼簿提示從 Android 13 起才有。
- 模擬器上設不了也讀不了剪貼簿（沒有對應的指令），UI 路走得通（`docs/qa-environment.md`「剪貼簿」一節，2026-09-16 確認）。
- 本輪開始時的程式碼基準是 commit `e8cf9aa`（任務 4 驗收 4 用它當「本輪實作之前的程式」）。

## 已知取捨與風險

- **原文永久留在手機上**（使用者裁決 6）：使用者以為刪掉的字，其實從資料庫檔讀得到。真正抹除列在「明確不做」。
- **佔位會累積**：沒有「清掉所有佔位」的入口，刪得多的對話會很長。
- **§6.6 沒有驗收**（存不下來時的表現），理由寫在該條旁。
- **§1.3、§1.4、任務 5 驗收 5 在裝置上可能每一輪都攔不到**；§1.3、§1.4 的權威在任務 1 驗收 7。
- **跨規格的字面矛盾會留著一段時間**（決策歷程 D4），與綁舊儲存形式的那批條文一起等下一次修訂。
- **複製出來的字與畫面上的字不一定相同**（決策歷程 D1）：貼到不認得 Markdown 的地方會看到星號與減號。

## 決策歷程

四項都在 2026-09-18 拍板，同一輪（RD 尚未開工、QA 未驗）直接寫回 v1。

### D1 對方的訊息複製出來的是什麼 → (a) 原始字串

- **為什麼問**：使用者說「複製的是那個聊天泡泡的文字」，而對方的回覆在畫面上是排版過的（`**重點**` 顯示成粗體、`- 蘋果` 顯示成「• 蘋果」、`1)` 顯示成「1.」、段落之間的空行不顯示），兩種解讀貼出來不一樣。
- **選項**：(a) 原始字串 —— 一字不漏，與搜尋比對、手機上存的是同一份，不必另外定義轉換規則；代價是貼到不認得 Markdown 的地方會看到星號。(b) 畫面上看到的字 —— 所見即所得；代價是要另寫一組「排版結果轉純文字」的規則與測試，排版規則每改一次就要跟著改，段落之間的空行會不見。
- **裁決**：(a)。使用者知悉的代價：貼出來會有星號、減號。
- **落實**：`spec.md` §2.1；任務 1 驗收 10、任務 2 驗收 5、6；`features.md` 聊天-19。

### D2 升級之後既有的對話 → (a) 保留

- **為什麼問**：存刪除狀態會動到儲存；上一次動儲存（改成資料庫）時使用者裁決不搬遷，這一次不替他假設。
- **選項**：(a) 保留 —— 以現在的儲存形式多記一個狀態不一定要改表格結構，成本接近零；RD 若改表格結構就得寫第一個資料庫搬遷，而資料庫層沒有自動化測試；驗收要用舊版建置造資料再覆蓋安裝。(b) 清空 —— 不需要相容處理；代價是所有對話不見，而且出現的提示說的是「讀不出來」，對正常升級是誤導。
- **裁決**：(a)。
- **落實**：`spec.md` §6.4；任務 1 驗收 8 的舊資料那一半、任務 4 驗收 4；`features.md` 保存-11。

### D3 自己說的話全被刪掉時的標題 → 新文案「（訊息已刪除）」

- **為什麼問**：裁決 7 說標題取下一則沒被刪的「你說的話」，一則都不剩時沒有下一則，而那段對話仍留在清單上（「PM 的判斷」第 1 項）。
- **選項**：(a) 沿用「還沒說話」—— 不用新文案，但那句話不是真的。(b) 新文案。
- **裁決**：(b)，確切字串「（訊息已刪除）」（全形括號）。
- **落實**：`spec.md` §4.3；任務 1 驗收 1；`features.md` 歷史-05。

### D4 別份規格裡字面對不起來的條文 → (a) 現在不改

- **為什麼問**：`conversation-search` §1.1 的「不得對訊息做任何層級的過濾」與本輪的「已刪除的訊息搜不到」都是使用者裁決，PM 不得自己選一邊，也不能動別的 slug。
- **選項**：(a) 現在不改，下次修訂時照清單改（比照 `conversation-store-db` 的 D4）—— 零成本，字面矛盾留一段時間。(b) 現在各開一輪只改條文 —— 兩輪 PM 工作。(c) §1.1 優先、已刪除的仍搜得到 —— 推翻本輪裁決 7 的搜尋那一半。
- **裁決**：(a)。本輪的行為以本規格為準；`features.md` 與架構文件反映新行為。
- **落實**：上面的「跨規格衝突清單」；`spec.md`「明確不做」最後第二列。

## PM 的判斷

**這十項不是使用者裁決。** 它們是使用者沒有明講、PM 依裁決推出來或補上的，都已寫進 `spec.md`。使用者經由主對話看過這份清單，沒有提出異議，也沒有逐項認可。日後使用者對其中任何一項有不同意見，那是一次正常的修訂，不是推翻裁決。

1. **「你說的話」全部被刪掉的對話，仍然留在歷史清單上、照常存檔**（§4.5）。照現行「沒有任何你說的話 ＝ 空白對話 ＝ 不存」的字面套用，刪光自己的話再切走，整段對話連同原文會從手機上消失，與裁決 6 牴觸。
2. **除了「生成中的那一則」與「佔位本身」，每一則都可以長按**，包含開場白、「出錯了：…」、「（這次沒有產生回覆…）」（§1.2）。依據：裁決只開了一個例外；開場白本來就不送給模型。
3. **對方還在生成時，別的訊息照常可以長按、刪除、復原**（§1.4）。依據同上。代價：生成途中的刪除會第一次讓「生成中的對話」被存下來，那個瞬間行程被結束時留下什麼放進了「明確不做」。另一個做法是「生成中整個清單都不能長按」，規則更簡單。
4. **刪除不再問一次**（§3.1）。
5. **佔位留在原位、靠原本那一邊、看不到任何原文；佔位長按沒有反應**（§3.2、§1.5）。
6. **被中斷的回覆刪除再復原，標記還在，文字一字不差**（§3.3）。
7. **選單上恰好兩項「複製」「刪除」**（§1.1）。
8. **複製沒有 App 自己的「已複製」提示**（「明確不做」）。
9. **「搜尋結果點進對話時命中的訊息後來被刪」不需要規則**：那個情境在畫面上做不出來。
10. **送給模型的上下文：先拿掉已刪除的，再略過開頭的助理訊息**（§4.1）。
