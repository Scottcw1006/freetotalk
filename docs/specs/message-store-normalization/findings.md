# 待辦單：訊息儲存正規化

**這不是 bug 單，是一張還沒被拿起來的需求單。** 這個目錄沒有版號目錄＝還沒開工。拿起來時走 spec-flow 路線 A（新功能／重構）；**階段 0 的需求範圍已經跟使用者確認過**（見「使用者裁決」），可以直接進階段 1 叫 PM。

記錄日期：2026-09-18。記錄時的程式碼：分支 `message-copy-delete`，commit `3c65e4d`。

# 使用者要什麼（原話）

> 我要正規化 db 以及支援刪除、恢復訊息的功能，同時如果沒有特別需要，不要有第二個資料來源

拆開來是三件事：

1. **正規化資料庫**：訊息要是資料庫裡自己的列，不是打包在對話那一列裡的一段 JSON。
2. **刪除、恢復訊息的功能要在新結構上照樣成立**：這個功能已經存在（`docs/specs/message-copy-delete/`，現行版的行為規格全部要繼續成立），刪除狀態要變成真正的資料庫欄位，不是 JSON 裡的一個鍵。
3. **沒有特別需要，就不要有第二個資料來源。**（意思見下面「使用者裁決」第 1–3 條。）

# 使用者裁決（2026-09-18，階段 0 已確認）

以下每一條都是使用者裁決，PM 照辦，不重新提問。

1. **單一資料來源的意思**：一則訊息的全部資料（文字、作者、時間、**刪除狀態**）都要是資料庫裡正規的列與欄位，**不得有一部分藏在 JSON 裡**。使用者要避免的就是 `message-copy-delete` 那一輪的形狀（刪除狀態記在 `messages` 那段 JSON 裡）。正規化之後舊的 `messages` JSON 欄位不得留著當第二份。
   - 使用者原話：「我想避免的是這次實作的情況，message 在 db，但 deleted 的訊息在 json，等於同一個資料分開兩邊存。」（RD 註：現況其實是訊息與刪除狀態**都**在同一段 JSON 裡，不是分開兩邊；已向使用者說明，意圖不受影響。）
2. **記憶體暫存可以**：App 執行中為了加速而放在記憶體的暫存，使用者沒有意見。
3. **生成中的回覆先不進資料庫**，使用者沒有意見 —— 它是被承認的例外，收尾（或停止、切走）時才寫入。「生成到一半行程被結束留下什麼」因此維持現狀，不在這一輪。
4. **這一輪包含 migration**：既有資料要搬過去（每一列的 JSON 拆成訊息列，`"deleted":true` 要帶過去）。
5. **資料庫不測試的裁決不變**（`conversation-store-db` 的 D1、D2 照舊：資料庫層不加自動化測試、產品程式碼不加測試專用入口）。
   - 後果（RD 註，PM 寫驗收時要處理）：搬遷與「多指令存檔整筆生效」都只能靠裝置上的驗收守 —— 用舊版建置造資料（含已刪除的訊息、以中斷標記結尾的回覆、解不開的一列）→ 覆蓋安裝 → 逐則比對。能抽成不開資料庫的純邏輯的部分（舊 JSON → 訊息列的轉換）仍可以、也應該有 JVM 測試。
6. **`fallbackToDestructiveMigration` 拿掉**（升版與降版兩個都拿掉）。以後漏寫搬遷時，資料庫開不起來、資料不動，由現有的「開不起來」那條路接住（不閃退、提示「目前讀不到之前的對話紀錄（紀錄沒有被刪除）…」），補上搬遷的下一版救得回來。
   - RD 註：`ConversationRepository` 的 `meansStoreIsDamaged` 目前把「Room 認不得的結構」歸在「內容壞了 → 丟掉重來」；拿掉 fallback 之後，「缺搬遷」必須落在「開不起來 → 不動」那一邊，否則等於從另一條路把資料清掉。這一點要有驗收條文。
7. **範圍包含歷史清單與搜尋**：改成查資料庫，不再把每段對話的所有訊息整份讀進記憶體。
8. **降版不管**：新版寫的資料被舊版讀，壞了就壞了，不做任何保證。

## 裁決之間留給 PM 處理的接縫

- **搜尋 × 生成中的回覆**：搜尋-15 規定「此刻正在生成中的回覆也搜得到」，而裁決 3 讓它不在資料庫裡。搜尋結果因此是「資料庫查到的＋記憶體裡那一則生成中的回覆」；怎麼合、兩邊的比對規則怎麼保證是同一套（現在只有一套，在 `chat/ConversationSearch.kt`，有大量 JVM 測試：大小寫、全形半形、空白攤平、片段與標示位置），是這一輪最大的設計問題。把比對搬進 SQL 會讓那套規則出現第二份實作 —— 這正是 `plan/architecture.html`「什麼算命中，只有一個地方說了算」在防的事。
- **從來沒說過話的對話**（只有開場白）：現行規則是不存，但畫面上看得到、搜得到。使用者沒有對它單獨裁決；照裁決 2 的精神它可以留在記憶體，PM 判斷後寫進規格，有疑慮再升級。
- **`conversation-search` §1.10「搜尋全程不產生檔案讀寫」**：搜尋改查資料庫之後，這條的字面要改（讀是必然的；「不寫」仍然成立）。

# 現況與診斷

- **一張表，一段對話一列，訊息是 JSON。** `conversations` 表的 `messages` 欄位是整段對話的訊息陣列（`data/ConversationRecords.kt:27-35`、`:91`）；已刪除的訊息在自己的 JSON 物件上多一個 `"deleted":true`，未刪除時不寫這個鍵。結構匯出在 `app/schemas/`（目前只有版本 1）。
- **DAO 只有四個單一指令**（`data/ConversationDatabase.kt:17-32`），檔頭註解寫明「每次寫入只有一個指令」是承重的，拆成多個指令必須同時補上交易與測試。
  - RD 的看法：這個理由說過頭了。原本的 bug（對話從清單上消失）來自檔案的「先清空再寫」；資料庫交易（Room 的 `@Transaction`）一樣能讓多個指令整筆生效。不拆表的真正原因是下面兩條。
- **結構版本對不上就整個清掉重來**：`data/ConversationRepository.kt:131-132` 的 `fallbackToDestructiveMigration`。這個專案**從來沒寫過資料庫搬遷**。正規化一定要升結構版本，沒有搬遷的話每個升級的使用者會失去全部對話，並看到「之前的對話紀錄讀不出來，已經清空…」—— 違反 `message-copy-delete` 的 D2 裁決精神（保護既有資料）。
- **資料庫層沒有自動化測試，產品程式碼不加測試專用入口**：`conversation-store-db` 的 D1、D2 使用者裁決。正規化會讓存一段對話變成多個指令＋交易，並且第一次需要搬遷；**這兩樣在沒有測試的情況下做，風險由誰承擔要重新裁決**。
- **讀取是整份讀進記憶體**：歷史清單只需要標題與預覽，卻把每段對話的所有訊息都讀出來解析（`ConversationRepository.kt:71` 的 `all`）；搜尋在記憶體裡比對全部對話。幾十段沒感覺，幾百段長對話時啟動與每次狀態變動都會變慢。正規化之後這裡有機會改成只查需要的欄位 —— 但那是不是這一輪的範圍要先決定。
- **每次存檔是整段重寫**：回覆收尾、按停止、切走、刪除或復原一則訊息（`chat/ChatViewModel.kt` 的 `persist`）。正規化之後「刪除一則」可以變成只更新一列。

# 還沒回答的問題

1. 解不開的舊資料列（JSON 壞掉、`author` 不認得）搬遷時怎麼辦。現行讀取規則是「只丟掉它自己、其餘照常」；搬遷時是跳過它（那段對話從此消失）、還是原樣留在某處。RD 傾向跳過，與現行行為一致；由 PM 判斷要不要升級。
2. 要不要先量「整份讀進記憶體」在多少段對話時開始有感，當作這一輪效能驗收的基準；還是只驗行為不驗速度。
