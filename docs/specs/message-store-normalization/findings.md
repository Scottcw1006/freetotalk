# 待辦單：訊息儲存正規化

**這不是 bug 單，是一張還沒被拿起來的需求單。** 這個目錄沒有版號目錄＝還沒開工。拿起來時走 spec-flow 路線 A（新功能／重構），從階段 0 開始；下面是階段 0 已經知道的事，省掉重新摸索。

記錄日期：2026-09-18。記錄時的程式碼：分支 `message-copy-delete`，commit `3c65e4d`。

# 使用者要什麼（原話）

> 我要正規化 db 以及支援刪除、恢復訊息的功能，同時如果沒有特別需要，不要有第二個資料來源

拆開來是三件事：

1. **正規化資料庫**：訊息要是資料庫裡自己的列，不是打包在對話那一列裡的一段 JSON。
2. **刪除、恢復訊息的功能要在新結構上照樣成立**：這個功能已經存在（`docs/specs/message-copy-delete/`，現行版的行為規格全部要繼續成立），刪除狀態要變成真正的資料庫欄位，不是 JSON 裡的一個鍵。
3. **沒有特別需要，就不要有第二個資料來源。**

## 第 3 點有兩種讀法，開工前要先問清楚（階段 0 的事，不要交給 PM 猜）

- **讀法 A（RD 認為比較可能）**：資料庫是對話內容的唯一來源。今天不是 —— 架構文件明寫「資料庫仍然不是唯一的來源」：開著的那段對話與正在串流的回覆只在記憶體裡，搜尋比對的是「記憶體裡開著的那段＋資料庫來的歷史清單」合併去重的結果（`chat/Conversation.kt` 的 `ChatUiState.allThreads`；`plan/architecture.html`「比對的是記憶體裡的對話，不是存下來的」）。照這個讀法，畫面、歷史清單、搜尋都該從資料庫讀，記憶體只留「特別需要」的東西。
- **讀法 B**：同一件事不要存兩份 —— 例如正規化之後，刪除狀態不得同時留在舊的 JSON 與新的欄位裡；舊的 `messages` 欄位要拿掉，不是留著當備份。

兩種讀法不互斥，可能兩個都要。

## 照讀法 A，哪些東西「有特別需要」留在記憶體，要逐一裁決

- **正在串流的回覆**：每秒變好幾次。每個片段都寫資料庫是一種做法（那樣「生成到一半被殺掉行程」會留下半截回覆，要同時決定它的樣子 —— `message-copy-delete` 的「明確不做」與 `stop-generation` 都指著這個洞）；只留在記憶體、收尾才寫是另一種（那就是一個被承認的第二來源，搜尋-15「生成中的回覆也搜得到」要靠合併才成立）。
- **從來沒說過話的對話**（只有開場白）：現行規則是不存（`conversation-search` §9.1、`conversation-store-db` §1.2；`data/ConversationRecords.kt:50`）。它在畫面上看得到、搜得到（搜尋-15），卻不在資料庫裡 —— 這是今天第二來源存在的另一個理由。要嘛改成存下來再於離開時清掉，要嘛承認它是例外。
- **查詢字串、引擎狀態、提示**：不是對話內容，不算在內（RD 判斷；請使用者確認）。

# 現況與診斷

- **一張表，一段對話一列，訊息是 JSON。** `conversations` 表的 `messages` 欄位是整段對話的訊息陣列（`data/ConversationRecords.kt:27-35`、`:91`）；已刪除的訊息在自己的 JSON 物件上多一個 `"deleted":true`，未刪除時不寫這個鍵。結構匯出在 `app/schemas/`（目前只有版本 1）。
- **DAO 只有四個單一指令**（`data/ConversationDatabase.kt:17-32`），檔頭註解寫明「每次寫入只有一個指令」是承重的，拆成多個指令必須同時補上交易與測試。
  - RD 的看法：這個理由說過頭了。原本的 bug（對話從清單上消失）來自檔案的「先清空再寫」；資料庫交易（Room 的 `@Transaction`）一樣能讓多個指令整筆生效。不拆表的真正原因是下面兩條。
- **結構版本對不上就整個清掉重來**：`data/ConversationRepository.kt:131-132` 的 `fallbackToDestructiveMigration`。這個專案**從來沒寫過資料庫搬遷**。正規化一定要升結構版本，沒有搬遷的話每個升級的使用者會失去全部對話，並看到「之前的對話紀錄讀不出來，已經清空…」—— 違反 `message-copy-delete` 的 D2 裁決精神（保護既有資料）。
- **資料庫層沒有自動化測試，產品程式碼不加測試專用入口**：`conversation-store-db` 的 D1、D2 使用者裁決。正規化會讓存一段對話變成多個指令＋交易，並且第一次需要搬遷；**這兩樣在沒有測試的情況下做，風險由誰承擔要重新裁決**。
- **讀取是整份讀進記憶體**：歷史清單只需要標題與預覽，卻把每段對話的所有訊息都讀出來解析（`ConversationRepository.kt:71` 的 `all`）；搜尋在記憶體裡比對全部對話。幾十段沒感覺，幾百段長對話時啟動與每次狀態變動都會變慢。正規化之後這裡有機會改成只查需要的欄位 —— 但那是不是這一輪的範圍要先決定。
- **每次存檔是整段重寫**：回覆收尾、按停止、切走、刪除或復原一則訊息（`chat/ChatViewModel.kt` 的 `persist`）。正規化之後「刪除一則」可以變成只更新一列。

# 拿起來時要先回答的問題（給使用者／PM）

1. 第 3 點是讀法 A、B，還是兩者都要；讀法 A 底下那幾項「特別需要」逐一裁決。
2. **既有資料**：搬遷（把每一列的 JSON 拆成訊息列；`"deleted":true` 要帶過去；解不開的那一列怎麼辦 —— 現行規則是只丟掉它自己），還是像上一次改儲存那樣不搬。RD 建議搬：這次使用者手上已經有帶刪除狀態的資料。
3. **資料庫層的測試**：D1／D2（不加自動化測試、不加測試專用入口）要不要為這一輪鬆綁。至少需要：一支搬遷測試（舊結構的資料庫檔 → 新結構，內容逐則相同）、一支「存檔整筆生效」的測試。
4. `fallbackToDestructiveMigration` 要不要留。留著＝以後任何人漏寫一次搬遷就清掉使用者全部對話；拿掉＝漏寫搬遷時 App 開不起資料庫（現有的「開不起來」那條路會接住：不刪、告知）。
5. **範圍**：只換儲存形式、對外行為完全不變；還是一併把歷史清單與搜尋改成查資料庫（讀法 A 幾乎必然帶出這一項）。
6. 降版（新版寫的資料被舊版讀）要不要有任何保證。今天沒有。
