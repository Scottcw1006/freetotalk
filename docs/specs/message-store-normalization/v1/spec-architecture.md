# 架構決策（訊息儲存正規化 spec 的第四節）

> 入口與檔案地圖見 `spec.md`。
>
> **這一整份是給 RD 的建議，不是裁決。QA 不驗這一節。** 你用了不一樣的做法、滿足了 `spec.md` 的行為規格、也通過了 `spec-tasks.md` 的驗收 —— 那就是完成，不是缺陷。**若你決定不照這裡的某一條走，請寫進 slug 根目錄的 `pm-inbox.md`**，講一句為什麼。
>
> 這裡只放說得出使用者後果的幾條；每一條的理由就是那個後果。Room 是既定的（`docs/specs/conversation-store-db/spec-architecture.md` §I）；表怎麼命名、欄位叫什麼、類別怎麼切，都是你的判斷。

## §A.1 存一段對話的多個指令，包在一個交易裡

- **理由（使用者後果）**：先清掉舊的訊息列、再寫入新的，若是各自生效的步驟，中間那一瞬間讀清單或搜尋的人會讀到「對話在、訊息不在」或一半的訊息 —— 形狀與當年「先把檔截成空的再寫入」一模一樣，被切走的那一段會暫時從清單或搜尋上消失（`spec.md` §2.2）。回覆還在生成時切換，同一段會被幾乎同時存兩次，這個並發是每天都在發生的。
- **這一層沒有自動化測試**（裁決 5），所以這一條沒有任何測試在守；請在資料層的程式碼註解裡寫明「哪幾個指令必須在同一個交易裡、為什麼」，把現在那句「每次寫入只有一個指令」換掉。
- **一個 Room 特有的坑**：若訊息列用外鍵連到對話列並設定連帶刪除，而對話列仍用「衝突時取代」的方式寫入 —— 取代在資料庫裡是「先刪再插」，會觸發連帶刪除，**每存一次檔就把那一段的訊息清光**。對話列請用更新或「有則更新、無則新增」的寫法。

## §A.2 一則訊息的身分是「哪一段 ＋ 訊息 id」；順序要有欄位可依

- **理由**：訊息 id 每一段各自從 0 起算、跨段會撞號（`spec.md`「這次會踩到的既有事實」第 8 條）。只拿訊息 id 當鍵，第二段對話的開場白會蓋掉第一段的。
- App 自己寫出來的 id 在一段之內一定遞增，所以「依 id 排序」就是畫面順序；另立一個位置欄位也可以。選哪一個，請寫進架構文件讓 QA 知道依哪個欄位排（`spec-tasks.md` 任務 7 驗收 3）。
- **刪掉一段對話時訊息一起刪**（`spec.md` §2.4）：外鍵連帶刪除、或同一個交易裡兩個刪除指令，都可以。孤兒訊息列的後果不只是原文留在手機上 —— 搜尋改查訊息之後，它們會變成點不開的命中。
- **RD 採用的形式（記錄）**：順序另立位置欄位；沒有外鍵，刪一段對話是同一筆交易裡兩個刪除指令。理由：連帶刪除只在開了外鍵的連線上發生，從 App 以外改資料庫的人不會開；也避開 §A.1 那個「取代觸發連帶刪除」的坑。**連帶的後果**：從 App 以外刪一段對話時，要自己連訊息列一起刪，否則會留下孤兒（`plan/architecture.html` 的驗收用說明要寫到這一點）。

## §A.3 搬遷：用 Room 的搬遷機制，在一個交易裡做完；轉換呼叫純邏輯的那一份

- **理由**：
  - 搬遷途中失敗要停在搬遷前的樣子（`spec.md` §3.4）。Room 的搬遷本來就包在交易裡；不要在搬遷裡自己提交或分段提交。
  - **不要用「另建一個資料庫檔、把資料倒過去、刪掉舊檔」的方式做**：App 是從「資料庫被重新建立了一次」認出「清掉重來」的，那樣做會讓每個升級的使用者看到「…已經清空，從這裡重新開始。」（「這次會踩到的既有事實」第 4 條）。
  - 舊結構的每一列逐列轉換、逐列接住失敗：一列解不開只略過它（§3.3）。任何一列讓搬遷丟出例外，後果是整個資料庫開不起來、每一段都讀不到。寫入訊息列之前先擋掉重複 id（任務 1 驗收 2），不要讓資料庫的唯一性限制去擋。
  - 逐列轉換用的必須是任務 1 測過的那一份；搬遷裡另寫一份 SQL 版的拆解（例如用資料庫內建的 JSON 函式），JVM 測試就什麼都沒守到。
- 拿掉舊欄位在 SQLite 上通常要「建新表、搬資料、刪舊表、改名」；匯出的結構檔（`app/schemas/`）要有新版本的那一份，QA 以它為準。
- **Room 的搬遷測試工具不在本輪範圍**（裁決 5）。日後要補時，起點在 `docs/specs/conversation-store-db/spec-appendix.md`「查證：資料庫能不能在 JVM 單元測試裡跑」。

## §A.4 缺搬遷的錯誤，要落在「開不起來」那一邊

- **理由**：`spec.md` §4.1。拿掉兩個方向的「對不上就清掉」設定之後，缺搬遷（或儲存的版本比建置新）時 Room 會丟出錯誤；這個錯誤若被判斷「儲存是不是壞了」的地方算成壞了，資料就從那條路被清掉。
- 依 Room 的行為，缺搬遷的錯誤訊息與那個判斷現在比對的「結構驗證不過」那一句不同，所以應該自然落在開不起來 —— **沒有人實際跑過**，請實際造一次確認（`spec-tasks.md` 任務 4 驗收 2 的突變建置就是這個造法）。
- **「結構驗證不過」那一句（改了結構卻沒升版本號時出現）要不要留在「壞了」的清單裡，規格不規定，由你判斷。** 使用者的裁決是：那是開發時的實作錯誤，不是規格要列舉的情形。
- 判不出來就當成開不起來（`docs/specs/conversation-store-db/spec-architecture.md` §G.2 的原則不變）。「偵測到資料庫被重新建立」那個記號照舊；結構搬遷不會重新建立資料庫，不該觸發它。
- **RD 採用的形式（記錄）**：「結構驗證不過」那一句留在「壞了」的清單裡不動；缺搬遷與版本比建置新都不會落進它（後者 RD 實測過，前者依 Room 的訊息確認，仍待任務 4 驗收 2 的突變建置在裝置上看到）。

## §A.5 歷史清單：查詢只取每一列要顯示的；標題與預覽的規則不要有第二份

- **理由**：`spec.md` §5.1、§5.4。清單需要的是每一段的對話欄位，加上「第一則沒被刪的你說的話」「最後一則沒被刪的訊息」「有沒有任何一則你說的話（含已刪除）」這三樣 —— 最後一樣是分辨「（訊息已刪除）」與「還沒說話」用的。
- 「取哪一則」放進查詢是合理的，但那就是「已刪除的訊息當作不存在」的第二個落點，而且 JVM 測試看不到它；截短（以使用者看到的一個字為單位）請繼續用既有的那一份純邏輯，不要在查詢裡截。
- **不建議把標題、預覽存成對話列上的欄位**：那是從訊息算得出來的第二份（`spec.md` §1.2），刪除、復原、收尾、停止每一條路都要記得更新它。真的要存，寫進收件匣並在架構文件裡寫明。

## §A.6 搜尋：開著的那一段走記憶體，其餘走資料庫；資料庫那一半不要跟著每一次狀態變動重查

- **做法已拍板**（`spec.md` §6.6、§6.7）：輸入停下來 250 毫秒之後，資料庫把存下來的訊息逐批交出來，交給現有那一份比對規則，比完就放掉。幾點提醒：
  - **逐批的意思是不要一次把整張訊息表讀成一個清單**；用游標或分頁，一批比完再要下一批。命中的那幾則才需要留下（片段與標示算完之後，連原文都不必留）。
  - **250 毫秒的等待請做成測試控制得了時間的樣子**（任務 6 驗收 1 (iv)）；它管的是整個搜尋，不只是資料庫那一半，而且只管「輸入框內容改變成一個非空的查詢」這一種觸發；**清空不走這段等待**，當下就回到未搜尋狀態，並取消還在等、還在跑的那一次（`spec.md` §6.7）。
  - **前一次搜尋還在讀的時候查詢又變了，請把它取消**，不要讓兩次全表讀取疊在一起。
  - **開著的那一段從資料庫那一半扣掉、改用記憶體那一份**，合併之後再排序（`docs/specs/conversation-search/spec.md` §3.5 的先後不變）。
  - **資料庫那一半只在「查詢字串變了」或「儲存有變動」時重查**；回覆串流時每秒好幾次的狀態變動，只需要重算記憶體那一半。理由：現在的結果是每一次狀態變動都重算一次全部，搬到資料庫之後照抄這個節奏，串流中的搜尋會讓資料庫每秒被掃好幾次。
  - **晚到的結果要丟掉**：查詢變了之後，前一個查詢還沒回來的結果不得蓋上來（`spec.md` §6.5）。
  - **決定什麼算命中、片段與標示的，仍然只有比對純邏輯那一份。** 資料庫可以負責「把訊息交出來」，不能負責「判斷命中」—— 它內建的比對不認得全形、不收合空白、大小寫只管 ASCII（`spec.md` §6.3）。
- 搜尋結果的每一個分組目前帶著完整的對話物件，畫面只用到它的 id、人格、模型、時間。分組改成只帶這幾樣，資料庫那一半就不必為了畫標頭而讀出整段對話。
- **RD 採用的形式（記錄）**：每 20 段對話一批讀出整段，比完只留命中；分組仍帶著對話物件，但資料庫來的那一半把它的訊息清單清空（每段最多三則命中各自帶著那一則的原文）。資料庫那一半全部比完才與記憶體那一半一起出結果，中途不顯示部分結果。

## §A.7 刪除與復原一則可以只更新一列，但要接住「那一段還沒存過」

- **理由**：`docs/specs/message-copy-delete/spec.md` §6.1「刪除與復原當下就存下來」。一段對話的第一句剛送出、回覆還在生成時，它還沒進資料庫；這時刪除開場白，「更新那一列」不會動到任何東西，刪除狀態就只在記憶體裡。退回「整段存一次」、或等收尾那一次存檔一起帶上，都可以；後者要確認收尾那次存的是含刪除狀態的版本。
- 存檔失敗的提示、空白對話不寫的規則，請讓這條路與其他存檔走同一個入口（那份規格的 §A.3 建議不變）。
- **RD 沒有採用「只更新一列」**：刪除與復原仍是整段存一次（一筆交易）。每一種改變走同一條路，`spec.md` §2.3 自然成立，「那一段還沒存過」也不必另外接。本條因此只在日後有人把它改成只更新一列時才適用。代價：長對話裡刪一則也要重寫那一段的每一列，目前的對話長度下可以接受。

## §A.8 讀取要一段一段容錯；不要讓資料庫程式庫直接把作者欄位映射成列舉

- **理由**：`spec.md` §2.5。一次查詢把訊息列直接映射成帶列舉的物件時，一列不認得的作者會讓整個查詢丟例外 —— 使用者看到的是整份歷史不見，或搜尋整個壞掉。讓資料庫交出原始的字串，解析與容錯留在純邏輯裡（任務 1 驗收 4 測的就是那一份），與現行做法相同。
- 在結構上用限制條件直接擋掉不認得的作者值也可以；那樣 §2.5 的那種壞資料就寫不進去，請在架構文件裡寫明（任務 7 驗收 3）。
