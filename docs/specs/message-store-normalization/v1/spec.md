# 功能總覽

## 使用者看到什麼

- **平常什麼都沒變。** 聊天、停止、切換、歷史抽屜、搜尋、長按複製、刪除與復原 —— 每一樣的畫面與行為都與本輪之前相同。
- **升級上來的那一次**：原本的每一段對話都在，順序與時間不變；已刪除的訊息仍是「已刪除的對話（復原）」，點復原得到的原文一字不差；被中斷的回覆結尾的標記還在；App 回到上次離開的那一段。不出現任何「讀不出來」「讀不到」的提示。
- **App 的版本與手機上紀錄的格式對不起來時**（開發上漏寫了搬遷；或日後從更新的版本裝回這一版）：紀錄**不會被清掉**。App 不閃退、照樣能聊天，告訴你「目前讀不到之前的對話紀錄（紀錄沒有被刪除）…」；裝上補好的版本之後紀錄就回來。
- **對話很多的時候**：打開 App、打開抽屜、搜尋，不再需要先把每一段對話的每一則訊息都讀進記憶體。
- **搜尋打字時**：結果不再每按一個鍵就變一次，而是**打字停下來約四分之一秒之後**才更新；仍然沒有搜尋鈕，不必按任何東西。

## 系統被切成哪幾塊

| 這一塊 | 負責回答什麼問題 | 邊界 |
|---|---|---|
| **對話儲存**（改寫） | 存下來的對話與訊息有哪些；一次存檔整筆生效；歷史清單每一列需要的東西；一段對話的完整內容；搜尋時把存下來的訊息逐批交出去；有變動就通知 | 只知道存下來的東西；不知道哪一段開著、不知道生成中的回覆；**不決定什麼算命中** |
| **舊資料轉換**（新，純邏輯） | 舊結構的一列 → 新結構的一段對話加它的訊息列，或「這一列解不開」 | 不開資料庫、不依賴 Android，可被 JVM 測試直接呼叫 |
| **結構搬遷**（新） | 升級時把舊結構的每一列交給舊資料轉換、寫成新結構、丟掉舊形式 | 只在結構版本前進時跑一次；整筆生效 |
| **儲存故障的分類**（修改） | 這次失敗是內容壞了（清掉重來）還是開不起來（不動）；**結構版本對不上歸後者** | 提示文字與畫面表現不變 |
| **比對純邏輯**（既有，不改規則） | 什麼算命中、片段、標示、計數 | 仍然是唯一的答案來源 |
| **搜尋的組裝**（修改） | 輸入停下來夠久了沒有；開著的那一段（記憶體）＋資料庫裡其他每一段 → 交給比對純邏輯 → 結果 | 不自己比對 |
| **歷史清單的組合**（修改） | 抽屜上列哪些對話、每一列顯示什麼 | 每一列的標題與預覽仍由既有的標題／預覽規則回答 |
| **聊天狀態**（既有） | 開著哪一段、那一段此刻的內容（含還沒存的與生成中的）、什麼時候存 | 存檔時機本輪不改 |

## 資料怎麼從一塊流到另一塊

```
送出／收尾／停止／切走／刪除或復原一則
  → 聊天狀態更新記憶體裡開著的那一段 →（既有的時機）交給對話儲存
  → 對話儲存把那一段寫成「一列對話 ＋ 它的訊息列」，整筆生效 → 發出「有變動」
  → 歷史清單：資料庫裡的每一段（只取每一列要顯示的）− 開著的那一段
  → 搜尋（輸入停下來 250 毫秒之後才開始）：
          開著的那一段（記憶體，含未存的與生成中的）
          ＋ 資料庫裡其他每一段的訊息（逐批讀出、比完就放掉）
          → 同一份比對純邏輯 → 結果

升級後第一次啟動
  → 打開資料庫 → 結構搬遷：舊結構每一列 → 舊資料轉換 → 新結構（解不開的那一列略過）
  → 之後一切照上面

打開資料庫時結構版本對不上（缺搬遷、版本比 App 新）
  → 歸「開不起來」：不動資料、告知、下次啟動再試
```

## 這次會踩到的既有事實

每一條都寫了它為什麼影響這次要做的事。系統層級的描述在 `plan/architecture.html`，這裡不重複。

1. **未刪除的訊息，在舊結構的 JSON 裡沒有 `deleted` 這個鍵；只有已刪除的才有 `"deleted":true`。** 沒用過刪除的對話，存出來與更早（還沒有刪除功能）的版本逐字相同。→ 舊資料轉換必須把「沒有這個鍵」讀成未刪除（§3.1）；一份舊資料同時涵蓋了「有刪除功能的上一版」與「更早的版本」兩種來源。
2. **資料庫現在設定成「結構版本對不上又沒有對應的搬遷時，整個清掉重來」，升版與降版兩個方向都是；這個專案從來沒寫過資料庫搬遷。** 清掉時會出現「之前的對話紀錄讀不出來，已經清空…」。→ 本輪一定要升結構版本；沒有搬遷的話每個升級的使用者失去全部對話（§3）。裁決 6 要求兩個方向的設定都拿掉（§4）。
3. **「內容壞了 → 清掉重來」的判斷，認的是 Android 回報的損毀、連線被損毀處理關掉，以及 Room 的一句錯誤訊息（結構驗證不過的那一句）；其餘的失敗一律當成開不起來。** → 拿掉第 2 條的設定之後，缺搬遷時 Room 會丟出錯誤；那個錯誤必須落在「開不起來」那一邊，不得被這個判斷算成壞了（§4.1）。依 Room 的行為，缺搬遷的錯誤訊息與那一句不同、會落在開不起來 —— **這一點我與 RD 都是依 Room 的文件與原始碼推的，沒有在這個專案裡實際跑過**；任務 4 的兩條驗收就是把它變成看得到的結果。
4. **App 是從「資料庫被重新建立了一次」認出「清掉重來」發生過的**（記號在偏好裡）。→ 搬遷若用「另建一個資料庫檔、或把檔刪掉重建」的方式做，升級後第一次打開會誤報「…已經清空…」，違反 §3.1。
5. **「一次存檔整筆生效」現在唯一的保證是「每次寫入只有一個指令」**，資料層的檔頭註解與 `conversation-store-db` 都寫明改成多個指令時要同時補回交易與測試。→ 正規化之後存一段對話必然是多個指令。使用者已知情裁決仍不測資料庫層（裁決 5），所以 §2.2 只剩裝置上的驗收與架構建議在守；缺口寫在 §2.2 旁與 `spec-tasks.md`「明確不做」。
6. **歷史清單與搜尋現在吃的是同一份「每一段對話的完整內容」**：儲存把每一列整份讀出來解析，狀態裡的歷史清單是完整的對話物件，搜尋結果在狀態送出去的路上同步算出來（回覆串流時每秒重算好幾次）。→ 改查資料庫之後，資料庫那一半變成非同步：結果可能晚一步到、也可能亂序到（§6.5）；而「每一次狀態變動都重查一次資料庫」在串流時會很重（`spec-architecture.md` §A.6）。
7. **抽屜每一列的標題與預覽，是對完整的對話物件問出來的**，截短以使用者看到的一個字為單位。→ 清單不再持有完整對話之後，「取哪一則」很可能搬進查詢裡 —— 那一半 JVM 測試看不到，只有裝置上的驗收在守（§5.1）。
8. **訊息 id 在每一段對話裡各自從 0 起算，不同對話會撞號；下一則的 id 是「那一段裡最大的 id 加一」；順序現在就是 JSON 陣列的順序。** App 自己寫出來的 id 一定遞增（中間可能有缺號：零文字停止的回覆被移除）。→ 新結構裡一則訊息的身分是「哪一段 ＋ id」；順序要有欄位可依（§1.1）；從 App 以外寫進來的舊資料可能有重複 id，不處理的話會讓整個搬遷失敗（§3.3）。
9. **刪除與復原一則訊息的存檔，現在是把整段重寫一次。** 對方還在生成時刪除別則訊息，會把生成到一半的回覆（沒有中斷標記）與剛送出、還沒到存檔時機的那一句一起存下來。→ 改成「只更新那一列」時，一段**還沒存過**的對話（第一句剛送出、回覆還在生成）沒有列可以更新；`docs/specs/message-copy-delete/spec.md` §6.1「刪除與復原當下就存下來」對它仍然適用（`spec-architecture.md` §A.7）。那個瞬間行程被結束時半截回覆留下什麼，仍然不定義（`spec-tasks.md`「明確不做」）。
10. **讀取時，認不得的人格或模型名稱會退回預設值；認不得的訊息作者沒有退回，整段讀不起來。** → 驗收的測資要避開退回值（`docs/specs/conversation-store-db/spec-tasks.md`「測資與讀取的約定」裡「比對的值，不得等於 App 讀不懂時會退回的值」，本輪照用）；「一段讀不起來」在新結構上仍要造得出來（§2.5）。
11. **`docs/specs/message-copy-delete/` 現行版新增或改寫的幾條驗收還沒有被任何一輪執行過**（它的 `spec-appendix.md`「驗收狀態」列了是哪幾條）。→ 本輪換掉的正是它們底下的儲存；回歸任務整組重跑那份規格的裝置端驗收，不假設它們已經成立（`spec-tasks.md` 任務 8）。
12. **在模擬器上一次生成通常只有數秒；APK 很大，覆蓋安裝前資料分割區要有足夠空間；舊版建置要在專案以外的暫存目錄 clone 出來建**（`docs/qa-environment.md` 有現成的做法與已知的坑）。→ 升級驗收（`spec-tasks.md` 任務 2）的前置與「做不到時怎麼記」照這些寫。

# 行為規格

QA 主要照這一節寫測試。**用語**：
- **儲存**：App 存對話的資料庫。**儲存的內容**：App 停止時從 App 以外唯讀地讀出來的每一段對話的每一個欄位、每一則訊息的每一個欄位（怎麼讀見 `spec-tasks.md`「測資與讀取的約定」）。
- **開著的那一段**：聊天畫面上此刻那段對話在記憶體裡的版本。
- **已刪除**：一律指「已刪除且尚未復原」。**逐碼位相同**：兩個字串的每一個 Unicode 碼位、順序、數量都相同。
- **解不開**：見 §3.3 的定義。

## §1 資料庫裡的一則訊息

**§1.1 一則訊息的每一樣資料，都是資料庫裡一個正規的欄位。**（裁決 1）
- 每一則已存下的訊息是資料庫裡自己的一列。這一列上各有欄位記下：屬於哪一段對話、訊息 id、作者、文字、建立時間、**刪除狀態**。同一段對話裡訊息的先後順序，由欄位的值決定（依某個欄位排序就得到畫面上的順序）。
- **刪除狀態每一列都有明確的值**，從資料庫直接看得出是「已刪除」還是「未刪除」；不是「缺了代表未刪除」。
- **整個資料庫裡沒有任何一個欄位裝著一則以上的訊息，也沒有任何欄位用打包格式（JSON 或其他）裝著訊息的一部分資料。** 舊結構裡裝整段訊息的那個欄位，在新結構裡不存在 —— 不留著當第二份，也不留空殼。
- 可判定：從 App 以外，用一般的 SQLite 工具、**只靠 SQL 查詢、不解析任何打包格式**，列得出指定一段對話的每一則訊息的 id、作者、文字、建立時間、刪除狀態，順序與畫面相同。
- 違反時：同一則訊息的資料分兩種形式存，正是使用者要避免的形狀；要看或要改一則訊息的刪除狀態就得解開整段。
- 守：`spec-tasks.md` 任務 2 驗收 1。

**§1.2 資料庫裡不另外存「從訊息算得出來的東西」，除非架構文件寫明它是什麼、為什麼需要。**（裁決「沒有特別需要，就不要有第二個資料來源」）
- 對話那一列上記的是對話自己的資料（id、人格、模型、建立時間、最後更新時間）。標題、預覽這類從訊息算得出來的東西，預設不存。
- **本輪的新結構裡沒有任何派生的欄位**：搜尋不另存整形後的文字（§6.6），標題與預覽查的時候才算（§5.1）。
- 日後真的需要存一樣派生的東西時，`plan/architecture.html` 要寫明：它是哪個欄位、由什麼算出來、為什麼非存不可、來源改變時怎麼保證它跟著變。
- 違反時：派生的那一份與訊息對不起來的那天，使用者看到的標題、預覽或搜尋結果與對話內容不符，而沒有人知道有第二份存在。
- 守：`spec-tasks.md` 任務 2 驗收 1 的後半（結構裡每一個欄位都說得出歸屬）；派生的東西與來源對不對得起來，由 §5.1、§6.3 的驗收守。

**§1.3 讀回來的，就是存進去的 —— 含刪除狀態。** 一段對話存下再讀回來（依 id 取、取清單、冷啟動後在畫面上看到的，都算）：對話 id、人格、模型、建立時間、最後更新時間，每一則訊息的 id、作者、文字、建立時間、刪除狀態與先後順序，都與存進去時相同。文字逐碼位相同，讀取時不做任何加工；讀回來的訊息沒有任何一則是「生成中」的樣子。
- 這是 `docs/specs/conversation-store-db/spec.md` §1.1「讀回來的，就是存進去的」與 `docs/specs/message-copy-delete/spec.md` §6.3「讀回來的刪除狀態，就是存進去的」在新結構上的樣子；測資的要求照那兩條。
- 守：`spec-tasks.md` 任務 1 驗收 4（不碰資料庫）；裝置上由任務 3 驗收 1、任務 8 驗收 3 守資料庫那一端。

**§1.4 記憶體裡可以有的只有兩種：開著的那一段，以及隨時可以從資料庫重新得到的暫存。**（裁決 2、3）
- **開著的那一段**含還沒到存檔時機的訊息與生成中的回覆；生成中的回覆到收尾、停止或切走才進資料庫。
- **從來沒說過話的對話（只有開場白）只活在記憶體裡**：不存、看得到、搜得到（§6.2），切走就不留 —— 與本輪之前相同。
- **暫存不得是任何資料唯一的所在**：任何已經過了存檔時機的改變（回覆收尾、停止、切走、刪除或復原一則），行程被結束之後冷啟動都還在。
- 違反時：使用者關掉 App 再打開，少了最後一輪對話、或刪除狀態不見了。
- 守：既有的三條各自守一個時機，本輪在回歸裡重跑 —— `spec-tasks.md` 任務 8 驗收 2（刪除與復原當下）、驗收 3（回覆收尾、停止、切走）。「生成到一半行程被結束時留下什麼」不定義（`spec-tasks.md`「明確不做」）。

## §2 存檔、刪除與整筆生效

**§2.1 每一個既有的存檔時機，在新結構上照樣把那一段存下來。** 回覆收尾、按停止、切走（開另一段、開始新的對話、換人格、換模型）、刪除或復原一則訊息的當下 —— 每一種之後，儲存的內容裡那一段就是畫面上那一段（§2.3）。存檔時機本輪不增、不減、不移動（`spec-tasks.md`「明確不做」）。
- 守：`spec-tasks.md` 任務 3 驗收 1；任務 8 驗收 2、3。

**§2.2 一次存檔是整筆生效的，即使它現在不只一個指令。** 任何時刻開始的讀取（歷史清單、搜尋、依 id 開啟、冷啟動續接）看到的每一段對話，都是**某一次存檔寫下的完整內容**：
- 不會看到「對話在、訊息不在」或只有一部分訊息；不會看到兩次存檔的訊息混在一起；
- 不論當下有沒有別的存檔正在寫同一段、同時有幾個在寫（回覆還在生成時切換，同一段會被幾乎同時存兩次相同內容）；
- 行程在存檔途中被結束 → 冷啟動後那一段是那次存檔之前或之後的完整版本。
- 違反時：被切走的那一段暫時從清單或搜尋上消失，或打開來少了幾則。
- **由哪一層守**：**沒有自動化測試**（裁決 5，使用者知情）。裝置上由 `docs/specs/conversation-store-db/spec-tasks.md` 任務 2 驗收 3「串流中切換，被切走的那段立刻在清單上」守並發那一半（本輪在 `spec-tasks.md` 任務 8 驗收 4 重跑）；任務 3 驗收 1 守「存完之後內容完整」。**「行程在存檔途中被結束」在裝置上造不出可靠的時機，知情留白**，只有 `spec-architecture.md` §A.1 的建議在提醒。

**§2.3 存檔之後，儲存裡那一段的訊息恰好是畫面上那一段的訊息，不多不少。**
- 記憶體裡被移除的訊息（還沒有任何文字就被停止的那則回覆），儲存裡也沒有它那一列；
- 復原之後，那一則在儲存裡的刪除狀態是「未刪除」，文字與刪除前逐碼位相同；
- 沒有任何一則重複、沒有任何一則留著上一次存檔的舊文字。
- 違反時：冷啟動之後畫面上多出一個空泡泡、少一則、或某一則是舊的內容。
- 為什麼要寫：整段重寫時這件事自然成立；改成「只動有變的那幾列」之後，每一種改變（新增、改文字、移除、刪除狀態）各是一條路，漏掉任何一條，記憶體與儲存就靜靜分歧，直到下一次冷啟動才看得到。
- 守：`spec-tasks.md` 任務 3 驗收 1。

**§2.4 一段對話從儲存裡消失時，它的訊息跟著全部消失。** 從歷史清單刪掉一段；或一段沒有任何「你說的話」的對話被存檔（等於移除，含從 App 以外寫進來、只有助理訊息的那種，打開再離開）—— 之後儲存裡沒有任何一列訊息屬於那一段，含已刪除的訊息。
- 違反時：使用者以為整段刪掉了，原文還留在手機上；或搜尋出現一段點不開的對話。
- 守：`spec-tasks.md` 任務 3 驗收 2；`docs/specs/message-copy-delete/spec.md` 任務 4 驗收 5（整段刪掉時原文一起消失）在任務 8 驗收 2 重跑。

**§2.5 一段讀不起來的對話，不得讓其他對話消失；清單、搜尋、開啟對它的答案一致。** 儲存裡有一段對話讀不起來時（例如它的某一則訊息的作者是一個不存在的值）：
- 它不在歷史清單上、搜尋搜不到它的任何一則訊息、依它的 id 開不到（冷啟動續接到它時，照「找不到就開新的」那條既有的路）；
- 其餘每一段照常：在清單上、搜得到、打得開、內容正確；App 不閃退、讀取不卡住。
- 違反時：整份歷史不見；或清單（或搜尋結果）上有一列點了沒反應。
- 這是 `docs/specs/conversation-store-db/spec.md` §1.5「一段讀不起來的對話，不得讓其他對話消失」在新結構上的樣子，多了搜尋那一句：清單與搜尋改成各自查資料庫之後，三條路各自有機會對同一段給出不同的答案。
- **新結構若讓這種資料根本寫不進去**（結構本身拒絕不存在的作者值），這條在那個造法上不可達，不算違反；`plan/architecture.html` 要寫明（`spec-tasks.md` 任務 7 驗收 3）。
- 守：`spec-tasks.md` 任務 1 驗收 4 的後半（不碰資料庫）；任務 3 驗收 3（裝置上）。

**§2.6 存檔寫不進去、儲存開不起來時的表現不變。** 照 `docs/specs/conversation-store-db/spec.md` §5.2「一次存檔寫不進去時」與 §5.4「儲存開不起來、但內容不一定壞了時，不刪、告知，下次啟動再試」。
- 守：§5.4 由 `spec-tasks.md` 任務 4 在新的成因上整組判到；§5.2 沒有獨立條文 —— 失敗提示走的是聊天狀態裡同一個入口，本輪不要求動它，由任務 4 驗收 1 的 (d)（開不起來期間的存檔失敗提示）判到。

## §3 升級：既有資料搬過去

**§3.1 升級之後，既有的每一段對話、每一則訊息都在。**（裁決 4）從舊版建置覆蓋安裝本輪的建置、第一次打開：
- 舊結構裡每一段解得開的對話都在（歷史清單上，或就是開著的那一段）；App 續接到升級前最後開著的那一段；
- 每一段的 id、人格、模型、建立時間、**最後更新時間**與升級前相同 —— **搬遷不算一次更新**，抽屜的順序與時間文字不變；
- 每一則訊息的 id、作者、文字、建立時間、先後順序與升級前相同；文字逐碼位相同（含結尾的中斷標記），搬遷時不做任何加工；
- **已刪除的仍是已刪除**：佔位在原位，點「復原」得到的文字與原文逐碼位相同；舊資料裡沒有刪除狀態紀錄的訊息（「這次會踩到的既有事實」第 1 條），是未刪除；
- **不出現**「之前的對話紀錄讀不出來，已經清空，從這裡重新開始。」，也**不出現**「目前讀不到之前的對話紀錄…」；
- 搬過來的對話之後照常使用：說下一句、刪除、復原、從清單刪掉、搜尋，每一則訊息恰好出現一次。
- 違反時：升級的使用者失去對話、已刪除的訊息原文重新出現在畫面上、清單順序被洗牌、或看到一句誤導的提示。
- 守：`spec-tasks.md` 任務 1 驗收 1（轉換，不碰資料庫）；任務 2 驗收 2（裝置上）。

**§3.2 搬完之後，舊形式不留。** 升級後的儲存裡，舊結構裝訊息的那個欄位不存在（§1.1），也沒有另外一份舊資料的備份表或備份檔。
- 守：`spec-tasks.md` 任務 2 驗收 1（與 §1.1 同一次讀取判到）。

**§3.3 一列解不開的舊資料，只丟掉它自己；其餘每一列照搬，搬遷照常完成。**
- **解不開的定義**：舊結構的一列，符合下列任一 —— 訊息那一欄不是合法的訊息陣列；某一則訊息缺少 id、作者、文字、建立時間任一項；某一則的作者不是「你」或「助理」那兩個值；**同一列裡有兩則訊息的 id 相同**。
- 解不開的那一列：升級後不在歷史清單上、搜不到、儲存裡沒有它的對話列也沒有它的任何訊息列。**不提示。**
- 解得開、但 App 自己寫不出來的舊資料列（只有助理訊息、或訊息陣列是空的）**照搬**，之後照 `docs/specs/conversation-search/spec.md` §9.1「儲存一段空白對話等於刪檔，不是寫檔」那條既有規則處理（打開再離開就清掉）。
- 為什麼丟掉而不是留著：這種列 App 自己寫不出來，只會從外面來；升級前它就不在清單上、使用者從來沒看過它；留著它就得在新結構裡保留一份舊形式（違反 §3.2）。（PM 的判斷，依據與反方向在 `spec-decisions.md`「我自己做的判斷」第 2 項。）
- 為什麼「重複 id」算解不開：新結構裡一則訊息的身分是「哪一段 ＋ id」，重複的 id 寫不進去；不先擋掉，整個搬遷會失敗，**所有**對話都讀不到。
- 違反時：一列外來的壞資料讓升級的使用者卡在「目前讀不到之前的對話紀錄」，每一段對話都看不到。
- 守：`spec-tasks.md` 任務 1 驗收 2（不碰資料庫）；任務 2 驗收 2（裝置上，測資含三種解不開的列）。

**§3.4 搬遷是整筆生效的，而且只做一次。**
- 搬遷途中失敗或行程被結束 → 儲存停在搬遷前的樣子，資料一則不少；下一次啟動再試。這種情況下 App 的表現照 §4.1（開不起來那條路），不得清掉。
- 搬遷成功之後再冷啟動，儲存的內容不再因為啟動而改變。
- **由哪一層守**：後半由 `spec-tasks.md` 任務 2 驗收 2 的 (f) 守。**前半沒有驗收，知情留白**：裝置上造不出「搬到一半」的時機，而資料庫層沒有自動化測試（裁決 5）；只有 `spec-architecture.md` §A.3 的建議在提醒。

**§3.5 降版不管。**（裁決 8）本輪的建置寫下的資料被舊版建置讀，不做任何保證。舊版建置仍帶著「對不上就清掉」的設定，那是它的行為，不在本輪範圍。
- **由哪一層守**：這是範圍排除，不是一條要求，沒有「被違反」的樣子；不立條文。唯一相關的可觀察面（本輪的建置遇到比自己新的儲存時不清資料）屬於 §4.1。

## §4 結構版本對不上時：開不起來、資料不動

**§4.1 資料庫的結構版本與這個建置對不起來時，走「開不起來」那條路，不得清掉。**（裁決 6）
- **涵蓋的情形**：儲存的結構版本比這個建置舊，而這個建置沒有對應的搬遷（漏寫）；儲存的結構版本比這個建置新。
- **表現照 `docs/specs/conversation-store-db/spec.md` §5.4「儲存開不起來、但內容不一定壞了時，不刪、告知，下次啟動再試」的每一項**：不閃退、聊天照常；提示一次「目前讀不到之前的對話紀錄（紀錄沒有被刪除），這段期間的對話也可能存不下來。」；**不出現**「…已經清空，從這裡重新開始。」；抽屜顯示「目前讀不到之前的對話紀錄。」；這段期間的存檔失敗照提示；**儲存的內容不被刪除、不被改動**。
- **裝上結構版本對得起來的建置之後**冷啟動：原本的每一段對話都讀得回來，不出現任何提示。
- 違反時：一次漏寫搬遷，讓每個升級的使用者失去全部對話，而且救不回來。
- 守：`spec-tasks.md` 任務 4 驗收 1（版本比建置新，不必另外建置）、驗收 2（突變建置：漏寫搬遷，由 QA 執行）。

**§4.2 內容真的壞了，仍然清掉重來並提示。** 資料庫檔損毀時的表現照 `docs/specs/conversation-store-db/spec.md` §5.1「儲存整份讀不起來時，告知一次後重新開始」，不因本輪而改變。那一條裡與「結構版本對不上」有關的部分改歸本規格 §4.1（那一份的字面還沒改，見 `spec-appendix.md`「跨規格覆蓋清單」）。
- 守：`spec-tasks.md` 任務 4 驗收 3（正向對照：與驗收 1 合起來，一個「永遠不清」或「永遠清」的實作都會被抓到）。

## §5 歷史清單查資料庫

**§5.1 抽屜上每一列顯示的東西，與本輪之前相同。** 對儲存裡每一段不是開著的對話：人格、模型、時間、標題、預覽、順序，都照 `docs/specs/conversation-search/spec.md` §5.2「抽屜必須有下面這些東西，行為如下」、`docs/specs/message-copy-delete/spec.md` §4.3「歷史清單的標題取第一則沒被刪的「你說的話」」與 §4.4「歷史清單的預覽取最後一則沒被刪的訊息」。含：第一句已刪除時標題取下一句；「你說的話」全部已刪除時標題是「（訊息已刪除）」；只有助理訊息的外來對話標題是「還沒說話」；每一則都已刪除時預覽是空的；截短不把一個字切成兩半。
- 違反時：標題或預覽露出已刪除訊息的原文；或刪除之後標題沒有跟著換。
- 為什麼要寫：清單不再拿到完整的對話之後，「取哪一則當標題」很可能由查詢決定 —— 那是「已刪除的訊息當作不存在」這條規則的第二個落點，而既有的 JVM 測試看不到查詢（「這次會踩到的既有事實」第 7 條）。
- 守：`spec-tasks.md` 任務 5 驗收 1（不碰資料庫的那一半）、驗收 2（裝置上）；升級後的清單由任務 2 驗收 2 的 (c) 判到。

**§5.2 清單照舊跟著儲存走。** `docs/specs/conversation-store-db/spec.md` §2「歷史清單跟著儲存走」整節不變：清單 ＝ 儲存裡的所有對話 − 開著的那一段，任一邊變動就更新；回覆還在生成時切換，被切走的那一段一打開抽屜就在最上面。
- 守：`spec-tasks.md` 任務 8 驗收 4。

**§5.3 從清單打開一段對話，得到它完整的內容。** 每一則訊息（含已刪除的佔位）都在、順序正確；不論那一段有多長。
- 守：`spec-tasks.md` 任務 3 驗收 1 的冷啟動與切換判讀；任務 2 驗收 2 的 (d)。

**§5.4 歷史清單不把每一段對話的所有訊息留在記憶體裡。**（裁決 7）抽屜需要的只有每一列要顯示的東西；一段對話的完整內容，在它被打開時才讀。
- 違反時：對話累積到幾百段之後，啟動與每一次儲存變動都要重讀、重解析全部訊息，App 變慢、吃記憶體。
- **由哪一層守**：這條的後果只在資料量大時看得到。**過程條文 `spec-tasks.md` 任務 5 驗收 3**（RD 寫明、PM 讀程式碼確認、QA 不判）；裝置上由任務 6 驗收 6（大量資料下仍然可用）判到「抽屜打得開、捲得動」—— 它抓得到慢到不能用，抓不到「其實還是整份讀進來」，所以過程條文照留。

## §6 搜尋 ＝ 資料庫裡的其他每一段 ＋ 記憶體裡開著的那一段

**§6.1 搜尋結果，等於把同一份比對規則套在「開著的那一段（記憶體裡的版本）加上儲存裡其他每一段」上的結果。** 分組、排序、每段最多三則、「還有 N 則符合」、摘要的兩個數字、片段、標示位置，全部照 `docs/specs/conversation-search/spec.md` §1–§4；已刪除的訊息照 `docs/specs/message-copy-delete/spec.md` §4.2「搜尋搜不到已刪除的訊息；復原之後又搜得到」。**使用者看到的搜尋結果與本輪之前相同。**
- 守：`spec-tasks.md` 任務 6 驗收 1（不碰資料庫）、驗收 2（裝置上）。

**§6.2 開著的那一段永遠取記憶體裡的版本，而且只出現一次。** 因此下列三樣不在儲存裡的東西照樣搜得到（`docs/specs/conversation-store-db/spec.md` §3.1「還沒存下的東西仍然搜得到」不變）：只有開場白、從未存下的那一段；已送出、回覆還沒結束的那一句；生成中的回覆此刻已經顯示的部分（命中會隨著生成增加）。開著的那一段同時也在儲存裡時，結果裡它只有一個分組，內容是記憶體那一份（`docs/specs/conversation-search/spec.md` §3.5「同一段對話只能出現一次，且以記憶體那份為準」不變）。
- 可判定（儲存裡的舊版本不得露出來）：開著一段已存過的對話，刪除其中一則含獨特詞 W 的訊息之後**立刻**進搜尋查 W → 無命中；不論那一次刪除的存檔完成了沒有。
- 違反時：使用者正在看的那一段搜不到、或同一段出現兩次、或搜到畫面上已經看不到的字。
- 守：`spec-tasks.md` 任務 6 驗收 1 的 (ii)、驗收 3（裝置上）；生成中那一項在裝置上盡力（任務 8 驗收 4 指向的既有條文）。

**§6.3 比對規則只有一份，儲存裡的訊息與記憶體裡的訊息用的是同一份。** 對儲存裡（不是開著的那一段）的訊息，下列每一項都與 `docs/specs/conversation-search/spec.md` 的規定相同：大小寫不分（§1.4）、全形半形不分（§1.5）、不做繁簡對應（§1.6）、所有空白先收成一個（§2.3、§2.6）、整串是一個子字串（§1.3）、片段與標示落在正確的字上（§4，含訊息裡有換行時）。
- 可判定（只靠 ASCII 就造得出來的鑑別案例）：一段已存下、不是開著的對話裡，你說過 `Hello  World`（中間兩個空白）。查 `hello world`（小寫、一個空白）→ 命中那一則，被標示的字取出來是 `Hello World`；查 `HELLO` → 命中；查 `hello,world` → 不命中。
- 違反時：同一句話，開著的時候搜得到、切走之後搜不到（或反過來）；使用者無從理解。
- 為什麼要寫：把比對交給資料庫查詢是最自然的寫法，而資料庫內建的比對不認得全形、不收合空白、大小寫只管 ASCII —— 那會是第二份比對規則，而且是既有的 JVM 測試看不到的那一份。**資料庫只負責把訊息交出來，判斷命中的仍是那一份比對規則（§6.6）。**
- 守：`spec-tasks.md` 任務 6 驗收 1 的 (i)（不碰資料庫）、驗收 2（裝置上）。

**§6.4 搜尋不改動儲存、不觸發推論。** 進入搜尋、打字、點命中列、離開：儲存的內容（每一段、每一則、含最後更新時間）前後相同；不觸發生成、不重新載入模型。**搜尋會讀儲存，這是預期的。**
- 這一條取代 `docs/specs/conversation-search/spec.md` §1.10「搜尋全程不觸發推論、不產生檔案讀寫」裡「不產生讀」那一半；「不寫」與「不觸發推論」不變（那一份的字面還沒改，見 `spec-appendix.md`「跨規格覆蓋清單」）。
- 守：`docs/specs/conversation-store-db/spec-tasks.md` 任務 7 驗收 9「搜尋與點命中列不改動儲存」，在 `spec-tasks.md` 任務 8 驗收 3 重跑。

**§6.5 畫面上的結果，對應的永遠是輸入框此刻的內容與此刻的資料。**
- 輸入停止後 1 秒內（一般資料量下），結果是輸入框此刻那個查詢的結果 —— 不是更早某一次按鍵的結果晚到蓋上來；
- 查詢清空（或只剩空白）之後，不得有任何結果列晚到出現，畫面是引導文案；
- 結果區仍然只有三種樣子（引導文案、結果列表、「找不到…」），沒有「載入中」的樣子（`docs/specs/conversation-search/spec.md` §1.9 不變）；儲存那一半還沒回來時，畫面可以暫時只有開著的那一段的命中，隨後補齊。
- 可判定：快速連續輸入 `h`、`e`、`l`、`l`、`o`（中間不停頓），停 1 秒 → 結果與「一次貼上 `hello`」的結果相同。把查詢整個刪掉 → 引導文案，之後 2 秒內不出現任何結果列。
- 違反時：使用者打完字，看到的卻是前幾個字的結果；或清空之後結果又冒出來。
- 為什麼要寫：結果原本是同步算出來的，不可能亂序；資料庫那一半變成非同步之後才有這種錯法（「這次會踩到的既有事實」第 6 條）。
- 守：`spec-tasks.md` 任務 6 驗收 1 的 (iii)（不碰資料庫）、驗收 4（裝置上）。

**§6.6 搜尋每一次都從資料庫把訊息逐批讀出來、用同一份比對規則比，比完就放掉；不把每一段對話的所有訊息留在記憶體裡，資料庫裡也不另存比對用的文字。**（裁決 7；使用者對 D1 的裁決）
- 任何時刻，記憶體裡因為搜尋而持有的，只有正在比的那一批訊息與已經命中的結果；搜尋結束（離開搜尋、查詢清空）之後不留下任何訊息文字的暫存。
- 資料庫裡沒有「整形後的文字」這類為搜尋而存的欄位（§1.2）。
- **使用者知情接受的代價**：每一次搜尋都把全部訊息文字從磁碟讀過一遍，對話很多時結果會晚一點出來；§6.7 的等待讓連續打字只讀一次。
- **由哪一層守**：結構那一半（沒有派生欄位）由 `spec-tasks.md` 任務 2 驗收 1 守；「不留在記憶體」是**過程條文任務 6 驗收 5**（RD 寫明、PM 讀程式碼確認、QA 不判）；資料多時還能不能用，由任務 6 驗收 6 守。

**§6.7 輸入停下來 250 毫秒，才開始搜尋。**（使用者對 D1 的附加裁決）
- 輸入框的內容每改變一次，就重新等 250 毫秒；這 250 毫秒之內內容又變了，就從頭再等。**等滿了才開始一次搜尋，搜的是那一刻輸入框裡的內容**；連續打字途中的中間內容不會各自被搜一次。
- **整個搜尋都等**：記憶體裡開著的那一段與資料庫那一半一起開始，不分先後出結果。
- **等待期間，結果區停在上一個狀態**（引導文案、上一個查詢的結果、或上一個「找不到…」），不因為還沒搜而出現第四種樣子（§6.5、`docs/specs/conversation-search/spec.md` §1.9）。「找不到符合「…」的訊息」括號裡的字（`docs/specs/conversation-search/spec.md` §2.9）因此在輸入停下來之後才保證與輸入框相同。
- **仍然沒有送出鈕，也不需要任何其他動作**：輸入停下來之後什麼都不做，結果自己出現；一般資料量下在輸入停止後 1 秒內（§6.5 與 `docs/specs/conversation-search/spec.md` §1.7 的判讀點不變）。
- **只管輸入框內容的改變。** 查詢沒變而資料變了（生成中的回覆多了字、儲存有變動）時，結果照舊跟著更新，不另外等。
- **查詢被清空（或只剩空白）時**：畫面回到引導文案，之後不得有結果晚到（§6.5）。回去之前要不要也等 250 毫秒，本規格不規定。
- **與 §6.2「刪除之後立刻查」相容**：那一條的「立刻」指的是刪除與進入搜尋之間不做別的動作；查詢打完、停下來 250 毫秒之後開始的那一次搜尋，看的是那一刻記憶體裡的版本。
- 違反時：每按一個鍵就把全部訊息從磁碟讀一遍（§6.6 的代價乘上字數），打字變鈍；或反過來，停下來之後結果遲遲不出現、使用者以為要按什麼鈕。
- **由哪一層守**：`spec-tasks.md` 任務 6 驗收 1 的 (iv)（不碰資料庫，時間由測試控制）守「250 毫秒內不開始、中間內容不搜、等滿就搜」；裝置上由任務 6 驗收 4 守「停下來之後不必做任何事、1 秒內出現、對應此刻的輸入」。**「250 毫秒」這個下限在裝置上量不到**（驗收環境送一個指令的來回就超過它），只有 JVM 測試在守。
