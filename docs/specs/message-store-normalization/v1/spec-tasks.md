- **標準測試指令**：`./gradlew testDebugUnitTest`。**本輪所有自動化測試都是 JVM 測試：不開資料庫、不依賴 Android。** 資料庫層不寫自動化測試、產品程式碼不加任何測試專用的入口（裁決 5；`docs/specs/conversation-store-db/` 的 D1、D2 照舊）。
- **任務只要被涵蓋即可**：一條驗收指向別的任務或別份規格的條文時，那一條就是要執行的條文，不另抄一份。
- **攔不到「還在生成中」時怎麼辦**：照 `docs/specs/conversation-store-db/spec-tasks.md`「攔住還在生成中的回覆：現場提示」；各條自己的「這一次算不算數」不變。

## 測資與讀取的約定

**本節取代 `docs/specs/conversation-store-db/spec-tasks.md`「測資與讀取的約定」裡與儲存結構有關的部分；那一節其餘的約定照用**（兩條路、清理排在判讀之後、開著的那段刪不掉、比對的值不得等於讀不懂時的退回值）。本輪重跑別份規格的條文時，凡是寫「讀儲存的內容」「從 App 以外寫入」的，一律照本節。

**造測資分兩條路（不變）**：App 自己做得出來的資料，用 App 的正常操作建立；App 做不出來的（只含助理訊息的對話、讀不起來的一段、解不開的舊資料列、整份壞掉的儲存、被改過的結構版本號），才直接改資料庫檔。**一律在 App 停止時改（`adb shell am force-stop com.example.demo`）、改完再冷啟動。**

**讀出「儲存的內容」**：App 停止時，把資料庫檔連同旁邊的附屬檔一起複製到主機，唯讀地開。位置、表與欄位照 `plan/architecture.html`「從 App 以外讀寫資料庫（驗收用）」（任務 7 驗收 3）；結構以 `app/schemas/` 裡匯出的最新一份為準。

**新結構下，一則訊息的原文與刪除狀態怎麼讀**：
- 訊息是自己的一列。**原文**就是那一列上記文字的欄位，逐碼位就是訊息文字，不需要解開任何東西；**刪除狀態**是同一列上的一個欄位，每一列都有明確的值。哪個值代表已刪除，照架構文件那一節。
- 「某一段對話的全部訊息」＝ 依對話 id 篩出那一段的訊息列，依架構文件指明的順序欄位排序。
- 「全部對話的內容裡找不找得到某個字串」（`docs/specs/message-copy-delete/spec.md` 任務 4 驗收 5 用到）＝ 把每一張表的每一列都列出來找，不是只找訊息那一張表 —— 這樣才照得出「原文被放到別的地方保管」的實作。
- 比的是**內容**（每一段的每一個欄位、每一則訊息的每一個欄位與順序），不是檔案位元組。Room 自己管理用的表（記錄結構識別的那一張）不算在「儲存的內容」裡。

**讀舊結構**（只有任務 2 驗收 2 的基準會用到）：舊結構的說明在舊版建置那個 commit 的架構文件裡 —— `git show e7de9fd:plan/architecture.html` 的「從 App 以外讀寫資料庫（驗收用）」。

**舊版建置怎麼來**：由 QA 在專案以外的暫存目錄 clone 出來、checkout `e7de9fd` 建置，**不在工作區切版本**（做法與已知的坑見 `docs/qa-environment.md` 講「建置舊版」的那一段）。突變建置（任務 4 驗收 2）同樣在暫存的 clone 裡做，**不得改動工作區的任何檔案**。

## 任務 1：舊資料轉換與新儲存形式的純邏輯

- **說明**：兩塊不開資料庫的邏輯。(1) 舊結構的一列 → 新結構的一段對話加它的訊息列，或「這一列解不開」（`spec.md` §3.1、§3.3）；(2) 一段對話 ↔ 新結構的儲存形式互轉，以及「依 id 取」與「取清單／取全部」共用的讀取規則（`spec.md` §1.3、§2.5）。
- **對應功能模組**：舊資料轉換；對話儲存裡不碰資料庫的那一半。
- **可驗證性要求**：這兩塊必須放在不依賴 Android、不開資料庫、能被測試直接呼叫的地方。**搬遷實際執行時用的轉換，必須就是被測試的這一份** —— 測試測的是一份、搬遷跑的是另一份，這個任務就是空的。
- **驗收標準**（每一條都要指得出對應的測試）：
  1. **舊資料照搬（§3.1）**。測資**直接寫成舊結構的形式**（一列的各個欄位值，訊息那一欄是一段 JSON 文字），不得用本輪的程式產生；舊形式在 `git show e7de9fd:app/src/main/java/com/example/demo/data/ConversationRecords.kt` 查得到。三列：
     - (i) 沒有任何 `deleted` 鍵的一列（還沒有刪除功能時存下的樣子）→ 每一則都是未刪除；
     - (ii) 含 `"deleted":true` 的一列：一則已刪除的「你說的話」、一則已刪除且以「…（已停止）」結尾的回覆、其餘未刪除 → 刪除狀態逐則相同；
     - (iii) 文字含 `docs/specs/conversation-store-db/spec.md` §1.1「讀回來的，就是存進去的」第一條可判定列出的每一種（換行與 tab、U+3000 與 U+00A0、兩個字元的 `\n` 與兩個反斜線、組合 emoji、前後空白、2,000 字元以上、以中斷標記結尾、空字串）→ 逐碼位相同。
     - 每一列斷言**完全相等**：對話的 id、人格、模型、建立時間、**最後更新時間**；每一則的 id、作者、文字、建立時間、刪除狀態；順序與 JSON 陣列的順序相同。人格與模型用非退回值；訊息 id 含缺號（例如 0、1、2、4）。
     - *獨自抓得到*：搬遷時把最後更新時間蓋成現在（抽屜順序被洗牌）；把刪除狀態漏掉（已刪除的原文回到畫面上）；對文字再做一次修復或去空白；依 id 重新編號。
     - **鑑別力**：把「沒有 `deleted` 鍵讀成未刪除」拿掉（改成必填），(i) 必須變紅；把刪除狀態一律給未刪除，(ii) 必須變紅。
  2. **解不開的只丟它自己（§3.3）**。給轉換一批舊資料列：正常的 E、F，加上四列解不開的 —— 訊息欄不是合法 JSON；某一則的作者是不存在的值；某一則缺少文字；同一列裡兩則訊息 id 相同。斷言：結果**恰為** E、F 兩段（內容完全相等），四列各自被判成解不開；整批轉換不丟出例外、在測試時限內結束。
     - *獨自抓得到*：一列壞資料讓整批搬遷失敗 —— 升級的使用者每一段對話都讀不到。
     - **鑑別力**：把「重複 id 判成解不開」拿掉，這一條的第四列必須讓測試變紅（不論是結果多了一段、還是少了斷言的「解不開」判定）。
  3. **解得開、但 App 寫不出來的列照搬（§3.3）**：只含助理訊息的一列、訊息陣列是空的一列 → 都判成解得開，內容完全相等。
     - *獨自抓得到*：搬遷順手把「空白對話」清掉 —— 那是「打開再離開才清」的既有規則，不是搬遷的事；清掉會讓 `docs/specs/conversation-search/spec.md` §9.1 的可判定（放一個只含助理訊息的對話，它出現在清單上）在升級情境下靜靜不成立。
  4. **新儲存形式來回（§1.3）與一段讀不起來（§2.5）**。一段含已刪除訊息、兩種作者、驗收 1 (iii) 那些文字、一則被標成「生成中」的訊息的對話 → 轉成新結構的儲存形式 → 經由「依 id 取」與「取全部」共用的讀取規則轉回來：每一個欄位、每一則（含刪除狀態與順序）完全相等；轉回來沒有任何一則是生成中。**後半**：給讀取規則一組儲存形式的資料，其中一段的某一則訊息作者是不存在的值，其餘兩段正常 → 「取全部」恰為那兩段；「依 id 取」對壞的那一段找不到、對好的取得到且內容相等、對不存在的 id 找不到；**對每一個 id，兩條路的答案相同**。
     - 這一條是 `docs/specs/conversation-store-db/spec-tasks.md` 任務 1 驗收 1、3 與 `docs/specs/message-copy-delete/spec.md` 任務 1 驗收 8 前半在新儲存形式上的樣子。既有的那幾支測試斷言的是舊儲存形式，**改寫成斷言新形式，要驗的性質一項都不得少**；除此之外的既有測試不得改動斷言。
     - *這一條管不到的*：資料庫那一端有沒有把各欄位原樣存好、原樣交回 —— 由任務 3 驗收 1 與任務 8 驗收 3 在裝置上承接。
  5. **空白對話的處置不變**：沒有任何「你說的話」的對話 → 判成「移除那個 id」；「你說的話」全部已刪除的對話 → 判成「寫入」（既有測試，照舊通過）。
  6. `./gradlew testDebugUnitTest` 全數通過。本輪之前就存在的測試一支都不得變紅、停用、刪除或改弱斷言，**只有兩組例外，都是「改寫到新的形狀、要驗的性質一項都不得少」**：(a) 驗收 4 指名的、斷言舊儲存形式的那幾支；(b) **斷言「開著的那一段＋歷史清單裡完整對話的合併」的那幾支**（今天是對聊天畫面狀態上那個「所有對話」的合併值斷言，分散在對話模型與搜尋兩個測試檔裡）—— 歷史清單不再持有完整對話之後（`spec.md` §5.4、§6.6），那個合併值不再存在；它們改寫成對新的搜尋組裝斷言同一組性質，性質列在任務 6 驗收 1 (ii)。**不得為了讓舊測試照舊編得過，而在產品程式碼裡留一個沒有人用的合併值。**
     - 冷讀判法：改寫前的測試在 `git show e7de9fd:<測試檔路徑>` 查得到；逐支對照，每一支原本斷言的性質，在改寫後的測試裡都指得出對應的斷言。
     - `docs/specs/conversation-search/spec.md` §3.5「同一段對話只能出現一次，且以記憶體那份為準」寫明那條可判定的測試不得因為畫面產不出這種輸入而被刪除 —— 改寫不是刪除，性質原封不動地守著。

## 任務 2：新結構與搬遷

- **說明**：資料庫改成新結構（`spec.md` §1.1、§1.2），結構版本前進，並提供從舊結構到新結構的搬遷（§3）。搬遷用任務 1 的轉換。
- **對應功能模組**：對話儲存；結構搬遷。
- **驗收標準**：
  1. **結構（§1.1、§1.2、§3.2；在裝置上，唯讀）**。用本輪的建置以正常操作建立一段對話（含兩種作者、一則已刪除、一則刪除後又復原），App 停止後照「測資與讀取的約定」讀儲存：
     - 只靠 SQL 查詢（不解析任何打包格式）列得出那一段的每一則訊息的 id、作者、文字、建立時間、刪除狀態，順序與畫面相同；已刪除的那一則刪除狀態是「已刪除」、原文完整；復原過的那一則是「未刪除」；
     - **列出資料庫裡每一張表的每一個欄位**（Room 自己管理用的表不算）：沒有任何一個欄位的內容是一則以上訊息的打包（看實際存下的值判）；舊結構裝訊息的那個欄位不存在；沒有舊資料的備份表；
     - **每一個欄位都說得出歸屬**：要嘛是對話自己的資料（id、人格、模型、建立時間、最後更新時間），要嘛是訊息自己的資料（§1.1 列的那幾樣與順序），要嘛在 `plan/architecture.html` 裡有一段寫明它是什麼、由什麼算出來、為什麼需要（§1.2）。三者都不是 → fail。
     - *獨自抓得到*：刪除狀態仍藏在某個打包欄位裡；舊欄位留著當第二份；多存了一份沒有人知道的派生資料。
  2. **升級（§3.1、§3.3、§3.4 後半；在裝置上）**。**每一步都要做，順序不得調換。**
     - **前置一（舊版建置造資料）**：清空 App 資料，安裝舊版建置。用正常操作建立三段對話，彼此的最後一次內容改變至少相隔 1 分鐘，人格與模型都選非退回值、三段不全相同：
       - **A**：至少兩輪來回；其中一句你說的話是 `Hello  World zqa-one`（中間兩個空白），另一句是 `second zqa-two`。刪除 `Hello  World zqa-one` 與一則對方的回覆（都不復原）。
       - **B**：送出一句會產生長回覆的話，生成中按停止 → 那則回覆以「…（已停止）」結尾。結尾不是這個標記 → 重做。
       - **C**：一輪來回；把你說的那一句刪掉（標題會是「（訊息已刪除）」）。
       - 最後從抽屜打開 **B**（讓它是開著的那一段），打開抽屜，**記下**每一列的標題、預覽、時間文字與由上到下的順序；再逐段打開，記下每一則的文字與哪幾則是佔位。最後停在 B。
     - **前置二（基準與外來的壞資料）**：停止 App。照「讀舊結構」讀一次儲存的內容當**基準**。然後從 App 以外加三列舊結構的資料：**X1** 訊息欄不是合法 JSON；**X2** 某一則的作者是不存在的值；**X3** 同一列裡兩則訊息 id 相同（其餘欄位合法）。三列各含一個別處沒有的字串（`zqx-one`、`zqx-two`、`zqx-three`）。
     - **升級**：覆蓋安裝本輪的建置（**不清資料**），打開。
     - **(a) 提示**：畫面出現後 3 秒內讀一次畫面 → 沒有「之前的對話紀錄讀不出來，已經清空，從這裡重新開始。」，也沒有「目前讀不到之前的對話紀錄…」。沒趕上 3 秒 → 寫明實際第幾秒看的，改以 (b)–(e) 全部成立判這一項（兩句提示都只在對話讀不到時出現）。
     - **(b) 續接**：開著的是 B；每一則文字與記下的相同，那則回覆以「…（已停止）」結尾。
     - **(c) 清單**：抽屜上恰好是 C、A 兩列（B 是開著的那一段），順序、標題、預覽、時間文字都與記下的相同；沒有 X1、X2、X3。
     - **(d) 佔位**：打開 A → 兩個佔位在原位、左右正確，整個畫面上讀不到 `zqa-one`；其餘每一則與記下的相同。**先不要復原。**
     - **(e) 儲存的內容**：停止 App，讀新結構 → A、B、C 每一段的 id、人格、模型、建立時間、最後更新時間，每一則訊息的 id、作者、文字、建立時間、刪除狀態、順序，都與基準相同；全部內容裡找不到 `zqx-one`、`zqx-two`、`zqx-three`，也沒有那三個 id 的對話列或訊息列。
     - **(f) 只搬一次**：冷啟動、不做任何事、停止 App，再讀一次 → 與 (e) 讀到的相同。
     - **(g) 搬過來的資料照常用**：打開 A，點 `Hello  World zqa-one` 那個佔位的「復原」→ 文字逐碼位相同（兩個空白都在）；在 A 送出 `after upgrade`、等回覆結束 → 每一則恰好出現一次、順序正確。開一段新的對話，進搜尋：查 `zqa-two` → 命中 A；查 `hello world zqa-one`（小寫、一個空白）→ 命中 A 剛復原的那一則。從抽屜刪掉 C → 那一列消失；停止 App 讀儲存 → 沒有 C 的對話列與訊息列。
     - **做不到時**：空間不足造成覆蓋安裝失敗、或兩份建置的簽章不同而裝不上 → 記「本環境無法執行」並寫明卡在哪一步；**不得清資料重裝後判 pass**。
     - *獨自抓得到*：升了結構版本而沒有搬遷、或搬遷沒接上（全部對話被清掉，或卡在「目前讀不到」）；搬遷漏掉刪除狀態、洗掉最後更新時間、重排順序、加工文字；一列外來的壞資料讓整個搬遷失敗；搬遷用「重建資料庫檔」的方式做而誤報「已經清空」；每次啟動都重搬一次。任務 1 不開資料庫，這些一個都看不到。
     - **QA 驗不到的**：搬遷途中行程被結束時資料是否完好（`spec.md` §3.4 前半，知情留白）；資料量很大時搬遷要多久。

## 任務 3：存檔、刪除與讀取在新結構上照樣成立

- **說明**：`spec.md` §2。存檔時機不變；存一段對話現在不只一個指令，整筆生效由 RD 保證（`spec-architecture.md` §A.1）。
- **對應功能模組**：對話儲存；聊天狀態（不改時機）。
- **驗收標準**（在裝置上）：
  1. **存檔之後，儲存裡那一段恰好是畫面上那一段（§2.1、§2.3、§1.3）**。開一段新的對話 T（人格與模型用非退回值），依序做下面每一步；**每一步之後**停止 App、讀儲存裡的 T、再打開 App（會續接到 T）：

     - *獨自抓得到*：只動「有變的那幾列」時漏掉一種改變（移除的訊息留著一列、復原沒寫回去、改過的文字沒更新）；記憶體與儲存靜靜分歧，要到冷啟動才看得到。

  3. **一段讀不起來不連累其他（§2.5）**。三段正常的對話 E、F、G（G 是開著的）。停止 App，從 App 以外把 E 的某一則訊息的作者改成不存在的值（E 裡有一個別處沒有的字串 `zqe-bad`）。冷啟動：不閃退；抽屜上有 F、沒有 E；搜 `zqe-bad` → 找不到；搜 F 裡的字 → 命中；打開 F 內容正確。再做一次，這次先讓「上次停在哪」指著 E（改壞之前最後開著 E）→ 冷啟動不閃退、畫面是一段新的對話。
     - **結構本身拒絕這種寫入時**（寫入被資料庫擋下）：記「結構上造不出來」，附上被擋下的錯誤訊息，判 pass —— 這種壞資料在新結構上不存在；並核對 `plan/architecture.html` 有寫明這一點（任務 7 驗收 3）。
     - *獨自抓得到*：清單的查詢不受影響而照樣列出 E、點了卻沒反應；搜尋搜得到 E 的訊息；一列壞資料讓整個清單或搜尋的查詢失敗。

## 任務 6：搜尋 ＝ 資料庫 ＋ 記憶體裡開著的那一段

- **說明**：`spec.md` §6。做法已由使用者拍板（§6.6、§6.7）：**輸入停下來 250 毫秒之後**才開始一次搜尋；資料庫那一半把存下來的訊息逐批讀出來，交給現有那一份比對規則，比完就放掉；資料庫裡不另存比對用的文字；開著的那一段取記憶體裡的版本。
- **對應功能模組**：搜尋的組裝；對話儲存；比對純邏輯（規則不改）。
- **可驗證性要求**：「等輸入停下來、把開著的那一段與資料庫來的訊息合起來、交給比對規則、產出結果」的那一段，必須能被 JVM 測試用一個**假的資料庫來源**直接驅動（不開資料庫、不依賴 Android），而且**等待的時間由測試控制**（測試不必真的等，也看得到「第幾毫秒向來源要了什麼」）。
- **驗收標準**：
  1. **組裝（不碰資料庫）**。用假的資料庫來源驅動搜尋的組裝，斷言：
     - **(i) 規則同一份（§6.1、§6.3）**：來源裡一段不是開著的對話含 `Hello  World`、`ＡＢＣ`、`北京` 換行 `天氣`、一則已刪除且含 `kiwi` 的訊息、一則未刪除且含 `kiwi` 的訊息 → 查 `hello world`、`abc`、`北京 天氣` 都命中對應那一則，片段與標示區間與比對純邏輯直接對同一則訊息算出來的**完全相同**；查 `kiwi` 恰好一則、摘要兩個數字是 1 與 1；查 `台`（訊息裡只有「臺」）不命中。
     - **(ii) 開著的那一段取記憶體那一份（§6.2）**（既有那幾支斷言「開著的那一段＋歷史清單的合併」的測試改寫到這裡，見任務 1 驗收 6）。**五項性質一項都不得少**：開著的那一段一定在；同一個 id 只出現一次；留下的是記憶體那一份，即使儲存裡那一份的最後更新時間較新；先決定留哪一份、再依最後更新時間排序；開著的那一段是空白對話（只有開場白）時也在。測資：來源裡有一段與開著的那一段同 id、但少一則訊息、最後更新時間較新 → 結果裡那個 id 只有一個分組，命中數與排序位置依記憶體那一份（`docs/specs/conversation-search/spec.md` §3.5 的那個可判定，換成新的來源形狀）；開著的那一段只有開場白、來源裡沒有它 → 查開場白裡的字命中它；開著的那一段有一則生成中的訊息 → 查它此刻的文字命中。
     - **(iii) 不亂序（§6.5）**：依序發出查詢 `h`、`he`，讓假來源對 `h` 的回應**晚於**對 `he` 的回應 → 最後的結果是 `he` 的；查詢清空之後來源才回應 → 最後沒有任何結果。
     - **(iv) 輸入停下來 250 毫秒才開始（§6.7）**：時間由測試控制。第 0 毫秒輸入 `h`、第 100 毫秒變成 `he`、第 200 毫秒變成 `hel`，之後不再變 → **第 449 毫秒為止，假來源一次都沒有被要過資料、結果仍是輸入之前的樣子**；第 450 毫秒（最後一次改變之後 250 毫秒）起來源被要了**恰好一次**，要的是 `hel`，`h` 與 `he` 從來沒有被搜過；結果是 `hel` 的，而且含開著的那一段的命中（記憶體那一半同一次出來，不提早）。**清空不等**：結果是 `hel` 的那個狀態下，把查詢改成空字串（另一個案例改成三個空白）→ **時間一毫秒都不前進**，結果已經是「沒在搜尋」（沒有任何結果列）；再前進 1 秒，來源沒有因為這次改變被要過任何東西。另一個案例：輸入 `h` 之後第 100 毫秒清空 → 前進到第 1 秒，來源一次都沒有被要過、沒有任何結果。**正向對照**：查詢不變、開著的那一段多了一則會命中的訊息 → 結果不必等任何輸入就更新。
     - 既有的比對測試（大小寫、全形、空白、片段、標示、計數、已刪除）照舊全部通過、斷言不改。
     - **鑑別力**：讓來自資料庫的訊息改走一份只會 ASCII 大小寫折疊的比對，(i) 的 `ＡＢＣ` 與 `北京 天氣` 必須變紅；把「開著的那一段從來源裡扣掉／以記憶體為準」拿掉，(ii) 必須變紅；把等待拿掉（每次改變就搜），(iv) 的「一次都沒有被要過」與「恰好一次」必須變紅；把等待改成「從第一次改變起算」而不是「從最後一次改變起算」，(iv) 的第 449 毫秒那一項必須變紅；讓清空也走同一段等待，(iv) 的「時間一毫秒都不前進，結果已經是沒在搜尋」必須變紅。
     - *這一條管不到的*：真的資料庫來源交出來的東西對不對（例如查詢在資料庫那一端先篩過一次、篩錯了）—— 由驗收 2 承接。
  2. **在裝置上：儲存裡的訊息用的是同一份規則（§6.3）**。一段對話 S 裡你說過 `Hello  World zqs-one`（兩個空白）與 `plain!` ；等回覆結束、開一段新的對話（S 不是開著的那一段），**冷啟動一次**，進搜尋：
     - 查 `hello world`（小寫、一個空白）→ 命中 S 的那一則，片段裡被標示的字是 `Hello World`；查 `HELLO` → 命中；查 `hello,world` → 「找不到…」；
     - **全形（做得到才判）**：用驗收環境產生得出來的全形字元查（例如全形驚嘆號：查 `plain！`，怎麼打出全形見 `docs/qa-environment.md` 講輸入法的那幾段）→ 命中 `plain!` 那一則。環境打不出任何全形 ASCII → 記「本環境無法執行」並寫明試過什麼，由驗收 1 (i) 守；
     - **含換行的訊息（做得到才判）**：S 裡若有一則對方的回覆含換行，取換行前後各一個詞、中間用一個空白查 → 命中那一則，被標示的字落在那兩個詞上。回覆都不含換行 → 換提示再試一次，仍沒有就記「本環境無法觀察」，由驗收 1 (i) 守。
     - **正向對照**：打開 S（讓它變成開著的那一段）再進搜尋，同樣三個 ASCII 查詢 → 結果與上面相同。
     - *獨自抓得到*：把比對交給資料庫內建的比對 —— 兩個空白對一個空白那一項一定不命中。驗收 1 用的是假來源，看不到真的查詢。
  3. **在裝置上：開著的那一段取記憶體（§6.2）**。(a) `docs/specs/conversation-store-db/spec-tasks.md` 任務 3 驗收 1「從未存下的新對話搜得到」、驗收 2「已送出、還沒收尾的那句搜得到」（盡力）在任務 8 驗收 4 重跑。(b) 本條另判：開著一段已存過的對話，其中你說過 `zqw-gone`；刪除那一則，**立刻**（不做別的動作）從抽屜進搜尋查 `zqw-gone` → 「找不到…」；回到聊天復原它，立刻再查 → 命中，而且那段對話只有一個分組。
     - *獨自抓得到*：開著的那一段也從資料庫查（刪除的存檔還沒落地時搜得到已刪除的字），或兩邊各出一個分組。
  4. **在裝置上：結果對應此刻的輸入（§6.5）**。儲存裡至少有三段含 `hello` 的對話。進搜尋，不停頓地連續輸入 `h`、`e`、`l`、`l`、`o`，停 1 秒，記下結果；離開再進搜尋，一次輸入 `hello`，停 1 秒 → 兩次的分組、命中列、摘要數字相同。接著把查詢整個刪掉 → 停 1 秒 → 引導文案；再等 2 秒 → 仍是引導文案，沒有結果列冒出來。任何時刻結果區都沒有「載入中」的樣子。**整條從頭到尾不按任何鈕、不收鍵盤**：每一次都是輸入停下來之後結果自己出現（§6.7「仍然沒有送出鈕」）。
     - **這一條判不到的**：「250 毫秒之內沒有開始搜尋」與「清空時沒有多等 250 毫秒」—— 驗收環境送一個指令的來回就超過 250 毫秒，量不到；由驗收 1 (iv) 守。
  5. **（過程條文，QA 不判）搜尋不把所有訊息長期留在記憶體（§6.6）**。同任務 5 驗收 3 的形式：RD 在同一筆收件匣裡寫明搜尋從資料庫取什麼、在記憶體裡留多久；PM 讀程式碼確認；QA 不判，也不構成裁決 7 已達成的證據。
  6. **在裝置上：大量資料下仍然可用（§5.4、§6.6；使用者對 D2 的裁決）**。
     - **前置**：清空 App 資料，用本輪的建置啟動一次、送出一句並等回覆結束（讓資料庫以新結構建立），停止 App。從 App 以外照 `plan/architecture.html` 的結構說明直接寫入**約 300 段對話、每段約 40 則、每則約 300–500 個字元**（App 做不出這個量，走「App 做不出來的才直接改資料庫檔」那條路；怎麼灌由 QA 決定，腳本歸 QA）。人格、模型、作者都用合法值，每一段至少一則「你說的話」，最後更新時間各不相同。**恰好 3 段**各有一則訊息含 `zqbulk-needle`，其餘都不含。
     - **判**：
       - (a) 冷啟動 → 聊天畫面出現、不閃退；打開抽屜 → **5 秒內**看得到歷史清單，順序是最後更新時間新到舊（看最上面三列）；把清單往下捲到底再捲回來 → 捲得動，沒有「應用程式沒有回應」的系統對話框；

     - **QA 驗不到的**：清單或搜尋是不是其實把全部訊息留在記憶體裡 —— 這個量整份讀進來也撐得住；那件事仍由過程條文（任務 5 驗收 3、本任務驗收 5）守。
