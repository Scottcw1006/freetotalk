# 小助理：功能清單

這份文件回答一個問題：**這個 App 現在做得到什麼？**

- 全部用日常語言寫，看得懂中文就看得懂。
- 每一項都是「使用者可以做什麼」或「使用者會看到什麼」，**寫的是現在的樣子**，不是計畫要做的樣子。
- **不寫**為什麼這樣設計（那在 `plan/architecture.html`）、也不寫某一輪要改什麼（那在 `docs/specs/<名稱>/`）。

## 這份文件怎麼維護

1. **新增或修改功能的時候，PM 在寫那一輪的 spec 時就要一起改這份文件。** 不是做完再回頭補，是同一件事的一部分。
2. **如果測試的時候發現這份文件跟 App 實際的樣子對不起來，或是某一輪不小心動到了別的功能 —— 不要自己決定誰對，拉給使用者判斷。**
3. **較早的規格可能還用舊的儲存方式在寫條文（2026-09-17 使用者裁決）。** 對話原本是「一段對話一個 JSON 檔」，`conversation-store-db` 那一輪改成資料庫之後，`docs/specs/` 底下較早的規格（例如 `conversation-search`、`stop-generation`）仍有條文寫著「對話目錄的檔案數」「檔案位元組」「把一個檔放進對話目錄」。**那些規格沒有回頭改。下一次有人修訂它們時，必須以這份文件與 `plan/architecture.html` 為準，把那些條文換成不綁儲存形式的寫法**；逐條的改寫清單在 `docs/specs/conversation-store-db/spec-appendix.md`「跨輪衝突清單」。下面「資料的保存與刪除」有幾列就指向那種條文，旁邊都有註記。

## 編號怎麼看

每一項有一個帶前綴的編號，例如 `搜尋-03`。**編號一旦給出去就不會再動。** 之後新增項目時往該區的後面接下去編，不會把舊的往後推 —— 因為之後會有一份「哪一項什麼時候被驗過」的帳，編號一動那份帳就對不上。

| 前綴 | 這一區在講什麼 |
|---|---|
| `啟動-` | 打開 App、模型準備、接續上次 |
| `聊天-` | 聊天畫面上說話與收回覆 |
| `人格-` | 換一個角色聊 |
| `模型-` | 換一個 AI 模型 |
| `歷史-` | 左邊拉出來的歷史抽屜 |
| `搜尋-` | 搜尋所有對話的內容 |
| `比較-` | 多個模型並排比較 |
| `保存-` | 資料什麼時候留下、什麼時候消失 |

## 「對應 spec」欄怎麼看

- 有寫位置的：那一項有規格條文在守，出問題時可以照那份判對錯。
- 寫「**尚無 spec**」的：這個功能**從來沒有被規格化過**，沒有任何驗收條文在守它。那個空白是刻意留的，不要為了好看去湊。

**引用的寫法（2026-09-10 定案）**：

```
docs/specs/conversation-search/spec.md §5.1「入口在歷史抽屜的歷史區塊，是一個入口列」
└──────── slug 目錄 ────────┘ └ 檔名 ┘ └節號┘ └───────────── 節名 ─────────────┘
```

- **不寫版號目錄。** 每一份 spec 的定版都留在自己的版號目錄裡（`v3.12/`、`v3/`…），版號是唯一會一直變的一段，所以砍掉；**讀的人自己挑版號最大的那個目錄**。
- **節號 + 節名一起帶。** 節號給速度（直接跳過去），節名給查核（確認跳對了）。**節號指錯是靜靜失敗** —— 你落在一個真實存在的節，它講的是別的事，而你以為自己找對了；**節名指錯是 grep 不到，當場就知道**。兩者不一致時讀的人立刻看得到。
- 節名取那一條規則**粗體的那句話**，太長就取前半句，只要 grep 得到即可。
- **這一欄的節名會過期。** 被指到的那一節若改寫了粗體那句話，這裡就 grep 不到 —— **那時要改的是這裡，不是那邊**。沒有任何機制會通知這份文件。

## 「※未經查證」是什麼意思

這份文件是讀程式碼與既有文件寫出來的，**寫的時候沒有人實際開 App 跑過**。絕大多數項目在程式碼裡讀得出來，但有少數幾項只能靠推論 —— 那幾項後面標了 `※未經查證`。**看到這個標記，就表示那一項還需要有人實際開 App 確認過。**

**「查證」看的是有沒有人實際開 App 確認過，不看那是什麼裝置。** 實體手機、模擬器都算 —— 只要那一項真的被操作過、被看過，它就不是「未經查證」。
