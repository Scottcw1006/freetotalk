小助理架構

一個完全離線的 IM 聊天 App：三個 LLM 打包在 APK 裡，五個可切換的人格，對話各自獨立存檔，也找得回說過的每一句話。 沒有網路、沒有 API key，所有推論都在手機的 CPU 上跑完。

元件

三個畫面，一個引擎

聊天頁和比較頁各有自己的 ViewModel，但它們共用同一個 LlmEngine 單例。 這不是為了省記憶體管理的工，而是因為一次只能有一個模型常駐——每個模型載入後佔用數百 MB 的 native 記憶體， 同時放兩個就是在等 low-memory killer 上門。

第三個畫面是搜尋，它刻意沒有自己的 ViewModel：它讀的就是聊天頁那一份狀態。 搜尋要找的是「使用者看得到的對話」，而唯一知道那是什麼的就是聊天頁的狀態—— 開著的那段對話只有它握著——還沒存檔的訊息和正在串流的回覆不在資料庫裡；另開一個 ViewModel 只拿得到資料庫那一半。 三個畫面之間也沒有導航框架，只有兩個布林旗標決定現在顯示哪一個。

聊天畫面上長按一則訊息會出現選單（複製、刪除），只有這個畫面有——搜尋的命中列與比較頁的卡片都沒有。 長按能做什麼不是畫面決定的：畫面問的是訊息自己（chat/Conversation.kt 的 longPressActions）， 還在生成中的那一則與已刪除的佔位回答「沒有」，畫面就連長按都不接。複製是畫面直接把那一則的原始文字放進系統剪貼簿，不經過 ViewModel、不改任何資料。

資料流

一則訊息從送出到存檔

整條路徑上最違反直覺的一步是第 4 步：每則訊息都開一個全新的 Session， 把整段對話重新餵進去，而不是讓一個長壽 Session 用 KV cache 累積歷史。 成本是每次重新 prefill，換來兩件事——對話之間不可能互相汙染，而且人格設定每一輪都重申一次，不會隨對話變長被擠出注意力。

第 1 步的次序是寫死的：先拿掉已刪除的訊息，再略過開頭連續的助理訊息（Conversation.contextForNextTurn()，純邏輯、有測試）。 開頭的助理訊息不送，是因為開場白是佈景不是對白；而使用者刪掉自己的第一句、留著對方的回覆時，那則落單的回覆也會變成「開頭的助理訊息」。 次序反過來的話它會被送出去，Gemma 的格式又會把人格設定併進第一則——人格設定就被塞進一則對方的話裡，口吻會跑掉。 上下文在送出那一刻就定了：生成途中才刪的訊息不影響正在生成的那一則，從下一次送出起才不算數。

存檔時機有四種：回覆收尾、按停止、切走，以及刪除或復原一則訊息的當下。最後一種是因為刪除之後不保證還有別的動作會順便存——直接關掉 App 的話刪除狀態就不見了。 四種走的是同一個入口（ChatViewModel.persist），所以存檔失敗的提示、空白對話不寫的規則都一樣。 代價：對方還在生成時刪除別的訊息，會讓「生成到一半的對話」被存下來一次，那則回覆當下存進去的是半截文字、沒有中斷標記；正常情況下收尾時會再存一次蓋掉它，只有行程剛好在那中間被結束才會留下半截。

取消只是發出請求。原生的推論執行緒在取消之後還會跑一小段，所以收束時要等推論真的停下來，才關掉 Session、才放開 Mutex（最多等 10 秒）。 不等的後果是：串流中切換模型時，換模型的那一步會在推論還在讀模型時把它關掉，App 在原生程式裡閃退（SIGSEGV）。這段等待看起來像可以省掉的延遲，別拿掉它。 代價是卡住時，停止之後的下一句要多等最多 10 秒才開始生成。

模型抽象

Prompt 格式綁在模型上，不是全域設定

餵錯轉折標記，模型不會報錯，它會安靜地退化成續寫機器。 ModelSpec 讓每個模型帶著自己的 renderer，PromptFormat 只有兩種實作， 但兩者的差異不只是標記字串不同——Gemma 根本沒有 system 角色。

量化

同一個模型，int4 說不了中文

Gemma3 1B 最早裝的是 int4，因為當時只有那個精度找得到免授權的來源。 它的英文完全正常，中文卻會在長回答中途崩解成標點和疊字： 您、您、您、 感到、 好像、 好像、 、 這些、 這些、。 同一個模型、同一個人格、相隔二十九秒的兩則回答，英文那則結構完整，中文那則垮掉。

換成 q8 之後，同樣的問題得到的是條列清楚的中文，而且模型自己停在 152 個 token， 既沒撞到長度上限也沒觸發迴圈偵測。順帶一提，q8 還比 int4 快兩倍以上 —— 16.3 對 7.0 tok/s，因為 XNNPack 不必為每次運算把 int4 權重解壓回去。

量化不是等比例地損失品質

int4 省下的那 476 MB，代價不是「答得差一點」，而是整個語言失效。 小模型的多語系能力是最先被量化壓垮的部分，而這件事在英文測試裡完全看不出來。

文字修復

模型的輸出到畫面之間隔著兩層損壞

兩個 bug 都不在 App 的程式碼裡，但都得在 App 裡修。 repairModelText() 是唯一的收斂點，只在生成時經過：存進資料庫的已經是修好的文字。 讀取時刻意不再修一次——那會連使用者自己打的字一起改掉（兩個字元的 \n 重開後會變成換行）。 以前讀取時也會修，是為了照顧修正上線前就存壞的舊檔；改用資料庫時舊檔不搬遷，這個理由就不存在了。

換行變成字面上的兩個字元

量測到的 fragment 字元碼是 [92, 110]，也就是反斜線加 n，不是 code 10。 所有樣本、中英文、清單和散文都一樣，一次都沒出現過真正的換行。 因為那不是空白字元，trim() 抓不到它。

byte-level BPE 的替身字元沒被還原

Qwen 和 SmolLM 把 byte 而不是字元拿去 tokenize，每個 byte 有一個替身字元——空格是 Ġ，0x8C 是 Į。 MediaPipe 通常會轉回來，但有些 token 沒有，於是一個中文字以它 UTF-8 三個 byte 的替身形式抵達。 Gemma 用 SentencePiece，沒有 byte 字母表，不受影響。

還原必須拒絕誤判

café、Ärger、naïve 全都是合法的替身字元序列。 所以只在兩個條件同時成立時才改寫：整段通過嚴格 UTF-8 解碼（CodingErrorAction.REPORT，不是會塞 U+FFFD 的寬鬆模式）， 而且結果含有三位元組字元。帶重音的拉丁字只會還原成自己，就被拒絕、原樣保留。

第三樣要清掉的東西是前一步自己造成的

模型寫的是 Markdown，而 Markdown 裡「行尾一個反斜線」的意思是強制換行。 反跳脫那一步已經把它後面的 \n 變成真的換行了，於是那個反斜線就變成畫面上看得見的垃圾， 必須在同一條流水線上收掉。順序有意義：一定要在反跳脫之後。

修好之後還有一步，那一步不是修復是呈現

模型會寫粗體、斜體和條列，直接顯示就是一堆星號。解析成區塊與強調是在畫的時候做的， 存下來的永遠是模型原本寫的文字。認不出來的標記一律原樣顯示——半寫完的 ** 讓人看見， 比被默默吃掉好。只有模型的訊息會走這一步，使用者自己打的字原封不動。

儲存

每個模型在裝置上存在三份

MediaPipe 的 setModelPath() 只接受真實的檔案路徑，而 APK 裡的 asset 不是檔案， 是 zip 裡的一段位元組。所以第一次用到某個模型時，必須先把它複製出來。 這就是為什麼系統設定裡的「使用者資料」會顯示 1.65 GiB。

對話儲存

一則訊息一列，歷史清單跟著資料庫走

對話存在 Room 資料庫裡，整個行程只有一個實例（ConversationRepository.get()）。 對話一張表、訊息一張表，一則訊息就是自己的一列：屬於哪一段、id、順序、作者、文字、時間、刪除狀態，每一樣都是一個欄位，沒有任何東西打包在別的欄位裡。 一則訊息的身分是「哪一段＋訊息 id」——訊息 id 每一段各自從 0 起算，單看 id 會跨段撞號。順序看 position 欄位，不看 id：App 自己發的 id 只會變大，但從外面寫進來的對話不保證。 資料庫裡也不存任何從訊息算得出來的東西（標題、預覽、給搜尋用的整形文字都沒有）；要存的那一天，這裡得先寫明它是什麼、為什麼非存不可、來源變了怎麼跟著變。

存一段對話是好幾個指令，包在一筆交易裡（ConversationDao.write：寫對話那一列、清掉那一段舊的訊息列、寫入現在的訊息列）；刪一段也是一筆交易（先刪訊息列、再刪對話列）。 交易讓它整筆生效，讀的人不會撞見「對話在、訊息不在」或只有一半的訊息。以前的「先把檔清空再寫入」正是這種暫時不見的來源：回覆還在生成時切換，同一段會被幾乎同時存兩次，讀清單的人剛好讀到空檔，那段就從清單上消失。 每一次存檔都是把那一段的訊息列整組換掉，所以存完之後資料庫裡那一段恰好就是記憶體裡那一段，不會有哪一種改變（新增、改字、移除、刪除狀態）漏寫。 訊息列是用明確的刪除指令清掉的，不靠外鍵的連帶刪除——連帶刪除只在有開外鍵的連線上才會發生，而且會讓「覆寫對話那一列」變成「清光它的訊息」。

這一層沒有自動化測試（使用者的裁決），產品程式碼也沒有測試專用的入口。所以「哪幾個指令必須在同一筆交易裡」只有 data/ConversationDatabase.kt 的註解與裝置上的驗收在守； 缺口是：行程在存檔途中、或在搬遷途中被結束時資料是否完好，沒有任何東西驗過，靠的是 SQLite 交易本身的保證。

歷史清單是持續算出來的，不是讀一次存起來的。它等於「資料庫裡的所有對話，扣掉目前開著的那段」，兩邊任一變動就重算（chat/HistoryList.kt）。 所以切換、刪除、回覆收尾之後都不必再去「重讀一次清單」——被切走的那段一存進去就出現在清單上。 清單不持有完整的對話。一個查詢替每一段只取它自己的欄位，加上三樣：第一則沒被刪的「你說的話」、最後一則沒被刪的訊息、有沒有任何一則「你說的話」（含已刪除的，用來分辨「（訊息已刪除）」與「還沒說話」）。 「取哪一則」在查詢裡（ConversationDao.observeHistory），那是 JVM 測試看不到的一半，由裝置上的驗收守；拿到之後標題與預覽怎麼算、怎麼截短，仍然只有 Conversation.title／preview 那一份—— data/HistoryRows.kt 把查詢結果立成一段最小的對話再去問它，有 JVM 測試對照完整對話的答案。一段對話的完整內容在它被打開時才讀。 資料庫仍然不是唯一的來源：開著的那段與正在串流的回覆只在記憶體裡（見下面搜尋那節）。

讀取有三條路（歷史清單、依 id 取一段、搜尋時一批一批取），取出整段對話的兩條走同一套解析規則（data/ConversationRecords.kt），而且是一段一段解析： 讀不起來的那一段（例如某一則訊息的作者是不認得的值）只丟掉它自己，不會讓整份歷史消失，幾條路對同一個 id 的答案也一定相同——歷史清單的查詢會把「有不認得的作者」的那一段標出來，由同一層略過。 Room 只負責交出每一列的原始字串；作者欄位刻意不讓 Room 直接轉成列舉，否則一列壞資料會讓整個查詢失敗。查詢裡要用到的作者名稱是綁進去的參數，SQL 裡沒有寫死任何一個。 新結構沒有用限制條件擋掉不認得的作者，所以這種壞資料從外面仍然寫得進去。

從舊結構升級。結構版本 1 是「一段對話一列、所有訊息打包成那一列裡的一段 JSON」，已刪除的訊息在自己的物件上多一個 "deleted":true、未刪除的不寫這個鍵。 版本 2 就是上面的樣子。升級時 Room 在一筆交易裡跑 data/ConversationMigrations.kt：舊表改名、建立新的兩張表、把舊的每一列交給 data/LegacyThreadRows.kt 的轉換（純邏輯，有 JVM 測試，搬遷跑的就是被測的那一份）、最後把舊表刪掉，不留備份。 沒有 deleted 鍵讀成未刪除；文字一個碼位都不動；最後更新時間照搬——搬遷不算一次更新，抽屜的順序與時間不變。 解不開的舊資料列只丟掉它自己（不是合法的訊息陣列、某一則缺欄位、作者不認得、同一列裡訊息 id 重複），其餘照搬；只有助理訊息或沒有訊息的列不算解不開，照搬。 搬遷在原本的檔案上做，不另建新檔——App 是從「資料庫被重新建立了一次」認出清掉重來的，重建檔案會讓每個升級的人看到「已經清空」。

以後每一次改結構，都要把 SCHEMA_VERSION（data/ConversationDatabase.kt）加一，並在 ConversationMigrations.all 補上那一步的搬遷。 「版本對不上就整個清掉重來」的設定兩個方向都已經拿掉：漏寫搬遷、或手機上的資料比這個建置新，結果是資料庫開不起來、資料原封不動（下表第二列），補上搬遷的下一版就救得回來。

舊版的 JSON 檔不搬遷。App 每次啟動、碰資料庫之前，會把 filesDir/conversations/ 這一個子目錄整個刪掉，而且只刪它——模型檔就放在它的上一層。刪不掉就等下次啟動再試，不影響開啟。

資料庫出問題時，分法看的是「存下來的內容本身壞了沒有」，不是錯誤發生在開檔還是讀寫：

情況原本的紀錄使用者看到
內容壞了：資料庫檔損毀丟掉，重新開始提示一次「之前的對話紀錄讀不出來，已經清空，從這裡重新開始。」
開不起來，而且判斷不出內容壞了：檔案被設成唯讀、權限不對；結構版本對不上（需要一段搬遷而這個建置沒有、或資料的版本比這個建置新）不動，下次啟動再試每次啟動提示一次「目前讀不到之前的對話紀錄（紀錄沒有被刪除），這段期間的對話也可能存不下來。」；抽屜寫「目前讀不到之前的對話紀錄。」；每次存檔失敗再提示「有一段對話沒能存下來。」
開得起來，但某一次寫不進去：空間不足不動「有一段對話沒能存下來。」
只有其中一段讀不起來其餘照常那一段不出現在清單上

判斷不出來時，一律當成開不起來。丟掉是不能復原的，而讓資料庫開不起來的原因往往會自己消失；判錯的另一個方向只是這次啟動讀不到。 所以只有 Android 回報的損毀、以及 Android 因損毀而關掉連線這幾種會丟掉重來（另外還留著一種開發時才會出現的：改了表格卻沒把結構版本加一，Room 會說它驗證不了資料——那是實作錯誤，不是使用者會遇到的情形）（ConversationRepository 裡的 meansStoreIsDamaged）；「開不了檔」那一類錯誤、唯讀、缺搬遷或版本比建置新（Room 的訊息是 A migration from X to Y was required but not found）、以及其他任何失敗都不會。 注意唯讀在 Android 上造成的是整個開不起來（Could not open the database in read/write mode），不是「只有寫入失敗」。

Android 遇到損毀的檔案會自己刪掉重建、不通知任何人，所以 App 是從「資料庫被重新建立了一次」這件事認出重來發生過的（記號放在 shared_prefs/conversation_store.xml，跟著 App 資料一起清掉，全新安裝不會誤報）。 同一個行程裡，重來之後只要有一次讀寫成功，之後再壞還能再重來；剛重建的資料庫馬上又失敗，就不再重來，免得無限循環。

  • 一律在 App 停止時做（am force-stop），改完再冷啟動。Room 看不到 App 以外的修改。
  • 這是 WAL 模式的資料庫，三個檔要當成一份。最近寫入的內容常常只在 -wal 裡：讀的時候三個檔一起複製出來再開；只覆寫 conversations.db 而留著 -wal，SQLite 會照樣從 -wal 讀出完整資料，看起來像什麼都沒壞。
  • 列出每一段對話：select * from conversations。列出某一段的每一則訊息：select id, author, text, createdAt, deleted from messages where conversationId='…' order by position。不需要解開任何東西。
  • 寫入一段自訂的對話（例如只含助理訊息的）：先把三個檔拉出來，用主機上的 sqlite3 開啟，INSERT 一列 conversations，再替它 INSERT 每一則 messages（position 從 0 依序編、deleted 給 0 或 1；sqlite3 會把 WAL 併回主檔），再把 conversations.db 推回去、刪掉裝置上的 -wal 與 -shm。
  • 讓一段對話讀不起來：把它某一則訊息的 author 改成不存在的值（例如 update messages set author='Robot' where conversationId='…' and id=1）。新結構沒有擋這種值，所以造得出來。
  • 讓整份讀不起來：把 conversations.db 整份覆寫成亂碼，並且刪掉 -wal 與 -shm。
  • 改掉資料庫檔記的結構版本號：它是 SQLite 的 user_version。sqlite3 conversations.db "PRAGMA user_version" 讀（現在是 2），"PRAGMA user_version=9" 改成比建置新，推回去並刪掉 -wal、-shm；還原就是改回原本的數字再推一次。
  • 結構版本號宣告在原始碼的哪裡：app/src/main/java/com/example/demo/data/ConversationDatabase.kt 最底下的 const val SCHEMA_VERSION = 2。只把它加一而不在 ConversationMigrations.all 補搬遷，就是「漏寫搬遷」的建置（建置時 Room 會多匯出一份 app/schemas/…/3.json，不影響建置）。
  • 舊結構（版本 1）的說明在版本控制裡：git show e7de9fd:plan/architecture.html 的同一節；舊的儲存形式在 git show e7de9fd:app/src/main/java/com/example/demo/data/ConversationRecords.kt。要從外面寫舊結構的資料列，得用舊版建置建立的資料庫檔。

啟動

回到你離開的地方，而不是最新的那一段

這一段的存在是為了修一個實際踩到的 bug：換了模型、關掉 App、再回來，模型又變回去了。 原因是切換模型會開一段空白的新對話，而空白對話刻意不存進資料庫——否則歷史清單會塞滿沒講過話的空殼。 於是那個切換只活在記憶體裡，程序一被回收就沒了。

搜尋

開著的那段看記憶體，其餘的從資料庫讀出來比——比的規則只有一份

這是最容易做錯的一步：對話存在資料庫裡，而資料庫本來就會查詢，所以「直接下查詢比對」看起來理所當然。錯有兩層。 第一層，那樣會漏掉兩種東西——正開著、卻還沒存過檔的那段對話（只有開場白的對話刻意不存）， 以及還在串流的那則回覆（它此刻只存在記憶體裡）。 第二層，資料庫內建的比對不是我們的比對：它的大小寫折疊只管 ASCII、不認得全形、不會把一串空白收成一個。交給它，同一句話就會「開著的時候搜得到、切走之後搜不到」，而且那是第二份比對規則，是測試看不到的那一份。

所以搜尋的結果＝開著的那一段（記憶體裡的版本）＋資料庫裡其他每一段，兩邊都交給同一個 searchConversations（chat/SearchAssembly.kt）。 資料庫只負責把訊息交出來，不判斷命中：每一次搜尋，資料層依最後更新時間把存下來的對話一批一批（一批 20 段）讀出來，比完只留下命中的那幾則，整批放掉——任何時刻記憶體裡都沒有全部的訊息，資料庫裡也不另存比對用的文字。 同一個 id 兩邊都有時留記憶體那一份（先決定留哪一份、再排序），因為存下來的那份可能時間較新、內容卻比較少。

代價是每一次搜尋都把全部訊息文字從磁碟讀過一遍（使用者知情接受）。所以輸入框停下來 250 毫秒才開始搜尋，搜的是那一刻的內容，打字途中的中間內容不會各自被搜一次； 等待的期間畫面停在上一個狀態。清空不等：輸入框一空就回到引導文案，還在路上的那一次搜尋直接作廢。前一次還在讀的時候查詢又變了，前一次會被取消，晚到的結果不可能蓋上來。 查詢沒變而資料變了時不另外等：開著的那一段變了（串流進一個字、刪除一則）只重算記憶體那一半；資料庫有寫入才重讀資料庫那一半。

結果不是寫進狀態的，而是在狀態送出去的路上接上去的（ChatViewModel.uiState）。結果帶著它所屬的查詢（SearchUiState.searchedQuery），畫面說「找不到符合「…」」時說的是那一個，不是輸入框此刻的字。

一段對話最多列三則命中，其餘只報數字（「還有 N 則符合」），免得一段長對話把其他結果全擠出畫面。 每則命中只顯示一個 60 個字的視窗：命中前面留 20 個字當引子。命中本身有 60 個字（含）以上時裝不下引子，視窗就從命中的第一個字開始。被裁掉的兩端各補一個刪節號。

這是比對層的契約：搜尋框本身打不出這種輸入（見下），但比對層仍然必須答對

輸入框裡留下什麼，跟拿去比對的是兩回事

開頭的空白一打就消失——它對比對毫無作用，留著只會讓空的欄位看起來有東西。 尾端的空白相反，打字時一定要留著：「北京 天氣」中間那一格，在剛打出來的那一瞬間 就是尾端空白，當場刪掉的話，帶空白的查詢就永遠打不出來。它要等到輸入框失去焦點 才移除。中間的空白完全不動。

而拿去比對的一律是整形過的文字，所以這兩次移除都不會改變找到什麼。 判斷「這是不是空白」用的也是上面那一份定義，不是語言內建的 trim—— 內建那一份幾乎一樣，但會多吃掉 U+001C–U+001F，那幾個在任何看得見的文字裡都不是間隔。

攤平是唯一准許改變長度的一步

先把每一段空白收成一個空格，之後索引就是所有人共用的座標系：命中位置、裁切邊界、標示範圍都算在這份攤平後的字串上。 接下來的大小寫與全形折疊是嚴格的一個字元換一個字元——這也是為什麼不能用 lowercase()： 它會把 İ 變成兩個字元，之後每一個標示位置都會偏一格。

空白是所有 Unicode 分隔符，但零寬字元不是

不換行空格、全形空格、行分隔符都算空白——只認 \s 那幾個字元的話，就得回答「為什麼 U+00A0 不算」，而那沒有答案。 零寬字元則刻意不算：它們沒有寬度，折成空格等於插入使用者沒打的空白， 而 U+200D 正是把 emoji 串在一起的那個字元，折掉它會讓 👨‍👩‍👧 裂成三個人。那已經是在改寫訊息了。

什麼算命中，只有一個地方說了算

比對、裁切、標示位置都在一塊不依賴 UI 框架的純邏輯裡算完，畫面只負責把算好的區間上色。 如果哪天畫的那一邊需要自己去 contains 一下，就表示比對規則出現了第二份——而第二份是測試看不到的那份。

開場白也搜得到

送進模型的上下文會丟掉開頭的開場白，但那是「模型該看什麼才答得好」的判斷； 搜尋回答的是「使用者在畫面上看過什麼」。兩個問題允許有不同答案，所以兩道過濾各自獨立，沒有共用。 代價是開場白是固定文案，搜它會在每段對話都命中一次——那是對的，不是雜訊。

已刪除的訊息搜不到，理由是同一個：它的原文不在畫面上。佔位上的字（「已刪除的對話」「復原」）是畫面畫的，不是訊息文字，所以也搜不到。

它是一個獨立畫面，不是抽屜裡的一段

邊打邊篩只有在打字的同時看得到結果才有用，而鍵盤佔掉半個螢幕，輸入框上方每一個固定的像素都是結果少掉的空間。 放在抽屜裡時輸入框落在螢幕中間，鍵盤一升起來就什麼都不剩了。 搜尋模式本身會跟著螢幕旋轉保留下來，轉個方向不會把正在打字的人踢出去。

每一次搜尋都會讀過全部訊息

這是「資料庫裡不存第二份、比對規則只有一份」換來的代價，250 毫秒的等待就是為它存在的。 如果哪天對話多到搜尋開始鈍，第一個該看的就是這裡；加一欄整形後的文字是往前相容的下一步，但那會是資料庫裡第一個派生欄位，要先回到儲存那一節寫明。

不變條件

幾條刻意維持的規則

  • 刪除一則訊息是在它身上做記號，不是把它拿走。已刪除的訊息留在對話的訊息清單裡，位置、id、原文都不動，所以隨時可以復原，新訊息的 id 也不會撞到它。 「當作不存在」由讀的那一方各自決定：送給模型的上下文、搜尋、歷史清單的標題、預覽都略過它；「這段對話是不是空白」照樣算它。 後者不能略過，是因為空白對話存檔時會被從手機上移除——使用者刪光自己說的話再切走，整段對話連同所有原文與復原的路就會無聲消失。 自己說的話全被刪掉的對話，標題是「（訊息已刪除）」，不是「還沒說話」。
  • 對話的「最後更新時間」只跟著內容走。新增訊息、訊息文字改變、訊息被移除、訊息被刪除或復原才算一次更新（訊息算不算數是內容的一部分）；切過去看一眼、切走都不算。否則「最近」會變成「最近被看過」，而歷史清單與搜尋結果的排序都靠這個時間。
  • 一段對話只有一個人格、一個模型。切換任何一個都會開新對話。不然歷史清單上那個標籤就是在說謊。
  • 對話之間的隔離是結構性的，不是靠記得清快取。一則訊息的主鍵是「哪一段＋訊息 id」；每一次存檔與刪除都只指名一個對話 id，包在一筆交易裡，不會動到別段，也不會留下寫到一半的一段。
  • 歷史清單是算出來的，不是存起來的。它跟著資料庫的變動與「現在開著哪一段」持續重算；沒有任何地方需要記得「存完要重讀清單」。
  • 串流片段只能顯示，不能保存。MediaPipe 逐片段解碼，多位元組字元被切在片段邊界就會壞掉。結尾的 Complete 是一次解碼的，那才是要存下來的版本。
  • 比較頁刻意不設長度上限，也不套人格。用中性 prompt 是為了量「誰答得好」而不是「誰比較會演」；不設上限是因為一個模型停不下來，正是比較時最該看到的事。
  • 讀回來的就是存進去的。讀取時不修復、不去空白、不改寫任何文字，刪除狀態也一樣；從舊結構升級時同樣一個碼位都不動。更早的一段對話一個 JSON 檔的紀錄不搬遷，所以也沒有需要重新貼標的舊對話。儲存裡出現認不得的模型或人格名稱時，退回預設值。
  • 預設模型只管新對話。啟動時接續的那段對話沿用它自己的模型，會蓋過預設值——這是刻意的，理由見上面的啟動那節。
  • 只有真的打包進來的模型才會被提供。選單列的是 assets 裡實際存在的那幾個；記住的模型如果已經不在了，就退回現在裝得到的第一個，不會把 App 卡在一個載不起來的選擇上。
  • 每個 Session 都給新的隨機種子。MediaPipe 的預設值是 0，而這個 App 每則訊息開一個新 Session，兩者相加會讓同一個問題永遠得到一字不差的同一個答案——包括同一個壞答案。
  • 搜尋的範圍是使用者看得到的一切，包含還沒存檔的對話和正在串流的回覆。開著的那一段看記憶體、其餘的從資料庫讀出來，用的是同一份比對規則。理由與細節見上一節。

「純邏輯」那一層刻意不依賴 Android、Compose，也不開資料庫，所以上表列為純邏輯的每一塊都能在 JVM 上直接跑單元測試（app/src/test）。 唯一的例外是 data/ConversationRecords.kt 帶著 Room 的表格標註（只是標註，不需要資料庫或 Android 就能執行）。 資料庫本身沒有自動化測試，它靠的是「存檔與刪除各包在一筆交易裡」這個結構與裝置上的驗收。 畫面只負責把算好的結果畫出來——搜尋的標示位置就是這樣送過去的。

ConversationRepository：一個行程一份，只知道存下來的東西

它曾經什麼事都不做，只是轉發。換成資料庫之後它有了三件事：握著行程內唯一的資料庫實例（Room 只通知同一個實例的訂閱者，兩個實例會讓歷史清單停在舊的樣子）、 把歷史清單做成會跟著變動重送的資料流、以及分辨「內容壞了」（丟掉重來並提示）、「開不起來」（什麼都不丟，讓畫面告知）和「寫不進去」（什麼都不丟，回報給呼叫端），判斷不出來時當成開不起來。 搜尋時它把存下來的對話一批一批交出去，但不判斷什麼算命中，也回答不了「畫面上有什麼」——它只知道存下來了什麼。

已知限制

目前修不掉的

  • 1B 級距的事實錯誤。Qwen 會說香港在台灣，Gemma 會把「南」寫成泰盧固文字母。那是模型選錯 token，不是解碼問題，程式層面無解。
  • 重複迴圈只能中斷，不能避免。Gemma 1B 在開放式問題上會陷進去；偵測到之後能做的只有取消生成、把重複的尾巴收成兩輪、在結尾標明中斷原因。那則回覆本質上是壞的，救不回來。
  • SmolLM 不發停止 token。只能靠 800 字元上限攔住，攔下來的回覆本質上是被硬切的。
  • MediaPipe 的 LlmInference 已標記為 deprecated。Google 正在往 LiteRT-LM 遷移，之後升版可能要改 API。
  • 模型佔用重複的 1.65 GiB。維持打包就無法避免。
